# Ключевая информация для агентов (AGENT.md)

Документ поддерживается DevAgent и редактируется пользователем. Содержит
ключевую информацию, необходимую агентам при работе с проектом: требования,
конвенции и ограничения.

## Обязательные конвенции разработки

1. **Текст элементов интерфейса - только из языковых ключей** (`langs/*.json`,
   функция `t()`); прямые строки в UI-коде запрещены (см. NFR5).
2. **Экономия за счёт кэша не должна страдать в результате правок**: сохраняйте
   стабильные кэш-дружественные префиксы запросов LLM - кэш токенов и
   эконом-режим опираются на неизменность ведущих блоков истории.
3. **Минимум сторонних библиотек**: новые зависимости - только в крайнем
   случае, когда без них невозможно обойтись; предпочитайте стандартную
   библиотеку Python.
4. **Один источник версий зависимостей**: устанавливаемый набор задаёт
   `requirements.lock` (точные версии и хэши), а `requirements.txt` и
   `requirements-api.txt` - только пределы версий для его пересборки.
   Установка идёт из lock, сверку ведёт `scripts/ci_check.py`.
5. **Установка только editable** (`pip install -e .`): каталоги данных
   вычисляются от родителя пакета `core` (`core/paths.py`), и обычная
   установка из wheel их теряет.
6. **Форма данных на границе объявляется моделью, а не собирается по
   ключам.** Внутри платформы это dataclass'ы ядра (`core/gateway/dto.py`),
   на проводе - pydantic-схемы (`server/schemas.py`); связывают уровни явные
   мапперы, и только `server/schemas.py` импортирует pydantic. Публичный JSON
   зафиксирован golden-тестами (`tests/test_api_golden.py`,
   `tests/golden/api_contract.json`): изменение контракта - это правка обоих
   файлов в одном коммите, а не побочный эффект рефакторинга.
7. **Число находок статического анализа не растёт.** `pyright` работает в
   режиме `basic` по пакетам `core`, `server`, `storage`, `sagaai`, а предел
   задан в `pyright_budget.json`. Новый отказ означает, что его сначала
   исправляют; поднимать бюджет можно только осознанно, вместе с причиной в
   описании коммита, а снижать - отдельным коммитом.
8. **Структурный бюджет крупных файлов не растёт.** Для файлов, которые ещё
   предстоит разделить, `refactor_budget.json` фиксирует три величины: длину
   файла, длину самой длинной функции и максимальную цикломатическую
   сложность (её меряет `ruff` правилом `C901`). Секция `global` того же
   файла задаёт два абсолютных потолка по всему продакшн-коду - длину самой
   длинной функции и максимальную сложность, - поэтому файл, которого нет в
   списке, всё равно остаётся под проверкой. Бюджет - потолок, а не цель:
   число может упасть, и тогда его правят в том же коммите, но вырасти оно не
   может. Проверка - `python scripts/refactor_budget.py`, в общем конвейере -
   шаг `budget`. Смысл в том, чтобы разделение нельзя было тихо откатить
   обратно, а новая длинная функция не проскочила мимо списка.

9. **Исполнение кода идёт только через песочницу `core/sandbox`.** Профиль
   объявляет требуемую изоляцию и потолки ресурсов, политика выбирает самый
   сильный доступный провайдер и **отказывает**, если ни один не достигает
   уровня (fail-closed), а `core.sandbox.runner` планирует, выполняет и
   записывает запуск в журнал `sandbox_runs`. Неизвестное имя профиля -
   отказ, а не режим по умолчанию. Аргументы инструмента могут только
   ужесточать лимиты профиля. Обход этой точки (прямой `subprocess` в
   инструменте) запрещён: тогда запуск не попадёт в журнал и гарантия
   перестанет быть проверяемой.

   Профиль задаёт и потолок изоляции (`max_isolation`), поэтому «сильнее» не
   значит «лучше»: профиль `off`, которым пользуется снятый переключатель
   «Песочница» в панели чата, требует уровень `none` и запрещает выбирать
   `seatbelt`. Иначе на машине с рабочим ядром отключение не срабатывало бы.
   Лимиты и построенное окружение действуют и в `off`.

   Провайдер получает хостовый `argv` и сам приводит его к тому, что
   существует на другой стороне границы: контейнеру - `python3` вместо
   хостового интерпретатора и монтирование названных путей, WSL - `/mnt/<буква>`
   вместо диска. Если команду нельзя перевести (сетевая шара на Windows),
   запуск **отказывает**: выполнить другой файл вместо проанализированного
   нельзя. Провайдер объявляет только те возможности, которые проверил на этой
   машине: `network-off` у WSL появляется после удачной пробы `unshare -n`, а
   не по факту наличия `wsl.exe`.

   Действующий режим песочницы виден в системном промпте блоком
   `## Code execution sandbox`: профиль, провайдер, гарантии, границы записи,
   сеть и лимиты. Факты берутся из того же решения политики, что и реальный
   запуск (`core/sandbox/status.py`), поэтому описание не может разойтись с
   поведением; отключённая песочница и отказ политики названы прямо.

   Решение человека по опасной операции может прийти и по HTTP (`POST
   /v1/runs/{run_id}/confirm`). Оно превращается в тикет `core/gateway/approvals.py`
   - файл на сервере, привязанный к запуску, к самой операции (хеш аргументов)
   и к сроку, одноразовый и различимый для `allow` и `deny`. Тикет не является
   аргументом инструмента: модель не может его передать, поэтому одобрение
   нельзя подделать из диалога.

## Назначение системы

SagaAI - универсальный AI-ассистент с веб-интерфейсом на базе Streamlit.
Приложение позволяет:
- вести диалог с большими языковыми моделями (OpenAI-совместимые API и GigaChat);
- управлять **помощниками** (system-промптами) - создавать, редактировать,
  удалять, прикреплять к ним файлы;
- переключаться между несколькими языками интерфейса;
- просматривать историю чатов и управлять тредами;
- безопасно редактировать код через **DevAgent** - встроенного разработчика с
  автоматическими бэкапами и контролем изменений;
- в режиме **универсального разработчика** работать с любым сторонним
  проектом, лежащим в отдельной папке, - DevAgent анализирует проект, ведёт
  документацию, создаёт снапшоты и применяет изменения после явного
  утверждения пользователем (либо сразу после плана, если пользователь
  явно выбрал полностью автономный режим без согласования);
- создавать и использовать **оркестраторы** (автономных AI-агентов, в UI
  называемых сотрудниками) на принципах DevAgent, заточенных под узкие
  задачи, с собственными настройками (модели, системный промпт,
  инструменты, инструкции, функции);
- создавать и использовать **базы знаний (RAG)** - хранить документы в
  локальных базах и искать релевантные фрагменты лексически (BM25, без
  API-ключей, режим по умолчанию), семантически (эмбеддинги) или в
  гибридном режиме;
- получать **обновления платформы** через встроенный конвейер обновлений
  (манифест версий, проверка/загрузка/применение без токена, выборочная
  установка, бэкап и откат);
- управлять **доступом к приложению** на странице «Доступы» (доступ по
  паролю: пароль из формы каноничен, `SAGAAI_AUTH_PASSWORD` - запасной
  источник, интервал повторного запроса).

## Функциональные требования

### FR1 - Чат с AI-моделью
- Пользователь выбирает Помощник (или оставляет стандартный) и вводит
  запрос.
- Поддерживается прикрепление файлов (текстовых, PDF, офисных форматов) -
  их содержимое добавляется в контекст.
- Встроенные изображения документа читаются отдельным шагом:
  `extract_document_images` сохраняет картинки PDF/DOCX/PPTX/XLSX файлами
  в `.dev_agent/doc_images/` рабочей папки и отдаёт группы для
  `analyze_image`, который возвращает текст под меткой `DATA_FROM_IMAGE`.
  Страницы PDF без текстового слоя (сканы) можно отрендерить в картинки.
- Ответ модели рендерится в виде Markdown с подсветкой кода и кнопкой
  копирования.
- Возможность создать новый диалог в любой момент.

### FR2 - Управление помощниками
- Создание помощника: имя, описание, системный промпт, опциональные файлы.
- Редактирование и удаление существующих помощников.
- Файлы помощника хранятся на диске и прикрепляются к контексту при вызове.
- Помощники сортируются по времени последнего использования в связанных
  тредах.
- Секция «Помощники» в сайдбаре: первые 5 позиций всегда видимы,
  остальные - в свёрнутом блоке «Все (N)»; поле поиска отображается
  только при количестве помощников > 5.
- При создании помощника автоматически подбирается подходящий сервис и
  модель (модуль `assistant_model_resolver`): классификация сложности и
  необходимости web_search; без веб-поиска используется основная модель
  из настроек оркестратора, с веб-поиском - модель YandexAI (pro/lite по
  сложности).
- Промпт помощника можно улучшить автоматически: сервис `prompt_improver`
  использует основную модель DevAgent и инструкцию `prompt_improver` для
  генерации улучшенной версии промпта.

### FR3 - Многоязычность
- Интерфейс переводится через JSON-файлы (`langs/en.json`, `langs/ru.json`,
  `langs/zh-CN.json`); канонические копии хранятся в `defaults/langs/`.
- Язык выбирается в боковой панели; сохраняется в настройках.
- Функция `t()` в `core/i18n.py` обеспечивает двухуровневый fallback:
  1. Если перевод отсутствует в выбранном языке, берётся значение из
     английского файла (`en.json`) - канонического источника всех ключей.
  2. Если ключ отсутствует и в английском файле, возвращается сам ключ.
- **Английский файл (`en.json`) всегда должен содержать актуальный полный
  набор ключей.** Остальные языковые файлы могут отставать - недостающие
  строки автоматически подтягиваются из английского.
- Названия оркестраторов и помощников хранятся в четырёх слотах: `name`
  (пользовательское имя) и `name_en` / `name_ru` / `name_zh`. Интерфейс
  показывает пользовательское имя в любом языке, а переводы (`name_en`,
  `name_ru`, `name_zh`) служат запасным вариантом: язык интерфейса, затем
  английский, затем любой непустой слот. Запись без единого непустого имени
  отклоняется.
- Те же четыре слота входят в `orchestrator.json` и `manifest.json`, в
  каталог маркетплейса (`name` как объект переводов) и в дефолтные
  оркестраторы и помощники; пользовательское имя при обновлении из каталога
  не перезаписывается.
- Установка агента переносит переводы карточки в слоты: `_apply_entity_names`
  подставляет `name_ru` / `name_zh` из карточки каталога, если имя пакета
  совпадает с английским именем карточки (автор повторил каталожное имя -
  значит оно не его собственное). Имя, которого в карточке нет, считается
  авторским и остаётся в пользовательском слоте без изменений.

### FR4 - История чатов
- Все диалоги сохраняются в виде тредов с привязкой к помощнику.
- Список тредов доступен на странице истории; каждый тред можно открыть,
  удалить, либо удалить все треды сразу.
- Метаданные треда и сообщения хранятся в SQLite.
- Диалоги оркестраторов хранятся отдельно (БД `devagent.db`) и доступны на
  вкладке «История» соответствующей страницы оркестратора.
- Файлы, загруженные пользователем в диалог оркестратора, сохраняются как
  сырые байты в `history/<tid>/files` (единый источник вложений диалога;
  платформа не извлекает их содержимое).

### FR5 - Настройки
- Конфигурация API-ключей: endpoint, ключ, модель, температура.
- Возможность протестировать соединение до сохранения.
- Настройки сохраняются в конфигурационном хранилище (SQLite KV).
- Встроенные настройки DevAgent (основная модель, опциональные модели
  распознавания и генерации изображений, поисковая модель, температуры,
  системный промпт, эконом-режим, инструкции) живут на
  странице самого оркестратора - Настройки → Модели / Промпт /
  Эконом-режим / Инструкции.
- Страница «Настройки» в общем меню содержит только API-ключи и переменные
  окружения.

### FR5a - Боковое меню (навигация)

Меню собрано из четырёх блоков в фиксированном порядке: **СОТРУДНИКИ**,
**ПОМОЩНИКИ**, **МАРКЕТПЛЕЙС**, **НАСТРОЙКИ**.

- Сотрудники и помощники показывают первые пять позиций, остальные уходят
  в свёрнутый блок «Все (N)»; поиск появляется при количестве больше пяти.
- Блок «МАРКЕТПЛЕЙС» (под флагом `marketplace.enabled`) раскрывает пять
  подразделов каталога: сотрудники, помощники, навыки, базы знаний,
  коннекторы. Подраздел - это пара «тип каталога + вид агента»: сотрудники
  и помощники делят тип `agent`, но ставятся в разные места, поэтому
  показаны отдельными списками. Клик по подразделу открывает витрину на
  нужной вкладке, а выбранная на витрине вкладка подсвечивает пункт меню
  обратно: обе стороны пишут один ключ `mp_section`, а запрос из меню идёт
  отдельным ключом `mp_section_target`, потому что записать состояние
  вкладки после её создания Streamlit не даёт.
- Блок «НАСТРОЙКИ» держит три постоянных пункта - Провайдеры, Коннекторы,
  Обновления; остальные семь (сотрудники, навыки, библиотека навыков, базы
  знаний, доступы, статистика, о программе) собраны в свёрнутом «Ещё (7)».

### FR6 - Оркестраторы (сотрудники)
- **Оркестратор** - автономный AI-агент (как DevAgent) со своим системным
  промптом, конфигурацией моделей, эконом-режимом, набором инструментов,
  инструкциями и пользовательскими функциями. В UI оркестраторы
  называются сотрудниками.
- Каждый оркестратор отображается **отдельной страницей в общем меню**
  (сайдбаре). DevAgent - встроенный оркестратор (slug `dev_agent`,
  `is_builtin=True`), всегда доступен и не может быть удалён.
- Кроме DevAgent платформа при первом запуске сеет **Universal-Agent**
  (slug `universal_agent`) из `defaults/orchestrators/universal_agent/`:
  универсальный исполнитель, который берёт роль, требования и ожидаемый
  результат из постановки задачи, а не из собственной специализации.
  Сидинг идемпотентен: повторный запуск возвращает `exists` без второй
  копии, а удалённый пользователем сотрудник не возвращается.
- Второй встроенный сотрудник - **Task Scout** (slug `task_scout`) из
  `defaults/orchestrators/task_scout/`: проактивный поиск задач, которых
  никто не записал. Принцип роли - сначала спросить делегированных
  сотрудников (`spawn_agent`), затем читать их рабочие папки и лишь в
  последнюю очередь диалоги; результат разделён на открытые, обещанные и
  вытекающие задачи с указанием источника. Роль поставляется с пустым
  `allowed_agents`: на чистой установке агент называет сотрудников,
  которых надо отметить на вкладке «Делегирование», вместо выдуманного
  списка дел. Два read-only инструмента (`agent_memory_reader`,
  `agent_thread_reader`) проверяют тот же список, поэтому угаданный slug
  или `thread_id` чужого сотрудника не расширяет права.
- Секция «Сотрудники» в сайдбаре: первые 5 позиций всегда видимы,
  остальные - в свёрнутом блоке «Все (N)»; поле поиска отображается
  только при количестве сотрудников > 5.
- Порядок сотрудников стабилен между перезапусками и определяется
  активностью: по времени последнего диалога (последний тред в
  `devagent.db`), а при его отсутствии - по времени создания; новый
  сотрудник появляется вверху списка.
- Страница оркестратора содержит вкладки: **Чат**, **История** и
  **Навыки**; ссылка на отдельную страницу **Настройки**.
- Настройки моделей - сервис + модель + температура: основная модель
  используется на всех шагах. У встроенного DevAgent поставляемые
  дефолты: основная модель - DeepSeek/`deepseek-flash` с уровнем
  рассуждений `xhigh`, распознавание изображений -
  DeepSeek/`deepseek-flash`, генерация изображений не назначена;
  поисковая модель - DeepSeek/`deepseek-flash` с температурой 0.4, не
  более чем 3 вызовами инструментов и уровнем рассуждений `high`
  (диапазон температуры определяется из файла описания сервиса). Модель
  загрузки страниц назначается отдельно и по умолчанию пуста.
- Модель, на которой сотрудник работает, определяет единый резолвер
  `resolve_strong_model(config)` в `core/orchestrator_strong.py`:
  настроенная пара `strong_service` / `strong_model`, затем устаревшие ключи
  `service` / `model`, затем платформенный дефолт
  (`DEFAULT_STRONG_SERVICE` / `DEFAULT_STRONG_MODEL`). Ответ у резолвера
  никогда не пустой, поэтому сотрудник без модельных ключей запускается на
  платформенном дефолте. Гейт страницы чата и сборка промпта спрашивают
  именно резолвер, а не сырой `config`: иначе страница блокировала бы
  сотрудника, которого среда исполнения всё равно запустила бы.
- Установка агента из каталога заполняет модельный базис тем же дефолтом
  (`core/marketplace/install_seed.py`, `_seed_platform_config`), не
  перезаписывая ключи пакета: агент из каталога стартует так же, как
  встроенный сотрудник. Оттуда же приходят переводы имени из карточки
  каталога (`_apply_entity_names`).
- Системный промпт оркестратора редактируется в отдельной вкладке. Правки
  промпта встроенного оркестратора (DevAgent) сохраняются между
  перезапусками: UI ставит маркер `prompt_user_edited`, и стартовое
  обновление больше не перезаписывает промпт из `dev_agent/system_prompt.md`.
  Вернуть поставляемый промпт можно кнопкой сброса на той же вкладке.
- К системному промпту каждого оркестратора при построении добавляется
  англоязычный блок `## Available tools` - перечень доступных инструментов
  (системные, workspace, инструменты включённых подключений, кастомные
  функции) с краткими правилами вызова. Каноничные промпты встроенных
  оркестраторов (`dev_agent/system_prompt.md`, YaAgent) не дублируют
  справочник таблицами инструментов: они ссылаются на автоматический
  блок и содержат только собственные правила использования.
- После каталога инструментов в промпт добавляется блок `## Current date` -
  единственный источник «сегодня» для модели. Модель не имеет часов,
  поэтому без блока дата либо угадывается, либо берётся из файла, который
  записал дату СОЗДАНИЯ: сводка расписания устаревает молча и продолжает
  отвечать за прошедший день. Блок выводится для каждого сотрудника, состоит
  из одного факта (`Today is Monday, 02 November 2026.` и строка
  `Installation timezone: MSK (UTC+03:00).`) и правил использования не
  содержит - системный промпт и без того велик.
- Блок стоит ПОСЛЕДНИМ: это единственный блок, меняющийся со временем, и в
  хвосте промпта смена суток инвалидирует только хвост префикса
  провайдерского кэша. Времени суток в блоке нет намеренно - метка с
  точностью до минуты ломала бы кэш на каждом шаге.
- День недели и месяц названы словами из таблиц `_WEEKDAY_NAMES` /
  `_MONTH_NAMES`, а не через `strftime('%A')`: локаль процесса не должна
  менять текст промпта.
- `config['current_date_enabled']` (булево либо строка
  `'false'`/`'no'`/`'off'`/`'0'`) убирает блок у конкретного сотрудника;
  по умолчанию включён. На инструмент выключатель не влияет.
- Инструмент `current_datetime` отдаёт то, что факт решить не может: время
  суток, день недели заданной даты, epoch. Ответ содержит `iso`, `date`
  (`ДД.ММ.ГГГГ`), `date_iso`, `weekday`, `weekday_ru`, `time`, `timezone`,
  `utc_offset`, `epoch`, `date_line`; `date_line` строится той же функцией,
  что и блок промпта, поэтому два источника не расходятся.
- Дата берётся только из системного времени. Сводки, кэши и журналы
  (`TODAY.md` и подобные) дату своего создания не задают: при расхождении с
  блоком файл считается устаревшим.
- В настройках оркестратора (вкладка «Функции») системные функции показаны
  с чекбоксами включения/выключения; выбор сохраняется в
  `config['disabled_tools']`.
- Отключённые инструменты исключаются из промпта и реально блокируются
  диспетчером при вызове (ошибка `disabled: true` до выполнения;
  legacy-алиасы учитываются в обе стороны).
- Модель загрузки страниц выбирается только из сервисов,
  объявляющих каталог `fetch_models` (Search/Fetch API провайдера;
  сейчас DeepSeek - `fetch_base_url`
  `https://api.deepseek.com/v1/tools/fetch`, модели `deepseek-flash` и
  `deepseek-v4-pro`). Пара хранится в конфигурации оркестратора
  (`fetch_service` / `fetch_model`); пустое значение = возможность
  выключена. Независимый переключатель `fetch_selenium` включает
  отрисовку страниц в headless-браузере. На вкладке «Модели» чек-бокс
  Selenium рисуется первым: пока он включён, селекторы пары
  `fetch_service` / `fetch_model` скрыты (подпись поясняет, что Markdown
  формирует основная модель), а сохранённая пара не сбрасывается и
  возвращается после снятия флажка.
- Инструмент `url_fetch` (прежнее имя `page_fetch` осталось
  legacy-алиасом) доступен, когда назначена fetch-модель ИЛИ включён
  Selenium. Ветки: PDF по ссылке (файл скачивается, текст извлекается
  pypdf и разбивается на страницы `### Page N`); Selenium -
  видимый текст отрисованной страницы, основная модель оркестратора
  формирует из него Markdown; иначе - Search/Fetch API провайдера
  (POST `{"url": ...}`), возвращающий Markdown с заголовком и адресом.
  URL валидируется (http/https, не длиннее 8192 символов, без логина и
  пароля, без приватных адресов), результат санитизируется и маркируется
  `[DATA_FROM_URL_FETCH]` как недоверенные данные, длина ограничена
  30 000 символов с пометкой об обрезке. Инструмент исчезает из
  каталога, блока `## Available tools` и списка системных функций, как
  только сняты и модель, и Selenium (или модель пропала из каталога
  сервиса).
- Назначенные модели изображений используются системными инструментами
  `analyze_image` (распознавание: файлы проекта и вложения диалога; сервис
  объявляет каталог `vision_models`: YandexAI - `qwen3.6-35b-a3b` и
  `deepseek-v4.1-flash`, DeepSeek - `deepseek-flash` через выделенный
  chat/completions endpoint `vision_base_url` с `detail="original"`) и
  `generate_image` (генерация: синхронный OpenAI-совместимый Images API
  YandexAI, модель `aliceai-image-art-3.0`; результат сохраняется файлом -
  в workspace или в папке файлов диалога, base64 не возвращается - и
  сразу показывается в ленте чата (вне свёрнутого блока результата
  инструмента) с кнопкой скачивания); при незаданной
  модели возвращается ошибка `not_assigned` с подсказкой, где назначить
  модель (глобальная инструкция `multimodal_mode`).
- Эконом-режим настраивается отдельно для каждого оркестратора (tail
  messages, кэш-режим).
- Строка токенов в ленте чата собирает честный кэш-бакет провайдера на
  всех транспортах (bearer/DeepSeek - `prompt_tokens_details.cached_tokens`
  с фолбэком `prompt_cache_hit_tokens`, GigaChat - `precached_prompt_tokens`,
  Responses - `input_tokens_details.cached_tokens`); метки строки
  локализованы (`token_line_*` во всех языковых файлах), а кэш строки
  учитывает язык интерфейса.
- Инструкции оркестратора хранятся в папке оркестратора
  (`orchestrators/<slug>/instructions.json` и `*.md`) и управляются со
  страницы оркестратора.
- **Экспорт/импорт** реализован на уровне core API
  (`core.orchestrators.export_orchestrator` / `import_orchestrator`, формат
  `sagaai_orchestrator/v1`). **UI для экспорта/импорта оркестраторов
  намеренно отложен** - в интерфейсе соответствующие кнопки отсутствуют.
- При импорте с конфликтом slug генерируется новый (`slug_2`, `slug_3`,
  …); инструкции импортируются без перезаписи существующих (по id).
- Страница чата оркестратора имеет одну панель инструментов (липкую сверху):
  web-поиск, safety-режим, «Настройки», «Новый диалог», «Копировать URL».
  Чекбоксы синхронизированы с каноническим значением в `session_state`
  и персистентностью в конфиге оркестратора. Эконом-режима в панели нет:
  компактный контекст - штатный режим чата (`ECONOMY_MODE_ALWAYS_ON`), он
  передаётся в цикл агента всегда, а исторический ключ
  `chat_economy_mode` игнорируется.
- Кнопка «Копировать URL» формирует deep-link вида
  `?orchestrator=<slug>&thread=<tid>` (thread опционален). При открытии
  приложения с таким параметром `ui/app.py` загружает указанный диалог
  (или начинает новый), переключает страницу и убирает параметры из URL
  (обработка идемпотентна).
- Лента чата показывает панель выгрузки/копирования (кнопки **📥 MD / 📥 TXT** и **Copy MD / Copy TXT**) у каждого текстового ответа ассистента без вызовов инструментов, а не только у финального; сообщения с распознанными вызовами инструментов панели не получают, даже если содержат видимый текст, а у «живого» финального ответа панель скрыта до завершения цикла агента (`ui/pages/orchestrator.py`).
- Системный промпт встроенного `dev_agent` автоматически обновляется из
  единственного источника `dev_agent/system_prompt.md` при каждом старте
  приложения (отдельная копия в `defaults/` не поддерживается).
- Чат оркестратора принимает вложения **любого формата** (без фильтра
  типов) прямо в поле ввода: `st.chat_input(accept_file="multiple")`
  показывает иконку-скрепку с всплывающей подсказкой, отдельного блока
  `file_uploader` и подписи «Прикрепить файлы любого формата…» больше нет.
  При отправке байты сохраняются в `history/<tid>/files`, в сообщение агента
  добавляется уведомление со списком файлов, а в персистентный префикс
  каждого запроса - тот же список. Если текста нет, а файлы приложены,
  сообщением задачи становится i18n-строка `orch_attach_only_message` с
  именами файлов. Платформа не извлекает содержимое на своей стороне; агент
  делает это штатными инструментами: `list_thread_files` / `read_thread_file`
  (текст документов - PDF, DOCX, PPTX, XLSX, XLS, RTF, ODT, HTML - через
  `core.document_text`) и `read_document` для файла на диске по абсолютному
  пути с окном строк. `run_code` для таких форматов не нужен: он оставлен
  последней очередью для операций без специализированного инструмента. Лимит
  одного файла - 100 МиБ.
- **Поиск по диалогам:** инструменты `search_in_threads` (поиск по
  сообщениям; по умолчанию - текущий диалог, без предварительных
  листингов; явный `thread_id` работает без списков; `scope` по
  оркестратору(ам) или всем диалогам; период по дате активности; regex;
  фильтр по роли), `list_threads` (список диалогов с пагинацией и
  счётчиками сообщений) и `read_thread` (окно сообщений с абсолютными
  индексами; по умолчанию - текущий диалог). Скрытые служебные сообщения
  (`tool_result` / `AUTO_CONTINUE`) по умолчанию исключаются из поиска и
  чтения. Контроль доступа: DevAgent видит все диалоги, остальные
  оркестраторы - только свои (чужие `thread_id` получают `Access denied`).
- **Прозрачные ретраи при обрывах связи:** LLM-запросы оркестраторов
  автоматически повторяются при `RequestTimeoutError` / `NetworkError` -
  пауза между попытками `SAGAAI_NETWORK_RETRY_DELAY` (по умолчанию 30 с),
  максимум `SAGAAI_NETWORK_RETRY_ATTEMPTS` попыток подряд (по умолчанию 3);
  в ленту чата добавляется событие `retrying_llm` (i18n-ключ
  `orch_retry_llm`). Сообщение пользователя сохраняется в историю ДО
  вызова модели, поэтому диалог не теряется даже после исчерпания всех
  попыток (`core/api_layer.py`, `core/assistant_tools.py`,
  `dev_agent/agent_loop.py`, `ui/pages/orchestrator.py`).
- **Ошибки Responses API не маскируются под пустой ответ.** Тело HTTP 200
  со статусом `failed` и/или объектом `error` (Yandex AI Studio, DeepSeek)
  поднимается как `ProviderResponseError` с кодом и текстом провайдера
  вместо молчаливого пустого ответа; то же касается native function-цикла
  ассистентов и проверки соединения в настройках (`(False, <текст>)`
  вместо OK). Пустые и whitespace-only сообщения истории исключаются из
  `input` запроса - каскад HTTP 400 «Content of input is empty» после
  сохранённого пустого ответа устранён (`core/api_layer.py`,
  `core/assistant_tools.py`, `core/api_errors.py`).
- **Усечённый (incomplete) ответ не выглядит как пустой.** Тело HTTP 200
  со статусом `incomplete` (обычно `incomplete_details.reason ==
  "max_output_tokens"`: бюджет рассуждений съел весь лимит вывода и
  видимого текста не осталось) детектируется в обоих Responses-провайдерах
  (`_responses_incomplete_details`, Yandex AI Studio и DeepSeek) и
  пробрасывается наружу необязательным `incomplete_callback`. Оркестратор
  (`dev_agent/agent_loop.py`) при пустом тексте делает РОВНО ОДИН
  восстановительный повтор с `reasoning_effort='none'` (весь бюджет уходит
  на видимый текст), сохраняя файловый контекст пользователя, и показывает
  в чате событие `incomplete_retry` (i18n-ключ `orch_incomplete_retry`).
  Ответ с видимым текстом не повторяется; повтор ограничен одним разом на
  шаг (`core/api_layer.py`, `dev_agent/agent_loop.py`,
  `ui/pages/orchestrator.py`).
- **Фасад `dev_agent/agent_loop.py` сохраняет имена, реализация - в `loop/`.**
  Модуль остаётся точкой входа цикла и держит ВСЕ публичные и приватные имена
  (`run_agent_loop`, `step_agent_loop`, `parse_tool_calls`, константы): тесты и
  monkeypatch-точки обращаются к ним через алиас модуля. `LoopRuntime`
  собирается из собственных module-level атрибутов фасада в момент вызова,
  поэтому `monkeypatch.setattr(agent_loop, 'send_request', ...)` действует и
  на код шагов. При переносе кода в `loop/` не разрывать это свойство: шаги
  берут runtime параметром, а не импортируют фасад (иначе циклический импорт).
- **Фасад `ui/pages/orchestrator.py` сохраняет имена, реализация - в `orchestrator_*`.**
  Страница разложена по темам: фасад держит импорт-блок (реэкспорты
  `orchestrator_text` для страницы и тестов), тонкие обёртки и две точки
  входа `page_orchestrator`/`page_devagent`, а тела - в `orchestrator_state`,
  `orchestrator_folder`, `orchestrator_loop`, `orchestrator_feed`,
  `orchestrator_chat`, `orchestrator_chat_input` и трёх
  `orchestrator_settings_*`. Подменяемое имя модуль объявляет один раз через
  `late("имя")` или `st_proxy()` из `ui/pages/orchestrator_shared.py` и
  разрешает на фасаде в момент вызова, поэтому
  `monkeypatch.setattr(orch_mod, "t", ...)` действует и на вынесенный код;
  `bind_facade` привязывает слой к объекту фасада, иначе вторая живая копия
  пакета (тесты, чистящие `sys.modules`) перехватывала бы подмену. При переносе
  кода не импортировать фасад из спутников - только `late`/`st_proxy` (иначе
  циклический импорт).

- **Фасад `core/orchestrators.py` сохраняет имена, реализация - в `orchestrator_*`.**
  API разложен по темам: фасад держит импорт-блок, реэкспорты и тонкие
  обёртки, а тела - в `orchestrator_defaults`, `orchestrator_store`,
  `orchestrator_links`, `orchestrator_prompt`, `orchestrator_models`,
  `orchestrator_strong`, `orchestrator_transfer`, `orchestrator_instr` и
  `orchestrator_builtin`.
  Подменяемое имя, ЗАИМСТВОВАННОЕ из другого модуля, спутник объявляет через
  `late("имя")` из `core/orchestrator_shared.py` и разрешает на фасаде в
  момент вызова, поэтому `monkeypatch.setattr(orch_mod, "get_orchestrator",
  ...)` и `patch("core.orchestrators._get_services")` действуют и на
  вынесенный код; `bind_facade` привязывает слой к объекту фасада, иначе
  вторая живая копия пакета (тесты, чистящие `sys.modules`) перехватывала бы
  подмену. Имя, которое спутник определяет сам, в late не нуждается: фасад
  оборачивает его в `<имя>_impl` тонкой функцией, и подмена на фасаде
  заменяет именно обёртку. При переносе кода не импортировать фасад из
  спутников - только `late` (иначе циклический импорт); `repo_*` и
  `_get_services` остаются атрибутами фасада и объявлены late в спутниках.


- **`core/chat_turn.py`** - один ход чата с помощником: история в форме API,
  вызов провайдера, сбор расхода и запись пары «вопрос → ответ» с вложением.
- **`core/orchestrator_step.py`** - запись шага агента в тред: отсечение уже
  сохранённого по курсору, карта полей истории в поля хранилища и
  возврат нового курсора, поэтому повторный вызов ничего не дублирует.

### FR7 - DevAgent (встроенный разработчик)
- DevAgent - встроенный оркестратор с slug `dev_agent`, работает как
  универсальный разработчик.
- Страница DevAgent - это `ui/pages/orchestrator.py` (фасад) и модули
  `ui/pages/orchestrator_*` с вкладками
  Чат / История / Навыки и отдельной страницей Настройки
  (`ui/pages/orchestrator_settings.py`).
- Настройки моделей и промпта доступны на странице DevAgent → Настройки.
- Агент использует единую основную модель на всех шагах: служебная
  классификация шага (`classify_step_strength`) сохраняется для
  журналирования, но модель не переключает.
- Агент предлагает изменения как полную перезапись файла (`propose_file`)
  либо точечные правки (`apply_patch`); в автономном режиме изменения
  применяются после утверждения плана, в ручном - после явного одобрения
  пользователем. Если пользователь передал готовый план (в том числе
  файлом), агент один раз уточняет, следовать ли плану в точности или
  сначала проанализировать код; при выборе «следовать в точности» план
  пользователя записывается в журнал задачи дословно и исполняется без
  фазы утверждения. Если передан подробный план, спецификация или ТЗ без
  требования точного следования, агент спрашивает, действовать ли
  полностью автономно или согласовать итоговый план после анализа; при
  явном выборе «без согласования» план всё равно составляется, но фаза
  утверждения пропускается и исполнение начинается сразу.
- Все изменения автоматически бэкапятся; возможен откат как отдельных
  файлов, так и всей кодовой базы (снапшоты).
- Для сложных многоэтапных задач агент ведёт внешнюю память
  `TASK_STATE.md` (архитектура, план, прогресс, handoff); инъекция
  журнала бюджетирована, восстановление состояния - по компактному
  дайджесту (`task_state_read(compact=True)`), полное чтение - по
  требованию.
- Агент может отправлять **несколько независимых вызовов инструментов
  в одном сообщении (батч)**: раннер парсит каждый фенс-блок, выполняет
  вызовы по порядку и возвращает все результаты вместе одним сообщением;
  батчить разрешено только независимые вызовы (нет общего файла-адресата,
  нет зависимости от результатов соседнего вызова, нет вызовов с
  подтверждением; записи - по одной до подтверждения авто-применения).
  Если часть блоков батча не распарсилась, валидные вызовы исполняются,
  а к результатам добавляется предупреждение `partial_batch` с
  диагностикой по каждому сломанному блоку (включая `TRUNCATED` и
  несбалансированные скобки/строки).
- Формат вызова инструментов: основной и единственный рекомендуемый -
  фенс-блок JSON (`{"tool": ..., "args": {...}}`). Резервный формат -
  DSML-диалект DeepSeek с зарезервированным токеном
  (`<｜｜DSML｜｜ invoke name="...">` + `<｜｜DSML｜｜ parameter>`); парсер
  толерантен к маркеру перед каждым тегом, разворачивает обёртку
  `name="args"` с JSON-объектом и ремонтирует лишнюю закрывающую скобку.
  Вызов, у которого аргументы не восстановлены, не исполняется с пустыми
  аргументами: он уходит в каскад JSON-ремонта, а модели возвращается
  подсказка формата. Резервная разметка никогда не попадает в чат -
  `_strip_tool_calls` вырезает её вместе с обычными XML-обёртками.
  После успешного исполнения шага, использовавшего DSML (разметка
  напрямую или DSML-хвост рядом с валидным JSON-вызовом), к результатам
  инструментов добавляется однострочное напоминание «Don't use DSML
  anymore, use only JSON for tool calling», пока модель не перейдёт на
  чистый JSON.
- Цикл агента защищён от зацикливания: счётчик отказов по инструменту
  (без учёта аргументов) после трёх подряд неудачных вызовов одной
  функции добавляет подсказку сменить инструмент по fallback-цепочке
  (вплоть до `run_code`), успех сбрасывает счётчик; поток одинаковых
  вызовов в одном сообщении схлопывается в одну компактную ошибку
  `identical_blocks`/`identical_calls` без диспатча.

### FR8 - Универсальный разработчик
- Возможность переключения рабочей папки на любой внешний проект.
- Изоляция рабочей папки между параллельными диалогами: активная папка
  привязана к потоку диалога (thread_id), а не к глобальному состоянию
  процесса; переключение папки в одном диалоге не влияет на другие
  параллельные диалоги. Привязка сохраняется в БД и восстанавливается
  при повторном открытии диалога, в том числе после перезапуска.
- **Пустое состояние «папка не выбрана»:** новый или сброшенный диалог
  стартует без папки - файловые инструменты отвечают структурной ошибкой
  `workspace_not_selected` с подсказкой выбрать папку, а `run_code`/`run_test`
  с `code=` выполняются с нейтральным cwd; после выбора папки состояние
  снимается. Два корня остаются доступны и без папки: рабочий каталог
  сотрудника (`memory:`) и папка файлов текущего диалога (`thread:`) - они
  принадлежат установке, а не проекту. Запрет проверяет каждый путь вызова
  (`dev_agent/tools/path_scope.py`): одного проектного пути в пакете
  достаточно для отказа.
- **«Последняя папка» треда:** путь хранится в мете треда
  (`workspace`/`target_file`; `NULL` - пустое состояние) и восстанавливается
  при открытии диалога; диалог без папки или с исчезнувшей папкой
  открывается пустым и не наследует папку соседнего диалога. Одноразовая
  миграция очищает легаси-мету тредов остальных оркестраторов, указывающую
  на платформенные корни.
- **Недавние папки** скоупятся по оркестратору: у каждого сотрудника своё
  меню (до 10 позиций); пути платформенной установки не показываются
  другим оркестраторам.
- **Блок «Выбор папки» в чате:** статичный селектор под полем ввода -
  «Авто», до 10 недавних папок оркестратора и последним пунктом нативный
  выбор папки на компьютере (`core/folder_dialog.py`: tkinter в дочернем
  процессе с откатом на osascript в macOS; без GUI пункт скрыт, остаётся
  ручной ввод пути). Отдельной кнопки «Обзор…» рядом с полем ввода нет:
  кнопка у скрепки-загрузчика читалась как «прикрепить файл», поэтому
  открытие диалога перенесено внутрь селектора - пункт-действие не
  залипает, после выбора или отмены селектор возвращается к выбранной
  папке. Выбранная папка применяется автоматически при отправке сообщения
  (до вызова модели), после чего селектор возвращается в «Авто», а активный
  путь виден под полем. Уже действующая папка повторно не применяется;
  активный путь показывается по привязке треда, поэтому временное
  переключение папки агентом не конфликтует с выбором в интерфейсе.
- **Авто-прокрутка ленты чата** (`core/feed_autoscroll.py`): пока агент
  работает, лента следует за новым выводом; ручная прокрутка вверх ставит
  слежение на паузу, возврат к низу - возобновляет; отправка сообщения
  форсирует прокрут вниз. Скрипт выводится через
  `st.html(unsafe_allow_javascript=True)` и исполняется в главном документе
  (устаревший `st.components.v1.html` работал в песочнице iframe, не видел
  скролл-контейнер приложения и писал предупреждение об удалении на каждый
  вызов). Скролл-контейнер ищется по атрибуту
  `[data-testid="stAppScrollToBottomContainer"]` и `#stMain` - в Streamlit
  1.66 это узел `main`, у которого тестид перекрывает `stMain`, а класса
  `section.main` больше нет. Отступ снизу модуль не задаёт - Streamlit 1.66
  сам резервирует место под липкой панелью.
- **Файлы во вводе чата:** загрузчик встроен в само поле ввода
  (`st.chat_input(accept_file="multiple")`, иконка-скрепка с всплывающей
  подсказкой); отдельной dropzone и подписи про «любой формат» нет. Файлы
  уходят вместе с текстом одной отправкой: только файлы - задача получает
  i18n-строку с их именами; только текст - как раньше.
- **Журналы задач и вложения диалога** при пустой папке живут в папке
  диалога (`history/<tid>/`) и не пишутся в чужие проекты.
- Автоматическое построение карты проекта (`PROJECT_MAP.md`), ведение
  `AGENT.md`, `ARCHITECTURE.md` и журнала изменений.
- Карта проекта - генерируемый документ: ручная правка запрещена, обновление
  выполняется только регенерацией (канонический генератор проекта; в
  репозитории платформы - `scripts/regenerate_project_map.py`). Состав карты
  покрывает только файлы, публикуемые на GitHub (`units[*].files` +
  `selectable` из `file_versions.json`); символы Python извлекаются
  AST-разбором (классы, методы, async-функции, вложенные определения,
  фактические диапазоны строк; лимит 200 символов на файл с пометкой об
  остатке; regex-фолбэк для файлов с синтаксическими ошибками). В шапке
  карты фиксируется sha256-отпечаток содержимого включённых файлов -
  расхождение с `build_project_map()['fingerprint']` означает устаревание.
- Агент работает с выбранной папкой как с собственной кодовой базой,
  применяя все правила безопасности DevAgent.
- Инструмент поиска `search_in_files` сканирует текстовые файлы проекта
  (по умолчанию типовые текстовые расширения); явный список `extensions`
  переопределяет набор по умолчанию, что позволяет искать в `.csv`,
  `.xml`, `.log` и т.п. Поиск регистронезависимый, лимит результатов -
  100 (c `truncated: true` при достижении). Файлы в иных кодировках
  декодируются через UTF-8→cp1251 fallback; нечитаемые и слишком большие
  файлы пропускаются и учитываются счётчиками `files_unreadable` /
  `files_skipped_large`.

### FR9 - Создание помощников
- Динамическое обнаружение помощников (assistant detection) **отключено**.
  `detect_and_select_assistant()` всегда возвращает пустой результат.
- Создание помощника происходит только по **явному запросу пользователя**
  (например, «Создай Помощник проверки орфографии»).
- Для создания помощника DevAgent вызывает `create_assistant_for_task()`,
  который использует **Assistant Creator** (id: `assistant_creator`).
- Assistant Creator - **внутренняя инструкция** DevAgent-оркестратора
  (хранится в `defaults/orchestrators/dev_agent/instructions/assistant_creator.md`
  и рантайм-копии `orchestrators/dev_agent/instructions/`), не является
  пользовательским помощником. Его промпт определяет строгие критерии
  качества для генерации новых помощников.
- Перед созданием помощника `assistant_model_resolver` классифицирует
  задачу:
  - Определяет сложность (только для выбора pro/lite при веб-поиске).
  - Определяет необходимость web_search.
  - Подбирает подходящий сервис и модель:
    - Если явно указаны в запросе - используются они.
    - Если web_search не нужен - основная модель из настроек оркестратора.
    - Если web_search нужен - из YandexAI (pro/lite модель по сложности).
    - Иначе - первый доступный сервис с ключом.
- Новый Помощник сохраняется в БД и становится доступен для последующего
  использования.

### FR10 - Базы знаний (RAG)
- Пользователь может создавать **базы знаний** (RAG) - локальные хранилища
  документов с индексом и поиском в одном из режимов: `bm25` (собственная
  лексическая реализация, без API-ключей - режим по умолчанию), `vector`
  (семантический поиск по эмбеддингам) или `hybrid` (объединение обоих
  ранжирований через Reciprocal Rank Fusion; при недоступности эмбеддингов
  деградирует до `bm25`).
- База знаний хранится в папке данных (`DATA_DIR/rag_bases/<slug>/`):
  `manifest.json` (включая `search_mode`), файлы документов, локальный
  SQLite-индекс `index.db`.
- Страница **«Хранилище»** (`ui/pages/storage.py`) позволяет:
  - просматривать список баз знаний;
  - создавать новую базу (имя, описание, эмбеддинг-модель, режим поиска);
  - загружать файлы в базу;
  - запускать индексацию (чанкинг + BM25-структуры; эмбеддинги - только в
    режимах `vector`/`hybrid`);
  - тестировать поиск в режиме базы;
  - переключать режим поиска базы (селектор в карточке базы).
- Индексация: `core/rag_chunker` разбивает текст на чанки,
  `core/rag_indexer` пишет чанки в `core/rag_index`, поддерживает
  лексический индекс `core/rag_bm25` (ленивая первая сборка для старых
  баз, далее инкрементальные обновления) и - в режимах `vector`/`hybrid` -
  вызывает Yandex Embeddings API (BYOK) для векторов.
- Поиск: `core/rag_search` диспетчеризует по режиму базы (`bm25` -
  собственный лексический индекс, `vector` - косинусное сходство,
  `hybrid` - RRF) и строит контекст для LLM; хиты несут `mode`.
- Качество лексического поиска (схема `bm25_version = 3`,
  полезависимый BM25F, см. `core/rag_bm25`): консервативный русский
  стеммер (без внешних зависимостей) сливает словоформы
  (`бренд`/`бренда`/`брендов`), служебные слова исключаются из индекса
  и запроса. Тело чанка и его служебная шапка индексируются как ДВА
  отдельных поля со своей статистикой (df/avgdl): повтор шапки не
  обрушивает IDF доменного термина тела, а имя продукта/раздела,
  встречающееся только в шапке (`Документ`/`Продукт`/`Заголовок`/
  `Раздел`), остаётся находимым; служебный маркер `Фрагмент` (N/M) в
  индекс не входит. Оценку качества можно измерить скриптом
  `scripts/rag_eval.py` (`Recall@5`, `MRR`, `nDCG@10`) на эталонных
  наборах `tests/fixtures/rag_eval/`.
- DevAgent и оркестраторы могут обращаться к базам через инструменты
  `list_rag_bases()`, `rag_search()` и `rag_get_chunks()` (метаданные баз
  добавляются в системный промпт оркестратора блоком
  `Available RAG knowledge bases` вместе с режимом поиска).
- Результаты `rag_search` несут `chunk_id` и 0-based позицию чанка;
  `rag_get_chunks` добирает конкретные чанки (по `chunk_ids` или `source` +
  `chunk_indices`) для восстановления контекста вокруг находки - и в
  ассистентах (function-цикл), и в DevAgent.
- Статистика базы (счётчики чанков/эмбеддингов) кэшируется в meta-таблице
  локального индекса `index.db` и обновляется инкрементально при каждой
  записи: горячие пути рендера и API запрашивают базы без статистики
  (`with_stats=False`), поэтому интерфейс не сканирует большие индексы при
  каждом обновлении; полная статистика читается только при явном запросе
  (страница «Хранилище»).
- Инструкция **Rag Base Creator** (навык `rag_base_creator`) описывает
  процедуру создания и индексации баз знаний, включая выбор режима поиска
  и явный slug базы: `--slug` задаёт латинский slug (нормализация,
  обязателен для нелатинских имён), `create_base` принимает его явно.

### FR11 - Коннекторы
- Пользователь может создавать **подключения** (коннекторы) к внешним
  сервисам (например, GitHub) - раздел настроек после «Хранилища».
- Подключение хранится в папке данных (`DATA_DIR/connectors/<id>/`):
  `manifest.json`; токен шифруется через `core.crypto.encrypt` и не
  попадает в публичные представления.
- Страница **«Коннекторы»** (`ui/pages/connectors.py`) позволяет:
  - просматривать список подключений;
  - создавать подключение (тип, имя, токен, аккаунт);
  - тестировать соединение;
  - изменять и удалять подключения.
- **Привязка к оркестраторам**: в настройках оркестратора (таб
  «Подключения») выбираются доступные подключения
  (`config['enabled_connections']`); связанные инструменты и блок
  `Available service connections` добавляются в системный промпт.
- **GitHub-коннектор:** единственный коннектор GitHub - REST
  (`core/github_connector_rest.py`, прямые запросы к REST API v3 через
  `requests`, без PyGithub). Legacy PyGithub-коннектор
  (`core/github_connector.py`, `core/github_tools.py`, инструменты
  `github_*`) полностью удалён.
- REST-коннектор реализует repo CRUD, чтение/запись файлов, метаданные,
  refs/коммиты/деревья и оптимизированную пакетную публикацию через Git Data
  API: все blobs создаются заранее, затем ОДНО дерево, ОДИН коммит и ОДНО
  обновление ref для всей пачки файлов (`batch_commit`; ветка создаётся,
  если репозиторий пуст). `batch_upsert` дополнительно сверяет локальные
  blob-SHA с удалённым деревом и пропускает неизменённые файлы (при полном
  совпадении коммит не создаётся). GET-запросы коннектора автоматически
  повторяются при сетевых сбоях (`requests.Timeout` / `ConnectionError`;
  до 3 попыток, паузы 0.5/1.5 с); write-методы и HTTP-ошибки не
  повторяются.
- Инструменты REST-коннектора для оркестраторов (`core/github_tools_rest.py`,
  префикс `ghr_*`): `ghr_list_repos`, `ghr_create_repo`, `ghr_read_file`,
  `ghr_upload_file`, `ghr_update_file`, `ghr_delete_file`, `ghr_list_files`,
  `ghr_batch_commit`, `ghr_batch_commit_paths`, `ghr_batch_upsert`,
  `ghr_test_connection`, `ghr_get_repo_info`, `ghr_read_file_meta`,
  `ghr_get_ref`, `ghr_get_commit`, `ghr_get_tree`, `ghr_create_ref`,
  `ghr_create_tag`; каталог - `get_tools()`.
  Сервис подключения - `github_rest`; legacy-сервис `github` (PyGithub)
  удалён и больше не существует. Токен шифруется через `core.crypto` при
  сохранении соединения и никогда не попадает в результаты, ошибки или
  публичные представления.
- **SSH-коннектор:** сервис `ssh` - SSH/SFTP-подключения к серверам
  (`core/ssh_connector.py`, paramiko + SFTP, ленивый импорт). Конфигурация -
  `host`, `port` (1..65535), `username`; секреты - пароль или приватный ключ
  (+ опциональная парольная фраза), шифруются через `core.crypto` и не
  попадают в публичные представления.
- Инструменты SSH-коннектора для оркестраторов (`core/ssh_tools.py`, префикс
  `ssh_*`): `ssh_exec`, `ssh_list_dir`, `ssh_read_file`,
  `ssh_test_connection`, `ssh_upload_file`, `ssh_write_file`; каталог -
  `get_tools()`.
  Таймаут команды 60 с по умолчанию (максимум 300 с); stdout/stderr
  обрезаются до 100 КиБ, чтение файла - до 256 КиБ, запись - до 1 МиБ;
  `ssh_upload_file` потоково публикует локальный файл (до 50 МиБ) на сервер
  и по умолчанию проверяет перенос по sha256; `create_dirs=True` создаёт
  отсутствующие каталоги при записи.
- Страница «Коннекторы» для сервиса `ssh` показывает поля host/port/username
  и секреты (пароль или приватный ключ + парольная фраза); тест соединения
  выполняет реальное подключение.
- Инструкция `ssh_connector` (глобальная и встроенная у DevAgent) описывает
  работу с SSH-подключениями.
- **Черновики подключений (draft/pending).** DevAgent создаёт подключение
  по запросу в чате через `create_connection(..., pending=True)` БЕЗ
  каких-либо секретов: `credentials_status=pending`, секрет отсутствует
  даже в зашифрованном виде. Учётные данные пользователь заполняет на
  странице «Коннекторы» (поля-пароли); подключение переходит в `active`.
  В блоке `Available service connections` промпта pending-подключения
  помечаются предупреждением о невведённых учётных данных.
- **Общие инструменты коннекторов** в диспетчере
  (`dev_agent/universal_agent.py`, 11 штук): `list_connections`,
  `get_connection`, `list_connector_services`, `create_connection`,
  `update_connection`, `delete_connection`, `test_connection`,
  `get_enabled_connections`, `set_enabled_connections`,
  `get_connection_memory`, `set_connection_memory`. Публичные манифесты
  секретов не содержат.
- **Файл памяти подключения:** у каждого соединения - агентские заметки
  `DATA_DIR/connectors/<id>/memory.md` (лимит 64 КиБ), читаются
  `get_connection_memory`, обновляются `set_connection_memory`; хранят
  факты о сервере/лимитах/путях, НИКОГДА - секреты. Промпт-блок
  Quick usage notes напоминает читать память до работы и предлагать
  обновление после.
- **Инструкция `connector_creator`** (встроенная DevAgent) ведёт весь флоу
  создания: черновик без секретов → заполнение на странице → проверка →
  включение для оркестраторов → посев памяти. Инструкции `ssh_connector` /
  `github_connector` дополнены правилами первого входа на неизвестный
  сервер и обязательным файлом памяти.

- **MCP-коннектор:** сервис `mcp` подключает MCP-серверы в двух
  транспортах: `stdio` (локальный процесс) и `http` (внешний сервер,
  например ВкусВилл). Подключение хранится в
  `DATA_DIR/connectors/<id>/`; секрет `env_json` шифруется через
  `core.crypto` и не попадает в публичные представления. Конфигурация
  stdio - `command` (белый список: `python`, `python3`, `node`, `npx`,
  `uvx`, `uv`) и `args` (массив строк); конфигурация http - `url`
  (только https; на локальной машине допускается http://localhost) и
  шаблон `auth_header` с плейсхолдерами `{ИМЯ_ПЕРЕМЕННОЙ}`: перед
  каждым запросом плейсхолдеры подставляются из расшифрованных
  секретов подключения; если все секреты шаблона пусты, заголовок не
  отправляется.
- **Клиент `core/mcp_client.py`** (только stdlib, без официального SDK):
  JSON-RPC 2.0. `McpClient` (stdio): `shell=True` запрещён; handshake
  `initialize` -> `notifications/initialized`; `tools/list` с кэшем на
  время жизни процесса; `tools/call` принимает только текстовые
  `content`, нетекстовые результаты отклоняются с понятной ошибкой;
  таймауты 30 с (`tools/list`) и 60 с (`tools/call`) с завершением
  процесса и блокировкой коннектора до пересоздания; реестр процессов
  на коннектор (пересоздание убивает старый процесс); падение сервера
  не затрагивает платформу; `stderr` пишется в лог и не парсится.
  `McpHttpClient` (http, только urllib): запросы POST на `url`, ответ
  принимается обычным JSON или SSE-потоком; `Mcp-Session-Id` из ответа
  сервера воспроизводится в следующих запросах; заголовок авторизации
  собирается из шаблона и расшифрованных секретов на каждый запрос;
  после обновления секретов закэшированный клиент сбрасывается, и
  новый токен доходит до следующего вызова. `inputSchema` (JSON Schema
  2020-12) транслируется в параметры инструментов платформы.
- **Инструменты для оркестраторов (`core/mcp_tools.py`):** статические
  `mcp_list_tools` / `mcp_call_tool` и динамические
  `mcp__<коннектор>__<инструмент>` (обратный реестр, кэш discovery
  60 с); `env_json` расшифровывается только для процесса сервера и не
  попадает в логи и каталог. Ветка `mcp` в `_connection_catalog`
  (`core/orchestrator_tools.py`); при ошибке старта или `tools/list`
  инструменты коннектора в каталог не попадают, в каталог выводится
  предупреждение.
- **Безопасность:** `disabled_tools` и `core/dangerous.py` действуют для
  MCP-инструментов; имена и описания от сервера - недоверенные данные
  (санируются, не подставляются в код); секреты сервера в диалогах не
  раскрываются.
- **Пресеты MCP-серверов:** шаблоны без секретов в
  `defaults/connectors/mcp/` (видимые в каталоге: `vkusvill` - http,
  `yandex_mail` - http, авторизация схемой `OAuth`)
  загружаются модулем
  `core/connector_presets.py`. У пресета проверяется обязательное
  поле `icon` (эмодзи-иконка для плитки вкладки MCP). Необязательный
  флаг `hidden: true` убирает пресет из каталога (`list_presets`), но
  оставляет его доступным по id (`resolve_preset`): подключение,
  созданное из такого пресета, продолжает редактироваться формой
  пресета, а плитка возвращается снятием флага. Скрыт пресет
  `github_mcp` - удалённый Copilot-эндпоинт принимает только
  fine-grained PAT с разрешением `Copilot Requests`, поэтому работа с
  GitHub идёт через подключение `github_rest` (инструменты `ghr_*`),
  а сторонний MCP-сервер добавляется плиткой «Свой MCP-сервер».
  Инструмент
  DevAgent
  `list_connection_presets` перечисляет доступные пресеты, а
  `create_connection(..., preset=<id>)` разворачивает пресет в черновик
  `pending` без секретов и засевает файл памяти из `memory_seed`.
  Пользователь заполняет только учётные данные на странице
  «Коннекторы»: для пресетов с `secret_env_fields` страница показывает
  понятные поля (label/help/password), значения упаковываются в
  зашифрованный `env_pairs`.
- **UI:** страница «Коннекторы» работает по модели `список ↔ форма`,
  как страница помощников: режим страницы хранится в `session_state`
  (`connectors_view` = `list` | `create` | `edit`), и форма ЗАМЕНЯЕТ
  список на той же странице. Список - три вкладки: `General services`,
  `MCP servers` и `Connections`; `st.tabs` создаётся stateful
  (`on_change="rerun"` + `default=<метка>`), потому что без
  `on_change="rerun"` виджет не хранит состояние вообще и после rerun
  всегда открывает первую вкладку. `General services` - плитки
  сервисов с иконкой и описанием (github_rest, ssh): клик по плитке
  только ОТКРЫВАЕТ форму создания сервиса, в БД ничего не пишется.
  `MCP servers` - плитки пресетов рядами по три (иконка, имя,
  описание; клик открывает ту же форму с предзаполненным именем и
  полями `secret_env_fields`) и плитка «+ Свой MCP-сервер» (stdio
  command/args/env_json либо http url/auth_header/env_json).
  `Connections` - карточки ВСЕХ сохранённых подключений
  (github/ssh/mcp) с иконкой сервиса, индикатором учётных данных,
  предупреждением о незаполненных кредах, тестом, редактированием и
  удалением.
- **Создание и редактирование:** полноэкранная форма (`create`/`edit`)
  содержит имя, аккаунт и поля выбранного сервиса/пресета, кнопки
  «Создать»/«Сохранить» и «Отмена», плюс `← Назад`. Запись в БД
  происходит ТОЛЬКО по «Создать»/«Сохранить»: подключение сразу
  активное (секреты, введённые в форме, сохраняются зашифрованными),
  а не черновик без учётных данных. «Отмена»/«Назад» возвращают к
  списку, ничего не создавая; после сохранения список открывается на
  вкладке `Connections`. Ошибка сохранения оставляет форму открытой,
  чтобы введённые значения не потерялись. Черновики `pending`, которые
  DevAgent создаёт из чата, остаются в списке и заполняются через ту же
  форму (кнопка «Заполнить учётные данные»).
- **Инструкция `mcp_connector`** (встроенная DevAgent) описывает флоу:
  пресеты и черновики (создаются из чата), заполнение учётных данных
  пользователем на странице, включение коннектора, вызов
  инструментов, поведение при ошибках и таймаутах, HTTP-транспорт и
  отключение.

### FR12 - Библиотека навыков (Skills)
- Навыки лежат в `DATA_DIR/skills/<folder>/`, реестр - `skills/skills.json`;
  каждая запись хранит `developer` (правообладатель) и `adapted` (статус
  адаптации под SagaAI).
- Платформенные навыки из `defaults/skills/` импортируются с
  `developer=SagaAI`, `adapted=True`; сторонние - `developer=unknown`,
  `adapted=False`, пока DevAgent не завершит адаптацию.
- Встроенный навык сеется в папку со своим именем (`rag_base_creator`),
  а не в папку от отображаемого названия: каталог адресует тот же навык по
  этому имени, поэтому установка из каталога и встроенная копия занимают
  одну папку. Запись с маркером `source: marketplace/<id>` или папка,
  которую она занимает, останавливают сидинг - иначе рядом появилась бы
  вторая копия с суффиксом и одна установка показывалась бы дважды.
- Неадаптированные навыки не попадают в блок `Available skills` системного
  промпта оркестратора: `get_enabled_skills_metadata()` возвращает только
  адаптированные записи. Инструмент `list_skills_library` при этом видит
  все навыки.
- Инструмент DevAgent `mark_skill_adapted(skill_id)` помечает навык как
  адаптированный (`core.skills_library.set_skill_adapted`).
- На странице библиотеки навыков для неадаптированных навыков есть кнопка
  «Адаптировать»: она формирует задачу адаптации и передаёт её в DevAgent
  (Skill Developer), который по завершении вызывает `mark_skill_adapted`.
- Файлы навыка лежат в его собственной папке вне workspace: читать их нужно
  инструментом `get_skill_file(skill_id, filename)` (`get_skill_folder` даёт
  путь и список файлов). Workspace-инструменты (`read_file`, `verify_file`)
  такие пути отклоняют («Path escapes project root») - блок `Available skills`
  системного промпта оркестратора предупреждает об этом явно.

### FR13 - Обновления платформы
- Обновления поставляются через публичный GitHub-репозиторий

- Манифест описывает units (атомарные пакеты; исполняемый код - один пакет

### FR14 - Доступ к приложению (страница «Доступы»)
- Страница **«Доступы»** (`ui/pages/access.py`, пункт меню «🔐 Доступы»
  перед «Обновления») управляет доступом по паролю.
- Блок «Доступ по паролю»: переключатель (по умолчанию выключен), поля
  пароля и подтверждения, интервал повторного запроса (по умолчанию 12
  часов, от 1 до 8760).
- Валидация: пароль и подтверждение должны совпадать; при включённом
  доступе пароль обязателен (если не задан ранее). При невалидном вводе
  настройки не сохраняются.
- Настройки хранятся в ConfigKV (`auth_enabled`, `auth_password`,
  `auth_reask_hours`); пароль шифруется Fernet (`core.crypto`) при
  сохранении.
- Приоритет пароля: значение формы (`auth_password`) канонично;
  `SAGAAI_AUTH_PASSWORD` используется только как запасной источник, если
  пароль формы пуст (`core.auth.resolve_auth_password`).
- После успешного входа пароль не запрашивается в течение интервала
  (`auth_reask_hours`); по истечении интервала - повторный запрос.
- Пока любой оркестратор выполняет задачу (агентный цикл активен),
  авторизация не запрашивается даже при истёкшем интервале
  (`core.auth.any_orchestrator_active`).
- Форма входа: `core.auth.require_auth()` вызывается в начале `main()`
  (`ui/app.py`) до рендера страниц; при выключенном доступе или
  аутентифицированной сессии - no-op.
- Это защита от случайного несанкционированного доступа, а не
  многопользовательская система (см. раздел «Ограничения»).

### FR15 - Защита от переполнения контекста LLM
- **M1 - политика размера результатов инструментов (спилл до отправки).**
  Результат, чей документ `{"tool_result": ...}` больше 35 000 символов,
  до первой отправки записывается целиком в
  `<workspace>/.dev_agent/tool_results/` (ротация до 100 последних
  файлов), а в контекст модели уходит ограниченное превью head+tail со
  `spill_path`: полный payload восстанавливается через `read_file`
  (offset/limit). Если запись спилла невозможна, результат длиннее
  200 000 символов не отдаётся в контекст: возвращается
  структурированная ошибка с фактическим размером и советом сузить
  аргументы (`result_too_large`, `result_size`). Политика применяется в
  `dev_agent/tool_executor.py` (диспетчер инструментов) и в
  `dev_agent/universal_agent.py` (custom-функции и инструменты
  подключений).
- **M2 - персист скрытых tool_result с сохранением проводной формы.**
  Результаты до 50 000 символов сохраняются в БД тредов дословно: при
  reload треда сообщение побайтово совпадает с отправленным проводом
  (resume-идентичность). Более крупные документы (аварийный путь, когда
  спилл недоступен) сохраняются краткой сводкой (статус, путь,
  применённость, размеры объёмных полей), а не сырым JSON; это
  защищает историю как от раздувания базы, так и от повторной загрузки
  сверхбольших payload'ов при reload тредов.
- **M3/B4 - единый бюджет истории (порог + гистерезис).** Бюджет берётся
  из общей формулы `history_cap(window, max_tokens, prompt_tokens)` =
  `0.75 × (окно - лимит вывода) - промпт` (потолок входа `input_ceiling`
  = окно минус объявленный лимит вывода) минус `_ECONOMY_GUARD_MARGIN`
  (2048) под пользовательское сообщение. Та же формула задаёт и порог
  pre-flight guard'а, поэтому guard не сдвигает экономический payload.
  Под бюджетом фронт истории не двигается; при превышении ведущие
  сообщения срезаются одним проходом: в кэш-режиме фронт сбрасывается до
  `tail` сообщений - тот же сброс, что даёт переполнение окна
  `tail × multiplier`; если и `tail` не укладывается в бюджет, срез
  продолжается до нижней ватерлинии (0.75×бюджета). Срез сворачивается в
  `state.economy_anchor`, поэтому фронт отправляемого окна остаётся на
  месте до нового перерастания. Служебная head-meta сохраняется всегда.
- **M4/M5 - pre-flight guard в api_layer.** Контекст запроса оценивается
  до отправки к провайдеру: резерв под вывод -
  `min(max_out, max(4096, 0.25×окна))`; при превышении 0.75 окна старые
  сообщения обрезаются, служебный head-блок эконом-меты не срезается; при
  превышении жёсткого порога (0.9 окна) и невозможности уложиться
  возвращается понятная ошибка `context_window_exceeded` без запроса к
  провайдеру; новый диалог не предлагается. Объявленные в каталогах
  сервисов лимиты вывода делают резерв реалистичным.

### FR16 - Совместимость GigaChat (payload, лимиты, видимость ошибок)
- GigaChat принимает ровно один system-промпт и только первым сообщением:
  `_gigachat_messages` (`core/api_layer.py`) фолдит в ведущее
  system-сообщение только ВЕДУЩИЕ system-блоки (системный промпт,
  эконом-мета) - в исходном порядке, а system-блок середины истории
  (task state, thread context) сохраняет позицию и отдаётся с ролью
  `user` (служебный контекст, не речь ассистента); префикс запроса при
  этом остаётся байтово стабильным от шага к шагу.
- Подряд идущие сообщения одинаковых ролей в GigaChat-payload
  схлопываются (склейка через пустую строку).
- `max_tokens` клампится по лимиту модели, при его отсутствии - по
  сервисному дефолту (`_clamp_max_tokens` в `core/api_layer.py`, до
  pre-flight guard); сервисы без объявленного лимита не затрагиваются.
- Ошибки LLM на первом шаге агентного цикла видны в ленте чата
  оркестратора: события шага (включая `error`) крепятся к сообщению
  пользователя текущего хода, если ответа ассистента ещё нет
  (`_attach_events` в `ui/pages/orchestrator.py`); ошибка не теряется при
  очистке loop_state.

### FR17 - Проверка зависимостей на холодном старте
- При первом старте приложения (`ui/app.py`, helper
  `_run_dependency_check_once`, один раз за сессию) выполняется аудит
  установленных библиотек через `core/dependency_check.py`.
- Реестр `DEPENDENCIES` задаёт для каждого пакета минимальную версию и
  флаг `required`; состав и минимумы синхронизированы с `requirements.txt`
  (проверяется тестом `tests/test_dependency_check.py`).
- Пользователю показываются отдельные предупреждения: `deps_missing` -
  отсутствующие библиотеки (с рекомендацией `pip install -r
  requirements.lock`); `deps_outdated` - устаревшие версии вида
  `pkg installed -> required` (с рекомендацией обновить).
- Проверка устойчива к сбоям: отсутствие metadata у пакета трактуется
  мягко, любая ошибка аудита не блокирует старт приложения.

### FR18 - Мультиагентная оркестрация (делегирование запусков)
- Сотрудник запускает другого сотрудника инструментом `spawn_agent` и
  обращается к помощнику одним вызовом `invoke_assistant`. Оба инструмента
  описаны контрактом `core/orchestration/contracts.py`, исполняются через
  `OrchestrationService` (`core/orchestration/service.py`) и не зависят от UI.
- `spawn_agent` доступен всегда: делегирование самому себе не требует
  настройки. `invoke_assistant` появляется в каталоге инструментов только
  когда у сотрудника непустой список разрешённых помощников. Каталог и
  диспетчер читают один источник прав, поэтому отклонённый вызов не
  показывается модели как доступный.
- Вызов помощника (`invoke_once`, `core/orchestration/invoke.py`) -
  ровно один запрос к модели без цикла инструментов, без RAG и без доступа
  к файлам; контекст передаёт вызывающий (`context_files` -> блоки
  `### File: <name>`). Документ читается через `core.document_text`, поэтому
  один файл - один вызов: текст не дробится на части, а нечитаемый файл
  попадает в `skipped_files` и не срывает вызов.
- Разрешённые сотрудники (`allowed_agents`) и помощники
  (`allowed_assistants`) хранятся в конфигурации оркестратора. Собственный
  slug в списке не хранится; список помощников сверяется с живыми
  карточками при записи, поэтому удалённый помощник не остаётся в правах.
- Встроенный исполнитель `universal_agent` доступен каждому оркестратору по
  умолчанию: право живёт не в `allowed_agents`, а в отдельном флаге
  `config.universal_agent_enabled` (отсутствие ключа = включено, поэтому
  новые сотрудники получают право без миграции). Эффективный список агентов
  строит `get_effective_agents()`: `allowed_agents` плюс исполнитель при
  включённом флаге, без дублей, без самого себя и без удалённого сотрудника.
  Читают этот список и рантайм-проверка прав, и блок `## Available agents`
  промпта, поэтому отозванное право исчезает из промпта вместе с отказом в
  вызове. На вкладке «Делегирование» флаг - отдельный чек-бокс над общим
  списком; снятие галочки не переписывает `allowed_agents`.
- Шесть лимитов (`get_delegation_limits` / `set_delegation_limits`):
  `max_depth` (0 запрещает делегирование, по умолчанию 1),
  `max_active_subagents` (одновременные дети и вызовы, семафор дерева;
  по умолчанию 5), `subagent_max_steps` (шагов на ребёнка; по умолчанию
  300), `total_subagent_runs` (суммарно на дерево; по умолчанию 64),
  `subagent_timeout_seconds` (сколько ребёнку разрешено работать; по
  умолчанию и не более часа), `subagent_budget_tokens` (0 - без потолка).
  Потолок шагов заведомо выше реальной работы: длинный запуск должен
  обрывать бюджет времени, а не счётчик шагов, иначе здоровый запуск
  останавливается с подсказкой «дробить задачу», хотя дробить нечего.
  Сеттер кламп-ит значения к диапазону, чтобы нулевой пул не защёлкнул
  первый запуск.
- Дерево запусков принадлежит диалогу: корневой запуск регистрируется при
  старте, `run_id` уникален, а тред ребёнка - производный
  `{parent}__s{run_id[:8]}`. Ребёнок работает в рабочей папке родителя, но
  получает собственный журнал задач; после завершения связывание и
  семафоры освобождаются (`release_tree`).
- Остановка диалога каскадна: `cancel(cascade=True)` переводит детей в
  `cancelled` с причиной `aborted` и кодом `cancelled_by_parent`.
- Сервис оркестрации разделён по ответственности, точка входа одна.
  `service.py` держит `OrchestrationService` и реэкспортирует помощников,
  поэтому `core.orchestration.service` остаётся единственным именем для
  вызывающего кода и для подмены в тестах. Дочерняя сторона запуска - сборка
  диспетчера ребёнка с суженным каталогом инструментов, приёмник транскрипта,
  область журнала, восстановление резюма, прокрутка цикла и итоговый
  `AgentRunResult` - живёт в `child_runner.py`; строки бутстрапа (производный
  тред, папка файлов, текст задачи) - в `child_text.py` без состояния
  сервиса. Сужение каталога задаётся атрибутом диспетчера, а не сигнатурой,
  поэтому набор запрещённых инструментов остаётся одним местом правды.
- Fan-out: независимые вызовы `spawn_agent` проверяются на права и
  аргументы всем набором до захвата пула, затем выполняются параллельно;
  события несут `run_id` ребёнка, и лента группирует их по запускам.
- Задание субагенту (`_build_child_task_text()`) содержит блок «Контекст
  запуска» с АБСОЛЮТНЫМИ путями: рабочая папка родителя и папка файлов
  диалога родителя (`history/<thread_id>/files`). Свой диалог субагента
  вложений родителя не содержит, поэтому относительный путь для него -
  тупик; описание `spawn_agent` требует абсолютные пути в самом контракте.
- В системный промпт сотрудника добавляются блоки `## Available agents
  (spawn_agent)` (сам сотрудник и `allowed_agents` с именами) и
  `## Available assistants (invoke_assistant)` (`allowed_assistants` с id и
  именами); раздел помощников появляется только при непустом списке, так что
  промпт не обещает вызов, который будет отклонён. Блок агентов перечисляет
  эффективный список, поэтому доступный по умолчанию исполнитель попадает в
  него с пометкой о такой доступности.
- Режим prompt-injection защиты наследуется: ребёнок работает с тем же
  `enable_injection_protection`, что и запустивший его диалог. Значение
  разрешается ОДИН раз при спавне и замораживается в записи запуска
  (`RunRecord.enable_injection_protection`, попадает и в durable-запись),
  поэтому фоновый ребёнок не читает настройку чужого диалога. Resume берёт
  значение из исходного запуска (это та же единица работы), явный аргумент
  вызывающего его перекрывает, а свежий спавн без аргумента остаётся под
  защитой. Одноразовый bypass после одобрения одного payload не наследуется:
  это разрешение посмотреть один фрагмент, а не режим. Модель не управляет
  этим - имя отсутствует в каталоге аргументов `spawn_agent`.
- В v1 дочерний запуск не создаёт и не изменяет сущности платформы
  (сотрудники, помощники, навыки, подключения) - эти инструменты выключены
  в каталоге ребёнка.
- Настройка прав и лимитов - вкладка «Делегирование» в настройках
  сотрудника: чек-боксы сотрудников и помощников (устаревшие id показываются
  с предупреждением, а не исчезают молча) и шесть числовых полей с
  подсказками.
- Фоновый запуск: `spawn_agent(background=true)` возвращает `run_id`
  сразу, ребёнок работает в отдельном потоке, а диалог продолжает работу и
  узнаёт о завершении из ящика извещений. Блокирующий режим (по умолчанию)
  остаётся для случаев, когда результат нужен немедленно.
- Состояние ребёнка наблюдается пятью инструментами: `subagent_status`
  (один запуск, всё дерево `root_run_id` или ожидание терминального статуса
  до 30 с через `wait_seconds`; истёкшее ожидание - не ошибка, запись
  возвращается с `timed_out=true`), `read_subagent_state` (журнал ребёнка по
  абсолютному пути из записи запуска, разделы как у своего журнала),
  `read_subagent_thread` (сама переписка ребёнка: `child_thread_id` из
  записи запуска адресует ФАЙЛОВОЕ хранилище транскриптов, поэтому видно,
  что ребёнок сказал и какие вызовы сделал, а не только что он записал в
  журнал; ребёнок, ещё не сделавший ни шага, отвечает пустым окном с
  пояснением, а ребёнок без строки индекса - `resume_unavailable` и
  указанием читать журнал), `sleep` (блокирующее ожидание события в дереве
  или таймаута; длительность выбирает вызывающий, потолок - час, таймаут
  ничего не отменяет) и `resume_subagent` (продолжение с того места, где
  ребёнок остановился).
- **Статус - не результат.** Забрать произведённое завершённым запуском -
  отдельный инструмент `subagent_result(run_id, wait_seconds=0)`: он
  возвращает итоговый текст, артефакты и израсходованные ресурсы в той же
  форме, в которой их отдаёт блокирующий `spawn_agent` (`AgentRunResult`),
  независимо от того, как запуск стартовал. Незавершённый запуск результата
  не отдаёт: ответ - `ready=false` с текущим состоянием и без ключа
  `result`, потому что частичная работа, выданная за результат, выглядит как
  успех и потому опаснее явной ошибки. `wait_seconds` (потолок - те же 30 с)
  позволяет забрать результат в том же шаге, если ребёнок уже заканчивает.
  Адресация - только своё дерево (`not_your_run`), а завершённая запись
  хранит полный результат, поэтому он остаётся доступным и после выгрузки
  дерева из реестра.
- **Родитель управляет своими детьми.** `cancel_subagent` останавливает
  запуск, который пошёл не туда, вместо ожидания его бюджета: запрос - это
  флаг в записи запуска, который цикл ребёнка проверяет на границах шагов
  (вызов инструмента, уже начатый, успевает завершиться), запуск и его
  потомки (`cascade=true`) завершаются как `cancelled` с причиной в
  `cancel_reason`. Адресация ограничена своим деревом: чужой запуск
  отвечает `not_your_run`, а отмена уже завершённого - не ошибка, а отчёт
  «нечего отменять», чтобы модель не уходила в цикл повторов. Оба
  инструмента - и `cancel_subagent`, и `read_subagent_thread` - работают
  только с запусками своей корневой ветки.
- **Завершение ребёнка - это `loop_status="done"`, а не вопрос.** У
  ребёнка нет человека, который ответит, поэтому его финальный статус
  `done` означает завершение работы: сервис ставит `completed`, а не
  `awaiting_input`. Запуск без сводки и без артефактов помечается
  `child_unfinished` в результате - это не результат, а незавершённая
  работа.
- Записи запусков долговечны (`core/orchestration/runs.py`): `start`,
  `heartbeat` и `finish` пишутся атомарно в
  `.dev_agent/orchestration/runs/<root_run_id>/`, переживают перезапуск
  процесса и чинятся при чтении (`heal`). Мёртвый `running` распознаётся по
  трём независимым признакам - устаревший heartbeat (окно равно одному
  бюджету запуска плюс запас), чужой `boot_id`, отсутствующий `pid` - и
  переводится в `failed/stale_run` с причиной, поэтому брошенный ребёнок не
  висит в статусе «работает» вечно.
- Читатель статуса судит о живости отдельно и строже, чем ремонт файла
  (`is_live`, `demote_if_dead`, окно `max(60, 3 x heartbeat)`): запись
  `running`, у которой нет живого двойника в реестре процесса, - остаток
  умершего потока, и в выдаче она помечается `failed/stale_run` с
  `live=false`. Живой двойник сильнее любой метки времени, поэтому таймер
  heartbeat заводится только фоновому запуску: блокирующий ребёнок держит
  запись в памяти до возврата. На старте процесса `sweep_dead_runs()`
  проходит по всему хранилищу без потолка и чинит записи прошлых процессов.
- Корневой запуск диалога - это ОДИН шаг, и воркера у него нет:
  `release_tree()` закрывает его сам (`close_root_run`), иначе запись на
  диске оставалась `running` и строка «работают субагенты» переживала
  завершение шага. Идентификатор диалога переживает шаги, поэтому
  `ensure_run()` переоткрывает терминальную корневую запись на новом шаге.
- Список запусков дерева (`subagent_status(root_run_id=...)`) считает
  незавершёнными только детей: корень диалога `running` по определению и
  готовность дерева не отменяет.
- Завершение публикуется ровно один раз: право на извещение захватывается
  атомарно (`claim_notice`, `O_CREAT|O_EXCL`), так что ни воркер, ни UI не
  показывают его дважды. Извещение доставляется скрытым
  system-сообщением `[SUBAGENT_NOTICE:<run_id>:<status>]` в фазе
  `calling_llm` следующего шага, а не видимой репликой пользователя,
  поэтому оно не переводит шаг в `awaiting_user`.
- Транскрипт ребёнка хранится в файле, а не в `devagent.db`
  (`dev_agent/transcript.py`): один JSONL-сегмент на шаг под
  `<history>/<parent>/subagents/<child>/`, дописывание одной строкой под
  локом на ПУТЬ. Инварианты, которые нельзя нарушать при правках: (1) запись
  не берёт блокировку базы и не мешает другим тредам; (2) префикс
  `__DEVAGENT_EVENTS__` срезается перед записью - это данные рендера; (3)
  сегмент определяется НОМЕРОМ, поэтому `.jsonl` и `.jsonl.gz` - один и тот
  же сегмент до и после уборки; (4) сжатие сохраняет время последней
  реальной записи; (5) активный сегмент неприкосновенен для квоты; (6)
  отсутствие строки в индексе делает папку кандидатом в сироты, но
  удаляется она только при явном `purge_orphans` - по умолчанию она
  попадает в отчёт.
- Продолжение (`core/orchestration/resume.py`, `build_resume`) строится по
  журналу ребёнка, а не по его переписке: журнал читается по абсолютному
  пути из записи (обычное чтение взяло бы журнал РОДИТЕЛЯ), выполненные шаги
  (`[x]`) попадают в «Already done, do NOT redo», незавершённые - в «Still
  pending», а вся подсказка ограничена 1200 символами
  (`MAX_HINT_CHARS`). Запуск без цели и без незавершённых шагов
  отклоняется с `resume_unavailable` вместо слепого продолжения; цепочка
  продолжений ограничена (`MAX_RESUME_CHAIN = 2`), дальше -
  `resume_chain_limit`.
- Продолжение наследует дерево, глубину и счётчики запусков
  (`resumed_from`, `resume_depth`): это та же работа, поэтому бюджет дерева
  не сбрасывается, а расходуется дальше.
- Автономия ребёнка: у субагента нет ЧЕЛОВЕКА, который нажмёт «Разрешить».
  Поэтому в цикле ребёнка (`state.child_mode`) вызов, требующий
  подтверждения, не останавливает работу: он возвращает отказ
  `confirmation_required` с требованием переписать операцию без
  подтверждения либо сообщить о блокере в результате. Инструменты,
  создающие сущности платформы, выключены в каталоге ребёнка. Вопрос
  человека ребёнку недоступен, но вопрос СВОЕМУ агенту - доступен
  (`ask_parent`, см. ниже).
- **Диалог с субагентом.** Ребёнок, которому не хватает вводной, задаёт
  вопрос своему агенту инструментом `ask_parent(question, options, done,
  blocked)`. Вызов ПАРКУЕТ текущий прогон: запись получает статус
  `awaiting_input` с причиной `question`, вопрос и срок ожидания
  сохраняются в durable-записи, а цикл ребёнка останавливается на границе
  шага - тот же `run_id`, тот же журнал, те же записанные файлы. Новый
  прогон НЕ создаётся.
- Ответ даёт только родитель, инструментом `answer_child(run_id, answer)`:
  он распаковывает прогон, доставляет ответ как сообщение пользователя
  (`[PARENT ANSWER] ...`) и продолжает работу с того же шага. Если ребёнок
  спросил снова, вызов возвращает следующий вопрос (`parked=true`) с
  подсказкой ответить ещё раз или потребовать закончить с тем, что есть.
  Разговор восстанавливается из состояния в памяти (тот же процесс) либо из
  транскрипта ребёнка (после перезапуска), поэтому ответ не начинает работу
  заново.
- **Вопрос - это данные.** Текст вопроса приходит родителю в границах
  `[DATA_BEGIN: subagent_question] ... [DATA_END]` - и в блокирующем
  результате, и в фоновом извещении (`format_subagent_notice`), потому что
  ребёнок читает файлы и веб-страницы и может процитировать чужие команды.
  Сама запись хранит текст без обёртки: границы - это транспорт, а не
  содержимое. Системного канала у вопроса нет.
- **Доставка родителю.** Блокирующий запуск возвращает вопрос прямо в
  результате (тот же шаг, ответ можно дать сразу). Фоновый ребёнок кладёт
  извещение в ящик дерева, и цикл родителя получает его скрытым
  system-сообщением `[SUBAGENT_NOTICE:...]` на следующем шаге - опрос не
  нужен. Право на извещение захватывается атомарно, а ключ захвата несёт
  номер раунда: два вопроса одного прогона - два отдельных извещения.
- **Бюджет диалога - пять раундов на прогон** (`dialog_rounds`, значение
  владельца; по умолчанию столько же). Раунд тратится ВОПРОСОМ, а не
  ответом, поэтому вопрос без ответа тоже расходует бюджет. Исчерпанный
  бюджет - отказ `question_limit` с числом использованных раундов; новая
  задача при этом не создаётся и уже сделанное остаётся на месте. Рядом
  действуют `question_max_chars` (1500), `answer_max_chars` (4000 - ответ
  это решение, а не новое задание), `answer_wait_seconds` (900) и
  `max_parked_runs` (8 одновременных ожиданий в дереве). Некорректное или
  отсутствующее значение даёт документированный дефолт, а не отключение
  ограничения: ноль раундов запретил бы первый же вопрос, поэтому
  кламп - не меньше 1, а срок ожидания не больше часа.
- **Лимиты диалога замораживаются на спавне** (`RunRecord.dialog_limits`)
  и попадают в durable-запись: ответ может прийти из другого процесса,
  где живёт чужой конфиг, и судить прогон нужно по бюджету, с которым он
  начался. Конкурентность, глубина и таймаут остаются живыми.
- **Ожидание истекает, а не висит.** По истечении `answer_wait_seconds`
  прогон завершается как `failed/answer_not_received` с текстом вопроса в
  сводке; частичный результат и записанные файлы сохраняются. Поздний
  ответ отвергается с тем же кодом и НЕ оживляет прогон - иначе об одном
  прогоне существовали бы две правды. Уборка (`expire_parked`,
  `runs.expire_unanswered`) выполняется на путях чтения, поэтому брошенный
  вопрос не занимает ни слот ожиданий, ни место в интерфейсе. Отмена
  (`cancel_subagent`, каскад) переводит ожидающий прогон в `cancelled` -
  ожидание не переживает задачу.
- **Ожидание переживает перезапуск.** Запись ожидающего прогона и его
  вопрос лежат на диске, поэтому после перезагрузки страницы ожидание
  видно, вопрос читается, а ответ принимается: `roots_for_thread(thread_id)`
  восстанавливает корень дерева по идентификатору диалога (сессия его
  забывает), а первый же ответ поднимает запись в реестр
  (`revive_parked_run`) - иначе вопрос был бы "не в этом процессе" и
  неотвечаемым. Дерево при этом пересоздаётся: ожидающий прогон не держит
  ни потока, ни слота пула.
- **Диалог - не продолжение.** `resume_subagent` нужен, когда прогон
  ОСТАНОВИЛСЯ (кончились шаги, ошибка, `awaiting_input` без вопроса): он
  начинает новый прогон с новым бюджетом и собирает подсказку из журнала.
  `answer_child` продолжает ТОТ ЖЕ прогон по вопросу, который ребёнок
  задал сам, и не тратит ни нового `run_id`, ни бюджета дерева. Поэтому
  извещение о parked-прогоне ведёт к `answer_child`, а не к
  `resume_subagent`.
- **Что видит пользователь.** Строка «ждут ответа: N» с агентом, коротким
  `run_id` и текстом вопроса (не более трёх строк, дальше - сводка),
  обновляемая тем же таймером, что и строка работающих субагентов; вопрос
  в ленте шага - раскрытый блок с пометкой «вопрос субагента», вариантами,
  «что сделано» и «на чём застрял». Опрос не засыпает, пока есть
  ожидающие. Отвечает всегда агент: прямого канала «человек -> субагент»
  нет, поэтому решение пользователя сначала попадает к агенту.
- **Сбой ребёнка классифицируется по источнику.** Исключение внутри цикла
  ребёнка (ошибка самого платформенного кода, например присваивание
  неверного типа в состояние) даёт `error_code=internal_error`,
  `retryable=false` и текст исключения в `summary`; сбой провайдера
  сохраняет `provider_error` и остаётся `retryable`. Различие важно
  вызывающему: повторный запуск при `internal_error` упадёт точно так же,
  поэтому такой запуск не перезапускают, а чинят причину. Признак
  `retryable` едет в записи запуска и в durable-записи, поэтому вердикт
  виден и после перезапуска процесса.
- **Личность и рабочая папка ребёнка фиксируются в записи запуска.**
  `RunRecord.child_thread_id` (производный тред ребёнка) и
  `RunRecord.workspace` заполняются до старта работы, а не остаются пустыми
  на всю жизнь запуска: без них нельзя ни адресовать журнал ребёнка, ни
  сказать, куда он писал. Если раннер (в том числе тестовый) не вернул
  тред в результате, сервис подставляет его сам, поэтому результат и
  запись не расходятся.
- **Тред ребёнка получает строку индекса при связывании.**
  `bind_child_thread` создаёт строку в таблице `threads` (`kind="subagent"`,
  `parent_thread_id`, рабочая папка, относительный `transcript_path`) - до
  первого шага ребёнка, идемпотентно и без права уронить запуск сбоем
  хранилища. Переписка читается только через эту строку, поэтому файл,
  записанный до её появления, был недостижим для `read_subagent_thread` и
  отвечал «Thread not found». Ребёнок не попадает в список диалогов:
  `repo_devagent_list_threads` отбирает строки с `parent_thread_id IS NULL`.
- **Итог запуска попадает в журнал ребёнка.** От ребёнка нельзя требовать
  вести журнал: read-only задание или падение до первого
  `task_state_init` оставляют файл пустым или отсутствующим. Поэтому
  `finish_run` дописывает в раздел `Handoff` журнала абзац
  `Runtime outcome (run <id>)` - статус, `stop_reason`, `error_code`,
  число шагов, признак `retryable`, сводку и незакрытые пункты. Запись
  идемпотентна по `run_id` (повторное завершение не дублирует абзац),
  никогда не затирает текст самого ребёнка и выполняется best effort:
  сломанный журнал не превращает завершённый запуск в failed.
- **Результаты инструментов объясняют статус.** Поле `note` в ответах
  `spawn_agent`, `resume_subagent`, `subagent_status` и
  `read_subagent_state` переводит статус в следующее решение: `failed` +
  `internal_error` - «дефект платформы, не повторяй»; `failed` +
  `retryable` - «одна попытка может пройти, но измени бриф»; `max_steps` -
  «дели на части, resume не добавляет шагов»; `timeout` - «сузь задачу или
  подними лимит»; истёкшее ожидание при `running` - «всё ещё работает, не
  завис»; `awaiting_input` - «читай журнал и продолжай»; пустой журнал -
  «это не значит, что ребёнок ничего не делал». Пояснения живут рядом с
  данными, поэтому не требуют правки системного промпта каждого
  сотрудника.
- Интерфейс: статус-строка диалога показывает живые фоновые запуски,
  плашка `_notice` помечает скрытое извещение в ленте, а обновление статуса
  выполняется через `st.fragment` - без перезапуска всей страницы.

#### FR18a - Проверка результата делегирования (`verify_result`)

- Веер возвращает результаты, но не проверяет их: родитель до сих пор верил
  сводке ребёнка на слово. Отдельный шаг после веера закрывает этот разрыв -
  инструмент `verify_result(run_id, criteria)` запускает настроенного
  агента-верификатора и возвращает структурный вердикт (`core/orchestration/verify.py`).
- Вердикт имеет ровно три значения: `passed` (результат соответствует
  критериям), `failed` (не соответствует, причины перечислены) и
  `inconclusive` (проверить не удалось: нет данных, критерии неконкретны,
  ответ не разобран). `inconclusive` - честный ответ «не знаю», а не ошибка,
  и выдавать его за успех запрещено.
- **Верификатор видит только результат.** На вход идут `summary`, артефакты
  (путь, вид, digest), `error_code`, `steps_used` и `tokens_used`, плюс текст
  критериев. Транскрипт, журнал и ход рассуждений целевого запуска не
  передаются: проверяющий, читающий мысли исполнителя, соглашается с ним
  вместо проверки. Содержимое артефактов верификатор читает сам своими
  инструментами по абсолютному пути.
- **Разбор ответа консервативен** (`parse_verdict`): ищется последний
  разбираемый JSON-объект (модель может предварить его рассуждением);
  отсутствие JSON, неизвестное значение вердикта и `reasons` не-списком дают
  `inconclusive`, а `passed` при непустых `reasons` превращается в `failed` -
  правило не даёт подписать результат и в том же ответе перечислить его
  дефекты.
- **Отказ верификатора не ломает веер:** если запуск проверяющего завершился
  `failed`/`error`/`timeout`, инструмент возвращает `ok: true` с вердиктом
  `inconclusive` и кодом сбоя в причинах. Ошибкой вызова (`ok: false`)
  считаются только нарушения контракта: пустой `run_id`, неназначенный
  верификатор (`verifier_not_configured`), неизвестный запуск
  (`run_not_found`), незавершённый запуск (`run_not_finished`) и попытка
  проверить сам запуск-верификатор (`invalid_args`).
- **Проверка проверки запрещена.** Запуск-верификатор распознаётся по слагу
  агента И по маркеру цели `VERIFIER_GOAL_PREFIX`, поэтому переназначение
  настройки не открывает обходной путь; сам инструмент выключен в каталоге
  ребёнка (`CHILD_DISABLED_TOOLS`).
- **Настройка - отдельное право.** Ключ конфига `verifier_agent` (пустая
  строка - не назначен) с геттером/сеттером `get_verifier_agent` /
  `set_verifier_agent`; сеттер отклоняет слаг, которого нет в реестре, и НЕ
  требует присутствия в `allowed_agents` - право проверять не должно
  зависеть от списка вызываемых. Инструмент появляется в каталоге и в блоке
  промпта `## Verifying delegated work` только при непустом значении; сбой
  чтения конфига скрывает его.
- **Запуск - тем же путём.** `verify_result` вызывает `service.run`, поэтому
  глубина, пул и суммарные запуски действуют как для любого ребёнка; дерево
  берётся из треда целевого запуска (или из его корня), чтобы проверка не
  сбрасывала лимиты. Верификатор получает собственный тред и журнал.
- Где вызывается: `verify_result` запускает ребёнка, поэтому исполняется в
  фазе веера (`_TREE_CALL_NAMES` в `dev_agent/agent_loop.py`), а не внутри
  `dispatch` - иначе запуск ждал бы блокировку связывания рабочей папки,
  которую держит родитель.

### FR19 - Персональная память (два хранилища)

Память разделена на два независимых хранилища с разными владельцами,
временем жизни и правилами экспорта. Смешивать их нельзя: личные заметки
никогда не покидают установку, рабочие данные проекта - всегда уезжают
вместе с проектом.

- **Персональный слой** (`core/personal_memory.py`) - заметки о том, КАК
  работать. Лежит в `DATA_DIR/personal/` (`.gitignore`), не экспортируется,
  удаляется вместе с установкой. Области (`scope`):
  - `user` - карточка владельца, общая для всех сотрудников;
  - `orchestrator:<slug>` - личная память конкретного сотрудника;
  - `project:<hash12>` - заметки о конкретном рабочем проекте (ключ -
    первые 12 символов sha256 абсолютного пути рабочей папки);
  - `connector:<id>` - адаптер: текст физически хранится в
    `DATA_DIR/connectors/<id>/memory.md` и обслуживается API коннекторов.
- **Лимит области** - 64 КиБ (`PERSONAL_MEMORY_MAX_BYTES`), версии -
  в `personal/.backups/<kind>__<key>/v<stamp>.md`, хранятся последние 10
  (`PERSONAL_BACKUPS_KEPT`). Запись атомарная (`tempfile` + `os.replace`),
  в шапке файла метки `updated_at`, `updated_by`, `revision`.
- **Фильтр секретов:** `write_memory` отказывает, если текст похож на
  учётные данные (`detect_secret`), и НЕ повторяет найденный фрагмент
  в сообщении об ошибке.
- **Права:** сотрудник пишет только свои области (`user`, свой
  `orchestrator:<slug>`, `project:<hash>`); чужая область сотрудника даёт
  отказ `another employee`. Внутренние вызовы (сборка промпта, UI,
  миграция) передают пустой `caller_slug` и считаются доверенными.
- **Инструменты агента** (`dev_agent/universal_agent.py`):
  `get_personal_memory` (чтение области; `scope` по умолчанию `current` -
  собственные заметки сотрудника, `max_chars` ограничивает вывод),
  `set_personal_memory` (`mode='replace'|'append'`), `list_personal_memory`
  (перечень непустых областей с метаданными). Они не входят в
  `WORKSPACE_REQUIRED_TOOLS`: память доступна и без выбранной папки.
- **Защита карточки владельца:** область `user` общая для всех сотрудников,
  поэтому `set_personal_memory` разрешает её дополнение (`mode='append'`),
  а полная перезапись (`mode='replace'`) отклоняется, пока вызов не передаст
  `overwrite_owner_profile=true` - флаг ставится только по явной просьбе
  владельца. Флаг принимает и булево значение, и строку (`'true'`, `'1'`,
  `'yes'`, `'on'`), потому что модель может прислать его строкой.
- **Инъекция в промпт** (`core/orchestrators.py`, `build_assistant_dicts`):
  `_extend_prompt_with_personal_card` добавляет карточку владельца
  (`## Owner profile`, только области `Rules`, `Preferences`, `Environment`,
  `Notes`, жёсткий потолок 2500 символов, `Rules` не отбрасывается никогда)
  и делает это только при непустой карточке.
  `_extend_prompt_with_memory` добавляет блок `## Memory` ВСЕГДА, даже когда
  заметок ещё нет: блок объясняет разделение двух хранилищ (КАК работать
  против СОДЕРЖИМОГО работы), перечисляет области, называет состояние
  собственной области (пусто либо размер, ревизия и дата) и задаёт правило
  «когда писать» - после поправки владельца, после решения, важного в
  следующий раз, после обнаруженного ограничения; одноразовые детали и уже
  видимое в промпте не записываются. Без этого правила практика заметок не
  начинается на чистой установке. Текст личных заметок сотрудника в промпт
  НЕ попадает - только размер, читать их нужно инструментом. При сбое слоя
  памяти блок выводится в форме «область пуста», а карточка владельца
  пропускается: промпт не ломается.
- **Интерфейс:** вкладка `🧠 Memory` в настройках сотрудника (просмотр
  размера, ревизии, даты, редактирование и удаление), блок памяти в карточке
  коннектора, страница персональной памяти владельца в настройках.
- **Каскад:** `delete_orchestrator` архивирует личную память сотрудника
  в `personal/.archive/`, а не удаляет её - заметки переживают увольнение.
  `create_orchestrator`/`save_orchestrator` принимают `memory_dir` и хранят
  его в `config.memory_dir`.
- **Рабочая папка (`MEMORY_DIR`)** - второе хранилище, для рабочих данных
  роли (реестры, карточки, журналы). Резолвер
  `core/orchestrator_folders.py:resolve_data_dir(slug, workspace)` отдаёт
  абсолютный путь по первому совпадению: маркер `MEMORY_DIR:` в промпте →
  `config.memory_dir` → центральный `DATA_DIR/agents_data/<slug>/`.
  Центральный корень - дефолт: папка принадлежит установке, поэтому одна роль
  имеет одну память в любом проекте. Явные формы: `workspace:<подпуть>` -
  от проекта, `central:<подпуть>` - от центрального корня, `.` - корень
  проекта, абсолютный путь - как есть, прочий относительный путь - от
  рабочего проекта. Результат содержит `source`, `scope`
  (central/workspace/external), `outside_workspace`, `legacy` и `conflicts`
  (папки, где остались файлы после смены пути: данные не переносятся молча,
  пользователь видит предупреждение).
  Пустые папки не создаются - файл появляется с первой записью.
  Если папка недоступна (перемещена, удалена, рабочая папка указывает
  в другое место), роль не создаёт новую молча: сообщает об этом, спрашивает
  владельца и до решения держит заметки только в текущей задаче. Заметка
  о том, КАК работать, от рабочей папки не зависит и сохраняется в
  персональной памяти.
- **Доступ файловых инструментов.** Рабочая папка - второй разрешённый
  корень наряду с проектом: `memory:registry.md` или абсолютный путь внутри
  папки (`config.to_project_relative` / `resolve_in_project`). Всё вне обоих
  корней отклоняется, включая папку другого сотрудника. Инструменты работают
  и без выбранного проекта. Путь объявляет платформенный блок
  `## Working memory` (`_extend_prompt_with_working_memory`), поэтому промпт
  роли его не дублирует.
- **Перенос старой раскладки.** `core/memory_migration.py` - план только на
  чтение, копирование с проверкой совпадения до отчёта, источник не
  удаляется, конфликт не сливается молча. Центральный корень `agents_data`
  сам оканчивается на `_data`, поэтому legacy-папкой он не считается:
  распознавание идёт по пути, а не по имени. Иначе установка, где `DATA_DIR`
  совпадает с корнем проекта, принимала бы его за папку сотрудника `agents`
  и предлагала слить данные всех ролей в `agents_data/agents/`. Настоящая
  `<проект>/<slug>_data` рядом с ним по-прежнему попадает в план. CLI:
  `scripts/migrate_agent_data.py` (dry-run по умолчанию, `--apply` для
  записи).
- **Профили структуры данных** (`employee_creator`, 7-я секция) выбираются
  по типу единицы работы: ПОТОК (реестр + журнал, без папок на единицу),
  ДЕЛО/КУРС/СТАТЬЯ (карточка на единицу со своим жизненным циклом),
  ИССЛЕДОВАНИЕ (реестр тем). Правило роста: папка на единицу создаётся,
  когда у неё появляется три и более собственных артефактов.

### FR20 - Маркетплейс сущностей (агенты, навыки, базы знаний, MCP-серверы)

Каталог сущностей с установкой, обновлением и откатом. Устанавливаются все
четыре типа: навык (`skill`), агент (`agent`), база знаний (`rag`) и
MCP-сервер (`mcp`). Публикатор каталога подписывает `index.json` и каждый
`entity.json` (`<файл>.sig`, Ed25519), а клиент проверяет подпись до разбора
JSON и до скачивания пакета.

- **Доверие.** Якоря доверия лежат в самой установке (`keys/*.pem`), а не в
  скачанном каталоге: ключ, приехавший вместе с данными, ничего не
  доказывает. `marketplace.signature_keyring` перенаправляет на другое
  кольцо (частное зеркало), `SAGAII_SIGNATURE_KEYRING` делает то же для
  апдейтера. Кольцо может держать несколько ключей сразу - это и есть
  ротация: новый ключ публикует, старый продолжает проверяться, пока от
  него не останется ни одного поддерживаемого клиента.
- **Политика каналов.** `stable` и явный `marketplace.require_signature`
  отказывают в неподписанном или чужом манифесте с кодом
  `signature_required`; каналы разработки (`main`, `raw`, `dev`) читают его
  и записывают `verified=false` в отчёт, поэтому локальная работа не требует
  ключа. `key_id` выводится из открытого ключа, поэтому подпись всегда
  называет ключ, которым сделана.
- **Якорь установлен.** Публичная половина релизного ключа лежит в
  `keys/ed25519-public.pem` (`key_id 75579089d2cb61b3`), поэтому проверка не
  требует скачивания: до 2.43.0 механизм был готов, но доверять было нечему -
  `stable` отказывал в каждом релизе, а `main` только предупреждал. Приватная
  половина живёт в `~/.sagaai/ed25519.pem` (права `0600`), в репозиторий не
  попадает и требует резервной копии: утрата ключа означает, что новые
  подписи делать нечем.
- **Подпись не входит в манифест.** `file_versions.json.sig` - sidecar: запись
  внутри подписываемого манифеста сделала бы первый релиз зависимым от
  подписи предыдущего, поэтому верификатор манифеста пропускает его явно
  (`COVERAGE_SKIP`).
- **Манифест обновлений.** `scripts/sign_release.py` подписывает
  `file_versions.json` (`sign`), проверяет (`verify`), генерирует пару
  (`keygen`) и печатает кольцо (`keyring`). Апдейтер скачивает `.sig` вместе
  с манифестом и отказывает `stable`-каналу без валидной подписи. Приватный
  ключ приходит путём или переменной `SAGAII_SIGNING_KEY` и в репозиторий не
  попадает: `.gitignore` держит `*.pem` вне `keys/`.

- **Единый выключатель.** `marketplace.enabled` (по умолчанию включён)
  закрывает три вещи сразу: блок «МАРКЕТПЛЕЙС» в боковом меню, разовый сидинг
  реестра на первом рендере и обновление кэша реестра при импорте
  встроенных оркестраторов (`core/orchestrators.py`). При выключенном
  выключателе раздел не рисуется и не пишет ничего - ни строк реестра, ни
  файлов.
- **Подразделы витрины.** Пять подразделов - сотрудники, помощники, навыки,
  базы знаний, коннекторы - это пары «тип каталога + вид агента»: сотрудники
  и помощники делят тип `agent`, но ставятся в разные места, поэтому у них
  свои списки. Подразделы работают и вкладками витрины, и пунктами меню; обе
  стороны пишут ключ `mp_section`, а запрос из меню идёт отдельным ключом
  `mp_section_target` и открывает нужную вкладку через `default` - записать
  состояние вкладки после её создания Streamlit не даёт.
- **Блок «Дополнительно».** Рекомендуемый набор сущности показан в карточке
  отдельным блоком: позиции подписаны переведёнными названиями типов и своим
  состоянием, галочки стоят по `default_selected`, недоступные позиции
  остаются видимыми и неактивными. Отчёт установки набора несёт
  `requires_secrets`/`credentials_status`, поэтому после установки коннектора
  карточка напоминает, где заполнить его учётные данные.
- **Одна кнопка установки.** Карточка показывает ровно одну кнопку
  «Установить», и одно нажатие ставит сущность вместе с отмеченными позициями
  набора: сначала сущность, затем набор как единый прогон с откатом. У уже
  установленной сущности та же кнопка ставит только отмеченное, а если
  отмеченного нет - кнопки нет. Раскрытие карточки хранится в
  `session_state` (`mp_open_<id>`), а не выводится из нажатия текущего
  прогона: каждое нажатие запускает новую перерисовку, где кнопка
  «Подробнее» уже не нажата, и карточка, свёрнутая по этому признаку,
  проглатывала бы установку - пользователь не видел ни агента, ни сообщения.
- **Старт приложения остаётся офлайновым.** Каталог читается только по
  нажатию кнопки: витрина грузит индекс по «Обновить», страница
  «Обновления» - по «Проверить обновления». Ни `app.py`, ни
  `core/default_imports.py`, ни сидинг реестра, ни рендер сайдбара не
  обращаются к сети; это закреплено и статической проверкой вызовов, и
  запретом сокетов в тестах.
- **Установка** (`core/marketplace/installer.py`) пишет журнал
  прогона до изменения файлов, копирует пакет во временную папку, сверяет
  sha256 по манифесту пакета и переносит результат атомарно. Строка
  `marketplace_installed` хранит тип, id каталога, runtime-slug, версию,
  `files_json`, `tree_sha256` и признак локальных правок; `skills.json`
  библиотеки обновляется в той же транзакции. Витрина и планировщик пакетов
  вызывают единый диспетчер `install_entity`, который по типу сущности
  направляет работу в свой установщик: `installer` (навык),
  `agent_installer`, `rag_installer`, `mcp_installer`. Список `SUPPORTED_TYPES`
  перечисляет все четыре типа и читается витриной и планировщиком пакетов
  вместо пробного вызова.
- **Вид агента** (`agent_kind`). Сущность типа `agent` бывает двух видов:
  `orchestrator` (сотрудник: папка оркестратора, мерж конфига, инструкции,
  functions) и `assistant` (помощник: папка `DATA_DIR/assistants/<slug>` с
  `manifest.json`, `prompt.md` и вложениями `files/*.txt`, строка в таблице
  `assistants`). Вид хранится в манифесте, в индексе каталога, в строке
  `marketplace_installed` и в карточке витрины; манифест без вида считается
  сотрудником - так читаются записи, созданные до появления поля. Вложения
  помощника принимаются только текстовыми: хранилище держит их как `.txt`,
  поэтому пакет с другим расширением отклоняется целиком, а не
  устанавливается наполовину. Смена вида у установленной сущности
  запрещена (`agent_kind_changed`): вид определяет и папку, и таблицу,
  поэтому сначала нужно явное удаление. При обновлении вложения, добавленные
  пользователем, сохраняются, а отредактированный промпт не перезаписывается
  каталогом.
- **Прерванный прогон восстанавливается на холодном старте**
  (`core/marketplace/bootstrap.recover`, хук в `app.py` до импорта
  Streamlit): незавершённый прогон откатывается по своему бэкапу и
  помечается в журнале, чтобы следующая попытка не начиналась поверх
  мусора.
- **Матрица конфликтов** (`core/marketplace/conflicts.py`) отвечает на
  вопрос «что делать с уже установленным»: локальные правки определяются
  сравнением `files_json` с диском, а не временем изменения файла.
  Состояние установки читает `conflict_state.py`, форк и возврат своей
  версии живут в `conflict_fork.py`. Три
  пути - оставить свою версию (`keep_mine`), взять каталог
  (`take_catalog`, с бэкапом заменяемых файлов) и форк (`fork`, новый id
  `<id>#forkN` и папка `<slug>_fork_NN`); оригинал при форке приводится к
  каталогу. Удаление пишет маркер в `marketplace_removed`, поэтому
  встроенный импорт не воскрешает удалённый навык.
- **Встроенные сущности усыновляются, а не дублируются**
  (`core/marketplace/migration.py`). `LEGACY_DEFAULTS` сопоставляет пару
  (тип, id) с копией, которая уже стоит на диске, и заводит ей строку
  реестра с синтетической версией `legacy` - ниже первого релиза каталога,
  чтобы пользователь увидел настоящее обновление, а не молчаливое «нечего
  делать». Навык `rag_base_creator` сеется из дистрибутива в папку со своим
  именем и потому усыновляется наравне с оркестратором и базой; каталог
  считает такую папку занятой (`adopt`) и не предлагает вторую копию.
  Оркестратор `universal_agent` записан в `LEGACY_DEFAULTS` по той же
  причине: он предустанавливается из дистрибутива и одновременно
  публикуется в каталоге, поэтому витрина показывает обновление, а не
  предложение поставить второй экземпляр, а установка из каталога
  обновляет ту же папку.
  Маркер удаления проверяется раньше усыновления - иначе удалённое
  вернулось бы первым же стартом.
- **Обновления** (`core/marketplace/updates.py`) сравнивают версии по
  semver и применяют ту же механику конфликтов. Проверка покрывает все
  четыре типа и раскладывает находки по секциям `skill`/`agent`/`rag`/`mcp`;
  ссылка на сущность принимается и в форме `type:id`, и в виде голого id
  (тогда тип ищется по реестру). Навык обновляется через трёхуровневый
  резолвер конфликтов, остальные типы - переустановкой своей версией через
  собственный установщик, потому что база и агент заменяются целиком.
  Отказ по отдельной
  сущности не отменяет остальные: сущность с несовместимой платформой,
  требующая исполняемого кода при `allow_code=false` или непринятой
  лицензии попадает в список недоступных с причиной, а остальные
  обновляются.
- **Откат** (`core/marketplace/rollback.py`) восстанавливает файлы, строку
  реестра и `skills.json` байт в байт; журнал прогонов ограничен - 20
  записей для навыков и 3 для баз знаний, потому что прогон базы знаний
  на порядок тяжелее.
- **Хранилище** - `DATA_DIR/marketplace/`: журнал прогонов, бэкапы
  прогонов и кэш пакетов. Строки реестра живут в SQLite
  (`marketplace_installed`, `marketplace_removed`).

### FR21 - Запуск по расписанию
- **Назначение.** Владелец один раз описывает задачу, исполнителя и
  периодичность, а платформа сама запускает диалог в нужный момент.
  Раздел «Запуск по расписанию» - это не отдельный вид агента: правило
  запускает обычный диалог выбранного сотрудника, поэтому результат виден
  в «Истории» рядом с диалогами, начатыми вручную.
- **Правило (расписание).** Название, сотрудник (`agent_slug`), текст
  задачи и брифа, часовой пояс, первый момент запуска, интервал
  (число и единица: часы/дни/недели), запрещённые дни недели, тихие часы
  и лимиты запуска (`max_runs`, `max_steps`).
- **Дни - это запрет, а не выбор.** `blocked_weekdays` перечисляет
  дни, в которые правило молчит; пустой набор означает «каждый день».
  Пресеты (`every_day`, `weekdays_only`, `weekends_only`) - лишь
  сокращения для частых наборов, хранится всё равно маска.
- **Расчёт момента.** Всё считается в зоне правила
  (`core/schedules/calc.py`): «09:00 Europe/Moscow» остаётся девятью
  часами утра и после переезда сервера. Предпросмотр следующих точек и
  движок запуска идут одним и тем же кодом, поэтому обещанное и
  случившееся не расходятся. Тихие часы сдвигают точку за пределы окна,
  а не отменяют запуск.
- **Один момент - один запуск.** Претензия на точку атомарна на уровне
  базы: повторный тик (перезапуск, медленный цикл, второй процесс)
  получает отказ и ничего не удваивает.
- **Пропуск - это пропуск.** Точка, чьё время прошло, пока платформа
  была выключена, записывается в историю как `skipped` с причиной
  `missed`, а сетка уезжает вперёд. Догонов по умолчанию нет: десять
  часов простоя не превращаются в десять запусков.
- **Ручной запуск - это касса, а не перевод часов.** Кнопка «запустить
  сейчас» проходит весь путь обычного запуска (строка истории, диалог,
  счётчики), но `next_run_at` не двигает: сетка остаётся там, где её
  оставил владелец. Поэтому счётчики и расписание живут отдельно.
- **Сбой и удержание.** Каждый запуск пишет статус и код ошибки в
  историю правила. Три сбоя подряд переводят правило в `error_hold`:
  дальше оно молчит, причина остаётся на карточке, а владелец решает,
  чинить её или удалять. Исчерпание `max_runs` переводит правило в
  `finished`.
- **Планировщик.** Один фоновый поток на процесс
  (`core/schedules/daemon.py`): идемпотентный `bootstrap`, сердцебиение
  для проверки живости, `tick_once` забирает дозревшие правила и тратит
  на каждое отдельный воркер. Число одновременных запусков ограничено
  размером пачки, а не числом правил.
- **Хранение.** Правила и история запусков лежат в SQLite
  (`schedules`, `schedule_runs`); диалоги - в обычном хранилище диалогов
  со своими транскриптами, поэтому расписание не заводит второй способ
  читать переписку.
- **Страница.** `ui/pages/schedules.py`: список правил со статусом,
  ближайшей точкой и счётчиками, форма создания и правки, подтверждение
  удаления, история запусков с ошибками, предпросмотр следующих точек и
  ручной запуск. Ключи переводов строятся только через явные словари -
  склейка ключей запрещена, иначе i18n-тест их не увидит.
- **Проверка.** `tests/test_schedules_*.py` (ядро, хранилище, раннер,
  демон, форма, страница) и
  `tests/scenarios/test_schedules_scenario.py`: правило срабатывает
  один раз и попадает в «Историю», перезапуск не повторяет точку,
  простой становится пропуском, запрещённый день пропускается в
  предпросмотре, три сбоя удерживают правило.

### FR22 - Консоль `sagaai` (третий вход в платформу)
- **Назначение.** Интерфейс, HTTP API и консоль - три равноправных входа в
  одну платформу. Консоль нужна там, где интерфейс недоступен или не нужен:
  сервер без браузера, cron-задача, CI, первичная настройка, диагностика
  установки, обслуживание баз.
- **Пакет и запуск.** Код - `sagaai/` (команды в `sagaai/commands/`),
  точки входа - `python -m sagaai`, консольная команда `sagaai` (из
  `pyproject.toml`) и скрипт `bin/sagaai` для неустановленной копии; все
  вызывают одну функцию `sagaai.cli.main`, поэтому ведут себя одинаково.
- **Изоляция.** Консоль не импортирует Streamlit и HTTP-стек: интерфейс
  запускается отдельным процессом (`sagaai ui`), сервер - лениво
  (`sagaai serve`). `tests/test_cli_imports.py` проверяет это в подпроцессе
  с заблокированными пакетами, а не по факту установки.
- **Команды.** `doctor` (диагностика без изменений), `run` (задача
  сотруднику с ожиданием результата), `serve` (HTTP API), `ui`
  (Streamlit), `token` (create/list/revoke), `update`
  (check/stage/apply/rollback), `migrate` (снимок, миграции, проверка
  целостности), `backup` (create/list/restore), `agents` (список slug'ов).
- **JSON-режим.** `--json` печатает РОВНО один объект на stdout:
  `{ok, command, exit_code, version, data}` при успехе и
  `{ok, command, exit_code, version, error{code,message,hint}}` при ошибке.
  Прогресс и предупреждения идут в stderr, поэтому перенаправление потока
  не портит результат. `--json` принимается и на верхнем уровне, и после
  имени команды.
- **Коды возврата.** 0 - успех; 1 - операция не удалась; 2 - ошибка
  конфигурации или запроса; 3 - конфликт (платформа уже запущена, запуск
  ещё идёт). Коды перечислены в `sagaai/exit_codes.py` и печатаются в
  `--help` каждой команды - скрипт не должен угадывать.
- **Разрушительные действия.** `update apply`, `update rollback`,
  `backup restore`, `migrate` требуют подтверждения: интерактивный терминал
  получает вопрос `y/N`, неинтерактивный - отказ с кодом 2 и подсказкой
  `--yes`. Причина в том, что чтение из пустого pipe зависло бы навсегда, а
  ответ «да» по умолчанию свёл бы флаг к пустышке. Замена файлов и баз
  дополнительно отказывает, пока платформа запущена (код 3), - живой
  процесс уже загрузил то, что команда собирается заменить.
- **`run` и пауза.** Запуск ждёт результата; пауза (план на утверждение,
  вопрос) - это РЕЗУЛЬТАТ с кодом 0 и описанием паузы, а не ошибка.
  Истёкшее ожидание даёт код 3 и run id, но запуск НЕ отменяется: отказ от
  ожидания не должен уничтожать работу.
- **Схема как версионируемый артефакт.** Единственный владелец структуры
  баз - цепочка ревизий Alembic в `migrations/versions/`. При старте и в
  `sagaai migrate` драйвер `storage/migrations.py` сначала выполняет
  data-миграции раскладки (архиваторы сообщений), затем `upgrade head`;
  повторный запуск на актуальной базе не открывает транзакцию. Новая
  установка создаётся той же цепочкой (baseline-ревизия), а база без
  `alembic_version` усыновляется baseline без пересоздания данных.
  `render_as_batch` обязателен: SQLite меняет таблицу пересозданием.
- **`doctor` только читает.** Диагностика не создаёт базы и не пишет в
  папку данных: `tests/test_cli_commands.py` проверяет, что после прогона
  на чистой установке файлов баз не появилось. Готовит установку `migrate`.
  Проверка `schema` показывает ревизию каждой базы и её расхождение с head
  (`behind`), отдельно называя базу без истории и отсутствующий файл.
- **Снимки баз.** `core/gateway/backup.py` копирует через движок SQLite
  (копия файла в WAL-режиме - не бэкап), пишет манифест с sha256 каждого
  члена и проверяет `PRAGMA integrity_check` до и после. Снимки лежат в
  `DATA_DIR/backups/databases/<id>/` рядом с базами, которые копируют, -
  это данные, а не код, и `SAGAAI_DATA_DIR` покрывает их целиком.
  Восстановление сначала снимает копию ТЕКУЩЕГО состояния, поэтому
  ошибочное восстановление отменяется восстановлением страховочного снимка.
- **Изоляция установки.** `SAGAAI_INSTALL_ROOT` переопределяет корень
  установки. Команда, заменяющая файлы, должна уметь работать не по
  рабочей копии, из которой её импортировали: тесты перенаправляют оба
  корня и не касаются дерева разработчика.
- **Проверка.** `tests/test_cli_imports.py` (границы слоя),
  `tests/test_cli_console.py` (конверт и форматирование),
  `tests/test_cli_commands.py` (команды как контракт процесса) и
  `tests/scenarios/test_cli_scenarios.py` (девять сквозных историй:
  подготовка чистой машины, окно обслуживания со снимком и откатом,
  обновление из локального зеркала с откатом, выдача токена скрипту,
  отказы без терминала, работа без Streamlit).


## Нефункциональные требования

### NFR1 - Модульность
- Код разделён на пакеты: `core/` (бизнес-логика без Streamlit), `ui/`
  (интерфейс), `storage/` (персистентность), `dev_agent/` (агентные
  возможности), `sagaai/` (консоль - третий вход в платформу),
  `server/` (HTTP API).
- Ядро оркестраторов - `core/orchestrators.py` - публичный API для CRUD,
  построения assistant-словарей, экспорта/импорта, preset-импорта; папки
  оркестраторов обслуживает `core/orchestrator_folders.py`.
- Универсальный UI оркестраторов - `ui/pages/orchestrator.py` - одна
  страница для всех оркестраторов (параметризуется slug), плюс
  `ui/pages/orchestrators.py` (управление списком) и
  `ui/pages/orchestrator_settings.py` (настройки).
- Встроенные сущности и канонические копии (промпты, переводы, сервисы,
  пресеты) лежат в `defaults/`; `core/defaults.py` и
  `core/default_imports.py` обеспечивают импорт «из коробки».
- RAG-подсистема: `core/rag*.py` (CRUD, чанкинг, эмбеддинги, индекс,
  индексатор, поиск) + страница `ui/pages/storage.py`.

### NFR2 - Тестируемость
- Полное покрытие модульными тестами (pytest).
- Моки Streamlit позволяют тестировать UI-логику без запуска реального
  сервера.
- Тесты запускаются в CI и при разработке.
- Статический анализ - `ruff` (конфигурация в `ruff.toml`, набор `E`/`F`/`I`).
  Запуск: `python3 -m ruff check`. Правило `E402` отключено пофайлово там,
  где импорт обязан идти после `sys.path.insert`/`importorskip`/
  `set_page_config` - каждая такая запись сопровождена причиной в конфиге.
  Массовые косметические правила (`UP`, `BLE`, `RUF013`) выключены осознанно.
- Регрессия прогоняется пакетами параллельно (файлы `tests/test_*.py`,
  `tests/scenarios/`, `tests/smoke/` - батчами по 12 в 4 потока): полный
  последовательный прогон на этой базе занимает слишком много времени.
- **Глобальное состояние процесса изолируется явно.** `dev_agent.config`
  хранит активную рабочую папку и признак `WORKSPACE_SELECTED`; отрисовка
  страницы оркестратора, сброс диалога и переход в пустое состояние его
  переключают. Утёкший `WORKSPACE_SELECTED=False` блокирует файловые
  инструменты во всех последующих тестах прогона, поэтому фикстура
  `_restore_dev_agent_state` из `tests/conftest.py` **не** объявлена
  autouse: её просит по имени тот модуль, который переключает состояние,
  либо он снимает и возвращает состояние сам. Папка `tests/scenarios/`
  владеет своим autouse-хуком - там переключение состояния и есть
  проверяемое поведение. `tests/test_test_state_isolation.py` разбирает
  тестовые модули через AST и падает с именем нарушителя, не давая утечке
  проявиться чужими падениями.
- **Данные записи тестов не попадают в установку.** `core.connectors._connectors_root`,
  `core.orchestrators` и родственные модули читают `core.paths.DATA_DIR` в
  момент вызова, поэтому тест, создающий подключение, сотрудника или
  помощника, без подмены этого пути пишет прямо в рабочую установку - и
  тестовая сущность переживает прогон, всплывая в интерфейсе рядом с
  настоящими. Такой модуль обязан изолировать `DATA_DIR` одним из трёх
  способов: подменить его самому, импортировать фикстуру изолирования из
  модуля-помощника (как `tests/test_ssh_tools.py` берёт
  `isolated_data_dir` из `tests/test_ssh_connector.py`) либо запросить
  фикстуру, имя которой оканчивается на `data_dir`. Проверку выполняет
  тот же `tests/test_test_state_isolation.py`: он сканирует модули через
  AST, знает перечень пишущих API и падает с именем нарушителя.
- **Поведение цикла агента зафиксировано golden-снимками.**
  `tests/test_loop_golden_payloads.py` проигрывает восемь сценариев цикла и
  сравнивает с `tests/fixtures/loop_golden/*.json` то, что уходит модели
  (сообщение, история, файловый контекст, флаг защиты от инъекций, набор
  колбэков) и что публикуется в интерфейс (последовательность событий
  `on_event`). Снимки обновляются только явно -
  `python scripts/capture_loop_golden.py`, который перезаписывает их и тут же
  проверяет воспроизводимость. Внутреннее устройство цикла можно менять
  свободно; его наблюдаемое поведение - только вместе со снимком в диффе.

### NFR3 - Безопасность при редактировании кода
- Защищённые файлы (ядро DevAgent) не могут быть изменены агентом.
- Каждое изменение файла создаёт бэкап с SHA-256 версионированием.
- Изменения применяются только после явного утверждения пользователем
  (в ручном режиме) либо после утверждения плана (в автономном режиме).
  Исключение - полностью автономный режим без согласования (pre-approved
  autonomous mode): пользователь явно отказывается от фазы утверждения,
  план составляется и исполнение начинается сразу; ручное применение
  (кнопка Apply) и подтверждения опасных команд продолжают действовать.
- Небезопасный код (`run_code`/`run_test`) проходит анализ в
  `core/dangerous.py`; опасные операции требуют подтверждения.

### NFR4 - Сохранность данных
- Все пользовательские данные (помощники, треды, конфигурация) хранятся
  в папке данных: строки и настройки - в SQLite, переписка диалогов -
  в файлах.
- **Переписка диалогов хранится в файлах, а не в таблице `messages`.**
  Каждый диалог - ассистентский (основная БД) и оркестраторный
  (`devagent.db`) - пишет сообщения в общий append-only JSONL-сегмент
  `dev_agent/transcript.py`, а его строка в `threads` держит индекс над
  файлом (`transcript_path`, `parent_thread_id`, `message_count`,
  `content_schema`). Файловую половину зеркала для обеих баз владеет
  `core/thread_mirror.py`: он не открывает БД, ничего не решает про индекс
  и не поднимает исключений - сломанное зеркало не должно ломать запись,
  которую оно зеркалит. Индексные колонки в своих таблицах обновляют
  `core/threads.py` (основная БД) и `core/threads_devagent.py`
  (`devagent.db`). Читатель отдаёт файл, только если в нём есть все
  сообщения, которые насчитал индекс (`thread_mirror.is_complete`):
  усечённый ретеншеном файл откатывается на таблицу, чтобы начало
  разговора не исчезло молча.
- **Переход на файловое хранилище выполняется один раз и без потери
  строк.** `core/chat_db_archive.py` при холодном старте (`app.py`, до
  открытия соединений): (1) пакует основную базу в проверенный zip рядом с
  собой, (2) пишет каждому диалогу его транскрипт, (3) заполняет индексные
  колонки, (4) только после этого удаляет перенесённые строки `messages`,
  (5) штампует раскладку в `PRAGMA user_version`. Файл базы НЕ заменяется
  (в отличие от `devagent.db`), потому что в нём же лежат помощники,
  настройки, коннекторы и реестр маркетплейса. Шаги идут под одной
  блокировкой `BEGIN EXCLUSIVE`: сообщение, записанное между копией и
  удалением строк, иначе пропало бы вместе со строками. Любая ошибка
  (непроверенный архив, занятая база, неудачная запись транскрипта)
  оставляет строки на месте - недоперенесённый диалог просто живёт в
  таблице, как жил раньше. Занятая другой копией база даёт `database is in
  use`, а не попытку писать вслепую.
- **Об успешном переводе сообщается один раз.** Факт переноса пишется в
  `DATA_DIR/chat_db_archive_notice.json` и читается через
  `chat_db_archive.take_notice()` в `ui/app.py` (страница один раз за
  сессию браузера): пользователь должен узнать, где лежит архив и сколько
  диалогов перенесено, потому что таблица после перевода пуста.
- Оркестраторы хранятся в таблице `orchestrators` (slug, prompt_text,
  config_json, tools, max_steps, auto_apply, is_builtin, sort_order);
  папка-источник каждого оркестратора содержит `orchestrator.json`,
  `instructions.json`, функции и инструкции.
- Треды оркестраторов хранятся в отдельной БД `devagent.db`; их
  переписка, как и переписка ассистентских диалогов, лежит в файловом
  транскрипте (см. выше).
- Файлы помощников и загруженные пользователем файлы сохраняются на диске.
- Базы знаний (RAG) хранятся в `DATA_DIR/rag_bases/` с локальным индексом
  и режимом поиска (`search_mode`: bm25/vector/hybrid); каноническая база
  `yaagentai_2020` поставляется в `defaults/rag_bases/`.
- Бэкапы и снапшоты кода хранятся в `.dev_agent/backups/`.
- Маркетплейс хранит журнал прогонов, бэкапы прогонов и кэш пакетов
  в `DATA_DIR/marketplace/`; строки установленного и маркеры удаления -
  в SQLite (`marketplace_installed`, `marketplace_removed`).

### NFR5 - Интернационализация
- Вся видимая пользователю строка должна проходить через `t()`.
- **Английский (`en.json`) - канонический языковой файл.** Он всегда
  содержит полный актуальный набор ключей. При отсутствии перевода в
  другом языке `t()` автоматически подставляет строку из английского
  файла (fallback).
- Комментарии в коде - только на английском.

## Ограничения

- Поддерживается только Python 3.12 и новее; установка - только
  editable-режим (`pip install -e .`), а точный набор зависимостей берётся
  из `requirements.lock` с проверкой хэшей.
- База данных - только SQLite; миграция на другие СУБД не предусмотрена.
- Аутентификация есть (страница «Доступы» или опциональный пароль
  `SAGAAI_AUTH_PASSWORD`), многопользовательский режим не предусмотрен.
- Приложение работает в окружении Streamlit для интерфейса; консоль
  `sagaai` (пакет `sagaai/`, консольная команда из `pyproject.toml`,
  скрипт `bin/sagaai` как совместимость) работает без Streamlit и
  без HTTP-стека - интерфейс запускается ею отдельным процессом.
- Универсальный разработчик работает только с папками, доступными
  локально (в пределах файловой системы).
- Экспорт/импорт оркестраторов в UI отложен (доступен только в core API);
  новые оркестраторы появляются через импорт на уровне core или через
  DevAgent.
- Поиск в RAG выполняется локально (SQLite): лексический BM25-индекс -
  полностью офлайн, векторный поиск - косинусное сходство, эмбеддинги
  генерируются удалённо через Yandex Embeddings API (только vector/hybrid).
