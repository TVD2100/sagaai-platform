# SagaAI - платформа для команды ИИ-сотрудников

**SagaAI - это платформа с открытым исходным кодом (source-available), на которой вы собираете и управляете собственной командой ИИ-сотрудников:** чат-ассистенты, автономные оркестраторы, базы знаний (RAG) и встроенный агент-разработчик DevAgent - в одном веб-интерфейсе, на вашем компьютере или сервере, с контролем над действиями агентов и защитой ваших данных. Лицензия - **PolyForm Noncommercial 1.0.0**: бесплатно для учёбы, личных проектов, образования и научных исследований, коммерческое использование - по отдельному договору.

Это не «ещё один чат-бот» и не «ещё один кодинг-агент». SagaAI объединяет персональных ассистентов, агентные платформы и кодинг-агентов в единой системе: сотрудники с разными ролями работают над задачами, опираются на ваши базы знаний, а агент-разработчик DevAgent редактирует код ваших проектов - с планом, утверждением, бэкапами и тестами.

## Кому подходит

Все сценарии ниже покрывает бесплатная некоммерческая лицензия - условия и полный список случаев в разделе [«Бесплатное использование»](#-бесплатное-использование).

### 🎓 Студентам и преподавателям

Учебные проекты, подготовка лекций и методических материалов, разбор сложных тем с ассистентом, проверка и рецензирование текстов, тренажёр по предмету на собственных конспектах. Базы знаний держат учебники и методички локально: агент отвечает по вашим материалам, а не по общим данным модели. Работает без API-ключей на лексическом поиске.

### 🔬 Исследователям и научным группам

Сбор и структурирование литературы, извлечение данных из PDF и таблиц, обработка результатов экспериментов, воспроизводимые опыты с ИИ-агентами. DevAgent помогает с кодом для обработки и анализа данных - с бэкапами, тестами и полным откатом.

### 🏛️ Некоммерческим организациям

Благотворительные фонды, госучреждения, организации здравоохранения и охраны окружающей среды: обработка обращений, работа с документами, подготовка отчётов и заявок, внутренняя база знаний по программам и регламентам.

### 🏡 Личным и хобби-проектам

Домашние проекты, любительская разработка, личные исследования и эксперименты, обучение новым инструментам. Можно собрать команду помощников под свои задачи, подключить базы знаний по интересам и вести проекты в DevAgent - без коммерческого применения.

### 👥 Сотрудники под конкретные роли

Ключевая идея платформы - не один универсальный чат-бот, а **команда специализированных ИИ-сотрудников**. Каждый сотрудник настраивается под узкую задачу без единой строки кода: роль и системный промпт, модель, набор инструментов, инструкции, навыки, свои базы знаний и подключения. ## Возможности

Каждая возможность платформы обслуживает главную идею - **команда ИИ-сотрудников под вашим контролем**.

### 💬 Чат с ИИ

- Чат с поддержкой OpenAI-совместимых API (YandexAI, DeepSeek) и GigaChat; поддержка веб-поиска от Yandex AI и Deepseek.
- Прикрепление файлов: текст, PDF, офисные форматы (docx, pptx, xlsx) с автоматическим извлечением содержимого.
- Ответы в Markdown с подсветкой синтаксиса и кнопкой копирования.

### 👥 Сотрудники (оркестраторы)

- Каждый сотрудник - автономный агент со своим системным промптом, моделью, эконом-режимом, инструментами, инструкциями, функциями, навыками, базами знаний и подключениями.
- **Модели.** Единая основная модель для всех шагов; дополнительно можно назначить модели распознавания и генерации изображений. У встроенного DevAgent поставляемые дефолты: DeepSeek `deepseek-flash` как основная модель (уровень рассуждений `xhigh`) и как модель распознавания изображений, генерация изображений не назначена. Назначенные модели используются инструментами `analyze_image` / `generate_image`: сотрудник читает изображения (вложения диалога или файлы проекта; YandexAI - `qwen3.6-35b-a3b` / `deepseek-v4.1-flash`, DeepSeek - `deepseek-flash`) и может сгенерировать новое (синхронный Images API YandexAI, модель `aliceai-image-art-3.0`) - результат сохраняется файлом и показывается в чате с кнопкой скачивания.
- **Загрузка страниц.** Необязательная модель загрузки: в списке только провайдеры с поддержкой Search/Fetch API (DeepSeek - модели `deepseek-flash` и `deepseek-v4-pro`). Рядом - чек-бокс «Использовать Selenium»: страница открывается в headless-браузере, её видимый текст основная модель переводит в Markdown (нужен пакет `selenium` и браузерный драйвер; при их отсутствии инструмент вернёт подсказку об установке). Пока чек-бокс включён, селекторы модели загрузки скрыты - конвертацию делает основная модель; сохранённая пара возвращается после снятия флажка.
- **Инструмент `url_fetch`.** При назначенной модели или включённом Selenium у сотрудника появляется инструмент `url_fetch` - загрузка одной веб-страницы как чистого Markdown-текста; ссылка на PDF скачивается и разбирается по страницам, остальное идёт через Search/Fetch API или браузер. URL валидируется (http/https, без логина и пароля, приватные и локальные адреса запрещены), содержимое санитизируется и помечается как недоверенные данные, длина ограничена 30 000 символов. Снятие обоих источников убирает инструмент; прежнее имя `page_fetch` работает как алиас.
- **Делегирование.** `spawn_agent` запускает другого сотрудника (в том числе параллельно - независимые запуски выполняются веером, а лента группирует события по запуску), `invoke_assistant` - один вызов помощника без цикла инструментов. В задании субагенту передаются абсолютные пути рабочей папки родителя и его файлов диалога, поэтому вложения доступны без пересылки; документ уходит помощнику файлом в `context_files` и читается целиком за один вызов. Кто кому может делегировать и сколько запусков разрешено, задаётся на вкладке «Делегирование»: чек-боксы сотрудников и помощников плюс шесть лимитов (глубина дерева, одновременные запуски, шаги и суммарное число запусков ребёнка, бюджет времени ребёнка - по умолчанию и не более часа, потолок токенов); лимиты диалога с субагентом вынесены туда же отдельной группой полей (см. «Диалог с субагентом»). По умолчанию: пять одновременных запусков, 300 шагов на ребёнка, 64 запуска на дерево - потолок шагов заведомо выше реальной работы, чтобы длинный запуск обрывал бюджет времени, а не счётчик, а веер из нескольких агентов не упирался в четвёртый запуск. Остановка диалога отменяет и дочерние запуски. По умолчанию делегирование разрешено на один уровень вглубь, вызовы помощников закрыты до явного разрешения. Встроенный **Universal-Agent** доступен по умолчанию: его право живёт в отдельном флаге `config.universal_agent_enabled` (отсутствие ключа = включено), поэтому новые сотрудники получают исполнителя без настройки, а снимается оно отдельным чек-боксом над списком сотрудников - общий список при этом не переписывается. Отозванное право исчезает и из промпта, и из рантайм-проверки: агент, которым нельзя пользоваться, не рекламируется модели.
- **Проверка результата.** Веер возвращает несколько результатов за один шаг, но не проверяет их. Шаг `verify_result(run_id, criteria)` запускает назначенного агента-верификатора и возвращает вердикт `passed`, `failed` или `inconclusive` (проверить не удалось - это не успех). Верификатор независим потому, что он НЕ видит: ему передаются сводка, артефакты, код ошибки и счётчики запуска, но не переписка и не ход рассуждений исполнителя - иначе проверка превратилась бы в согласие с ним; содержимое файлов он открывает сам. Разбор ответа консервативен: `passed` рядом с замечаниями считается провалом, а неразобранный ответ - `inconclusive`. Проверить сам запуск-верификатор нельзя. Сбой верификатора не ломает веер - вердикт остаётся `inconclusive` с кодом сбоя. Верификатор назначается на вкладке «Делегирование» отдельным правом: слаг не обязан входить в список вызываемых, а пока верификатор не назначен, инструмент не показывается вовсе.
- **Фоновые субагенты.** `spawn_agent(background=true)` возвращает `run_id` сразу: ребёнок работает в своём потоке, а диалог продолжает работу и получает извещение о завершении скрытой system-строкой на ближайшем шаге (без видимой реплики пользователя). Состояние запуска смотрят `subagent_status` (один запуск, всё дерево или ожидание терминального статуса до 30 с), а произведённое им забирает `subagent_result`: итоговый текст, артефакты и израсходованные ресурсы в той же форме, которую возвращает блокирующий запуск, - независимо от того, стартовал ребёнок в фоне или блокирующе. Пока запуск не завершён, результата нет: ответ сообщает `ready=false` и текущее состояние, потому что частичная работа, выданная за результат, выглядит как успех и потому хуже явной ошибки; `wait_seconds` (до 30 с) позволяет забрать готовый результат в том же шаге. Журнал ребёнка читает `read_subagent_state`, `sleep` блокирует шаг до события в дереве или таймаута (сколько ждать, решает вызывающий, потолок - час, без отмены работы), а `resume_subagent` продолжает работу с того места, где ребёнок остановился: готовые шаги не переделываются, уже созданные файлы не перезаписываются, дерево и счётчики запусков наследуются. Записи запусков переживают перезапуск процесса, а брошенный запуск распознаётся как `failed` по устаревшему heartbeat, чужому процессу или исчезнувшему pid. У субагента нет человека рядом, поэтому операция, требующая подтверждения, не подвешивает его: он получает отказ и переписывает действие без подтверждения либо сообщает о блокере. Цепочка продолжений ограничена, поэтому повторное продолжение упирается в `resume_chain_limit`, а не крутится бесконечно.
- **Диалог с субагентом.** Ребёнку иногда не хватает вводной: он не знает, какую из двух папок считать рабочей, и догадка стоила бы часа работы. Тогда он задаёт вопрос инструментом `ask_parent` и приостанавливается - тот же прогон, тот же журнал, уже записанные файлы на месте, `run_id` не меняется. Вопрос виден в ленте шага раскрытым блоком с пометкой «вопрос субагента», вариантами ответа, «что сделано» и «на чём застрял», а сверху диалога появляется строка «ждут ответа: N» с агентом и вопросом. Отвечаете вы, но всегда через агента: прямого канала «человек → субагент» нет, поэтому ваше решение сначала попадает к сотруднику, а тот передаёт его инструментом `answer_child(run_id, answer)`. Ответ продолжает ТУ ЖЕ задачу с места остановки, а не начинает новую - для новой работы есть отдельный запуск. Вопрос ждёт ограниченное время (по умолчанию 15 минут): по истечении запуск завершается с причиной «ответ не получен», но сделанное сохраняется, а поздний ответ запуск не оживляет - иначе об одном прогоне было бы две правды. На задачу даётся пять раундов вопросов, и раунд тратит вопрос, а не ответ. Ожидание переживает перезагрузку страницы: вопрос и запись лежат на диске, ответ принимается и после перезапуска. Лимиты диалога (раунды, длина вопроса и ответа, срок ожидания, сколько задач может ждать одновременно) редактируются на вкладке «Делегирование» рядом с остальными.
- **Транскрипты субагентов.** Переписка ребёнка не пишется в общую базу: каждый шаг дописывается строкой в `<history>/<parent>/subagents/<child>/transcript.jsonl`, поэтому запись одного ребёнка не блокирует чтение других диалогов, а обрыв процесса портит максимум последнюю строку - остальное читается. События рендера ленты в файл не попадают (это данные интерфейса, и на реальных диалогах они занимали около половины объёма сообщения), так что хранилище растёт примерно вдвое медленнее переписки. Старые сегменты сжимаются в `.gz` и читаются прозрачно, а сжатие не обновляет время последней записи - иначе тред выглядел бы свежим после каждой уборки и никогда не удалялся. Уборка (`sweep`) по умолчанию только показывает план: она сжимает холодные сегменты и режет целые сегменты самых тихих тредов, но никогда не трогает активный файл и не удаляет молча папку, чья строка в индексе исчезла, - такая папка попадает в отчёт, потому что в ней могут лежать загрузки, которые вы ещё откроете. Читает всё это `read_subagent_thread`, а упавший ребёнок продолжается с места остановки: к переписке прилагается чекпоинт с номером шага и уже созданными файлами, поэтому продолжение не переписывает готовое.
- **Переход на новый формат базы.** База, написанная прежними версиями, хранила переписку внутри себя. При первом запуске после обновления такой файл целиком уходит в архив `devagent.db.zip` рядом с собой, а рабочая база создаётся заново - в ней больше нет текста диалогов. Ничего не пропадает: архив содержит прежнюю базу полностью, а при запуске появляется сообщение с путём к архиву и числом сохранённых диалогов. Архив проверяется до удаления оригинала, поэтому оборванный переход оставляет либо старое состояние, либо целый архив; повторные запуски ничего не трогают. Прежние диалоги в интерфейсе не восстанавливаются автоматически - это отдельная операция переноса, которая выполняется только по вашему согласию и сначала показывает план.
- **Диагностика субагента.** Сбой ребёнка классифицируется по источнику: исключение внутри его цикла помечается `internal_error` с `retryable=false` (повтор упадёт так же - чинится причина, а не перезапуском), а сбой провайдера остаётся `provider_error` с `retryable=true`. Запись запуска сразу хранит производный тред ребёнка и его рабочую папку, поэтому журнал адресуем, а `finish_run` дописывает в раздел `Handoff` этого журнала абзац `Runtime outcome` со статусом, кодом ошибки, числом шагов и сводкой - даже если сам ребёнок журнал не вёл. Результаты `spawn_agent`, `resume_subagent`, `subagent_status`, `subagent_result` и `read_subagent_state` несут поле `note` с готовым смыслом статуса: «дефект платформы, не повторяй», «провайдер, одна изменённая попытка», «кончились шаги - дели задачу», «истёкшее ожидание значит работает, а не завис», «пустой журнал не значит, что работы не было».
- **Документы.** `read_thread_file` открывает вложения диалога, `read_document` - файл в рабочей папке по абсолютному пути (окно строк для больших файлов). Поддерживаются PDF, DOCX, DOC, PPTX, XLSX, XLS, RTF, ODT, HTML и plain text; текст и исходники читаются напрямую, поэтому `run_code` остаётся средством последней очереди.
- **Картинки в документах.** Смысл отчёта часто живёт не в тексте, а в диаграмме, скане или скриншоте. `extract_document_images` достаёт встроенные изображения из PDF, DOCX, PPTX и XLSX, сохраняет их PNG-файлами в `.dev_agent/doc_images/` рабочей папки и возвращает готовые группы по 5 штук - столько `analyze_image` принимает за один вызов. Распознаёт картинки назначенная модель распознавания изображений; её ответ помечается как недоверенные данные (`DATA_FROM_IMAGE`). Для сканов есть рендер страниц: `ocr='auto'` включается только когда у PDF нет ни текстового слоя, ни извлекаемых картинок, `ocr='force'` рендерит страницы всегда, причём рендер страницы заменяет встроенные картинки той же страницы - один и тот же материал не оплачивается дважды. Без назначенной модели файлы всё равно сохраняются, а инструмент подсказывает, что включить в настройках.
- **Журналы задач не копятся.** Каркас журнала задач создаётся заранее для каждого диалога, поэтому со временем накапливались файлы, которые уже никто не прочитает. Уборка при старте удаляет пустой журнал старше недели и журнал завершённого дочернего запуска, чей родительский журнал исчез; живой диалог, свежие файлы, журналы с историей и посторонние файлы не трогаются, а удаление пустого родителя не уносит с собой работающего ребёнка в том же проходе. Обход покрывает и рабочую папку проекта, и папки диалогов без выбранной папки, и выполняется один раз за процесс.
- **Системные функции включаются и выключаются чекбоксами** на вкладке «Функции»; отключённый инструмент реально блокируется диспетчером.
- В системный промпт каждого сотрудника автоматически добавляется каталог доступных инструментов (`## Available tools`) с правилами вызова; независимые вызовы разрешено объединять в один батч (с условиями независимости).
- **Память сотрудника.** У каждого сотрудника два независимых хранилища. Персональная память (`get_personal_memory` / `set_personal_memory` / `list_personal_memory`) хранит заметки о том, как с вами работать: общая карточка владельца (правила, предпочтения, окружение) и личная память конкретного сотрудника; она живёт в `DATA_DIR/personal/`, не экспортируется и не попадает в git, а при удалении сотрудника архивируется, а не стирается. Правило «когда писать» сотрудник получает в системном промпте всегда, даже пока заметок нет: после вашей поправки, после решения, важного в следующий раз, после обнаруженного ограничения; одноразовые детали и уже видимое в промпте не записываются. Карточка владельца общая для всех сотрудников: дополнить её может любой (`mode='append'`), а полная перезапись отклоняется, пока запись не передаст отдельный флаг `overwrite_owner_profile` - он ставится только по вашей явной просьбе. Рабочая папка роли (`MEMORY_DIR` в промпте, вкладка «🧠 Memory» в настройках) хранит рабочие данные - реестры, карточки дел, журналы решений. По умолчанию она центральная, `DATA_DIR/agents_data/<slug>/`: папка принадлежит установке, поэтому одна и та же роль видит одну и ту же память в любом проекте и не теряет данные при смене рабочей папки. Сотрудник обращается к ней префиксом `memory:` (`memory:registry.md`) или абсолютным путём, и это работает даже до выбора проекта. Роль, чьи материалы обязаны ехать вместе с проектом, указывает это явно через `MEMORY_DIR: workspace:<подпуть>`; `central:<подпуть>` задаёт общую папку внутри установки. Старые папки `<проект>/<slug>_data` переносятся скриптом `scripts/migrate_agent_data.py` (по умолчанию только показывает план, запись - с `--apply`), исходная папка при переносе не удаляется. Карточку владельца видят все сотрудники; её текст ограничен по объёму, а заметки самого сотрудника в промпт не вставляются - он читает их инструментом, когда они нужны.
- Сотрудники ищут по истории диалогов: `search_in_threads` (по умолчанию - текущий диалог, без предварительных списков; явный `thread_id`, охват по оркестратору или всем диалогам, период), `list_threads` и `read_thread`. DevAgent видит все диалоги, остальные сотрудники - только свои.
- Правки системного промпта встроенного сотрудника (DevAgent) сохраняются между перезапусками; вернуть поставляемый промпт можно кнопкой сброса на вкладке «Промпт».
- DevAgent - встроенный (неудаляемый) оркестратор, всегда доступен.
- Секция «Сотрудники» в сайдбаре: первые 5 всегда видны, остальные - в свёрнутом блоке «Все (N)»; поиск показывается только при количестве сотрудников больше пяти. Порядок - по времени последнего диалога (новые и недавно использованные сверху).
- В ленте чата у каждого завершённого текстового ответа сотрудника есть панель выгрузки/копирования (📥 MD / 📥 TXT и Copy MD / Copy TXT); ответы с вызовами инструментов панели не получают.

### ⏰ Запуск по расписанию

- Задача выполняется сотрудником в заданные моменты, без вашего участия: правило хранит агента, текст задачи, первый запуск и шаг - от минут до месяцев, - а также собственный часовой пояс.
- Исключения задаются маской: запрещённые дни недели, запрещённые периоды и тихие часы. Политика `skip` переносит точку на следующую разрешённую, `postpone` - сдвигает её на конец запрета; выбор виден в предпросмотре ближайших запусков ещё до сохранения.
- Одна точка выполняется не более одного раза: захват атомарен, перезапуск платформы не повторяет уже выполненное, а накопившиеся за простой пропуски фиксируются в истории как пропущенные (`missed`) вместо волны догоняющих запусков.
- Планировщик работает внутри процесса платформы: он выполняет расписания, пока приложение открыто, и завершается вместе с ним - отдельной службы нет. Страница честно показывает heartbeat: если время последнего тика устарело, расписания не сработают, и это видно до наступления срока.
- Каждый запуск - обычный диалог в «Истории» (без родительского диалога), поэтому видно, что именно сделал агент; карточка запуска ведёт в этот диалог. Запуск ограничен шагами, временем и, по желанию, бюджетом токенов; делегировать дальше он не может.
- Кнопка «Запустить сейчас» отвечает на вопрос «правильно ли настроено» одним настоящим запуском, не сдвигая сетку. Три неудачи подряд ставят правило на паузу, а причина остаётся на карточке; пауза и возобновление - в один клик.
- История запусков хранит статус, длительность и расход токенов; запуск, оборванный остановкой платформы, помечается как прерванный (`interrupted`) при следующем старте.

### 🧩 Помощники

- Создание, редактирование и удаление помощников (системных промптов) с привязкой файлов и подбором модели под сложность задачи.
- Assistant Creator - встроенный мета-инструмент: генерирует качественный системный промпт по описанию роли.
- Секция «Помощники» в сайдбаре: первые 5 всегда видны, остальные - в свёрнутом блоке «Все (N)»; поиск показывается только при количестве помощников больше пяти.

### 🔧 DevAgent - встроенный агент-разработчик

- Редактирование кода с утверждением изменений: каждое изменение предлагается и применяется контролируемо.
- Полностью автономный режим по вашему выбору. При готовом плане DevAgent спросит, следовать ли ему в точности или сначала проанализировать код; при подробном ТЗ - действовать ли без согласования. План всё равно составляется, но фаза утверждения пропускается и исполнение начинается сразу.
- Версионирование файлов (бэкапы), снапшоты проекта и полный откат.
- Регламентированный пайплайн тестирования: юнит-тесты, регрессия, сценарные тесты, саморевью.
- Внешняя память задач (`TASK_STATE.md`): план, прогресс, журналы анализа и открытых вопросов - для многоэтапных работ.
- Защита от path traversal (инструменты не выходят за пределы рабочей папки), санитизация и разметка недоверенных данных, эвристическая защита от prompt-injection.
- Работа с любым проектом: DevAgent строит карту проекта (`PROJECT_MAP.md`) и ведёт документацию (`AGENT.md` - ключевая информация для агентов, архитектура, changelog).
- Изоляция рабочей папки: новый диалог начинается без папки («папка не выбрана»), активная папка привязана к диалогу и восстанавливается при его открытии; меню недавних папок у каждого сотрудника своё.
- Блок «Выбор папки» в чате: «Авто», до 10 недавних папок и нативный выбор папки на компьютере отдельным пунктом селектора - кнопки рядом с полем ввода нет, чтобы её не путали со скрепкой загрузки файлов. Выбранная папка применяется автоматически при отправке сообщения (агент не тратит на это шаг), после чего селектор возвращается в «Авто», а активный путь виден под полем.
- Панель чата: веб-поиск и защита от prompt-injection. Экономный режим (компактный контекст) включён всегда и переключателя не имеет - он снижает расход токенов на длинных диалогах.
- Авто-прокрутка ленты чата: пока агент работает, лента следует за новым выводом; прокрутка вверх ставит слежение на паузу, возврат к низу - возобновляет; отправка сообщения прокручивает вниз.
- Загрузка файлов прямо в поле ввода чата: иконка-скрепка с подсказкой, без отдельного блока и подписи; файлы уходят вместе с текстом одной отправкой.

### 📚 Базы знаний (RAG)

- Локальные базы знаний с тремя режимами поиска: **bm25** (собственный полезависимый лексический индекс BM25F, без API-ключей, режим по умолчанию), **vector** (семантический поиск по эмбеддингам) и **hybrid** (объединение через RRF); загрузка документов, автоматическая индексация (чанкинг + BM25; эмбеддинги - в режимах vector/hybrid). В режиме bm25 тело чанка и его контекстная шапка (продукт, заголовок, раздел) индексируются как отдельные поля: термин из шапки помогает найти нужный продукт или раздел и не «забивает» ранжирование.
- Страница «Хранилище»: создание баз, файлы, индексация, тестовый поиск и переключение режима поиска. DevAgent и сотрудники обращаются к базам напрямую; результаты поиска несут идентификаторы чанков, а инструмент добора (`rag_get_chunks`) возвращает соседние фрагменты для восстановления полного контекста.

### 🛒 Маркетплейс сущностей

- Пункт меню «🛒 Маркетплейс» (блок **МАРКЕТПЛЕЙС** в боковом меню): витрина каталога с поиском, карточкой сущности (лицензия, требуемые инструменты, совместимость платформы) и установкой в один клик. Пять подразделов - сотрудники, помощники, навыки, базы знаний, коннекторы - работают и как вкладки витрины, и как пункты меню: клик в меню открывает витрину на нужной вкладке, а выбранная вкладка подсвечивает соответствующий пункт. Сотрудники и помощники делят один тип `agent`, но показаны разными списками: они ставятся в разные места, и общий список смешивал бы два разных продукта. Каталог читается только по нажатию кнопки - старт приложения остаётся офлайновым.
- Устанавливаются четыре типа: навык, агент, база знаний и MCP-сервер. Агент бывает двух видов - сотрудник (папка оркестратора с мержем конфига, инструкциями и функциями) и помощник (папка помощника с манифестом, промптом и текстовыми вложениями); карточка витрины подписывает вид, чтобы до установки было ясно, что появится. База знаний ставится манифестом, источниками и индексом с проверкой `index_sha256`/`index_schema` и атомарной заменой папки, а MCP-сервер - подключением без секретов, которое ждёт заполнения учётных данных на странице «Коннекторы».
- Рекомендуемый пакет вынесен в блок «Дополнительно» карточки: каждая позиция подписана человеческим названием типа (агент, навык, база знаний, коннектор) и своим состоянием, галочки стоят по признаку «выбрано по умолчанию», а позиции, которые нельзя поставить сейчас, остаются в списке неактивными - намерение набора видно целиком. Установка набора ставит отмеченное целиком: если поздний член не установился, уже поставленные откатываются. После установки набора с коннектором карточка напоминает, что учётные данные заполняются на странице «Коннекторы».
- Кнопка установки на карточке одна: «Установить» ставит и саму сущность, и отмеченные позиции набора за одно нажатие. У уже установленной сущности та же кнопка доставляет только отмеченное. Раскрытая карточка остаётся раскрытой после нажатия, поэтому результат виден сразу: сообщение об установке и обновлённое состояние карточки.
- Установка пишет журнал прогона до изменения файлов, сверяет sha256 пакета и переносит результат атомарно; прерванный запуск восстанавливается на холодном старте, поэтому установка не оставляет половину файлов.
- Локальные правки не теряются: правка установленной сущности определяется сравнением с записанным манифестом, а не по времени файла. При конфликте предлагаются три пути - оставить свою версию, взять версию каталога (с бэкапом заменяемых файлов) или сделать форк под новым именем. У помощника при обновлении сохраняются добавленные пользователем вложения, а отредактированный промпт не перезаписывается каталогом.
- Обновления - на странице «Обновления», в разделе маркетплейса: проверка версий по всем четырём типам, установка с той же политикой конфликтов и отказ по отдельной сущности, не отменяющий остальные (несовместимая платформа, требование исполняемого кода при закрытом `allow_code`, непринятая лицензия). Ссылка на сущность принимается и как `type:id`, и как голый id.
- Журнал прогонов с кнопкой «Отменить этот прогон»: откат восстанавливает файлы, строку реестра и `skills.json` байт в байт. Журнал ограничен - 20 записей для навыков и 3 для баз знаний.
- Удаление ставит маркер, поэтому встроенный импорт не воскрешает удалённое при следующем старте. Раздел целиком скрывается выключателем `marketplace.enabled`.
- Встроенный навык Rag Base Creator ставится сразу при первом запуске и остаётся доступен без каталога: встроенная копия занимает ту же папку, что и каталожная, поэтому витрина показывает её как установленную, а не предлагает вторую.

### 🌐 HTTP API v1

Платформу можно встроить в другую систему, не работая через браузер:
HTTP API v1 повторяет возможности страницы чата - список сотрудников и
помощников, запуск диалога, поллинг прогона с длинным ожиданием, отмена,
чтение сообщений треда.

- Аутентификация - Bearer-токен (`core/api_token_store.py`), сравнение
  постоянного времени, троттлинг неудачных попыток.
- Ошибки приходят единым конвертом `code` / `message` / `details` с
  осмысленным HTTP-статусом.
- API живёт в отдельном процессе и не требует Streamlit: зависимости
  ставятся из `requirements.lock` либо группой `api` пакета
  (`pip install -e ".[api]"`), затем запуск через
  `core/gateway_launcher.py`.
- Тот же процесс можно ограничить списком разрешённых `Host`
  (защита от DNS-rebinding) и закрыть автоматическую документацию.

Контракт запуска у API и UI общий (`core/gateway/`), поэтому ответ на
один и тот же запрос совпадает независимо от транспорта. Форма ответа
объявлена моделями, а не собирается по ключам на каждой стороне, поэтому
пропущенное или переименованное поле становится отказом теста, а не
сюрпризом для клиента; точный публичный JSON зафиксирован golden-тестами
и меняется только вместе со снимком в диффе.

### ⌨ Консоль sagaai

Третий равноправный вход в платформу - для сервера без браузера,
cron-задачи, CI и первичной настройки. После установки пакета
(`pip install -e .`) команда доступна напрямую: `sagaai --help`.

Без установки работают и оба запасных пути: `python -m sagaai --help` из
корня копии и `./bin/sagaai --help` - лаунчер добавляет корень копии в
`sys.path` сам.

| Команда | Что делает |
| --- | --- |
| `sagaai run --agent <slug> --task "..."` | даёт задачу сотруднику и ждёт результат |
| `sagaai doctor` | диагностирует установку, ничего не меняя |
| `sagaai agents` | список сотрудников и их slug'ов |
| `sagaai token create/list/revoke` | выдаёт и отзывает Bearer-токены для HTTP API |
| `sagaai update check/stage/apply/rollback` | конвейер обновлений, в том числе из локального зеркала |
| `sagaai backup create/list/restore` | снимки баз с проверкой целостности и страховкой при восстановлении |
| `sagaai migrate` | миграции баз со снимком до, откатом при сбое и проверкой целостности после |
| `sagaai ui` / `sagaai serve` | запускают интерфейс / HTTP API отдельными процессами |

- Консоль не импортирует Streamlit и HTTP-стек: на сервере без них работают
  все команды, кроме запуска самого интерфейса.
- `--json` печатает ровно один объект на stdout - `ok`, `command`,
  `exit_code`, `version` и `data` при успехе либо `error` с полями `code`,
  `message`, `hint`; прогресс идёт в stderr, поэтому результат удобно
  разбирать скриптом.
- Коды возврата: `0` успех, `1` операция не удалась, `2` ошибка
  конфигурации или запроса, `3` конфликт (платформа уже запущена, запуск ещё
  идёт).
- Разрушительные команды требуют подтверждения: в терминале - вопрос `y/N`,
  в скрипте - флаг `--yes` (иначе отказ с кодом 2). Пока платформа
  запущена, замена файлов и восстановление баз отказывают с кодом 3.
- Пауза запуска (план на утверждение, вопрос агента) - это результат с кодом
  0 и описанием паузы, а не ошибка; истёкшее ожидание даёт код 3 и run id,
  не отменяя работу.

```bash
python -m sagaai run --agent dev_agent --task "Проверь README на опечатки" --json
```

### 🔗 Коннекторы

- Подключение внешних сервисов (GitHub, SSH, MCP) с хранением токенов и ключей в защищённом виде.
- Создание подключения через DevAgent прямо в чате: сначала черновик без секретов, затем заполнение учётных данных на странице «Коннекторы». У каждого подключения есть файл памяти агента (заметки о сервере и лимитах - без секретов).
- Готовые пресеты MCP-серверов без секретов на отдельной вкладке «MCP-серверы»: плитка с иконкой «ВкусВилл» открывает форму подключения с уже заполненной конфигурацией сервера, где остаётся ввести токен; рядом - плитка «Свой MCP-сервер» для любого stdio/http-сервера. Работа с GitHub идёт через отдельное подключение «GitHub» (`github_rest`), которому нужен обычный Personal Access Token. Поддерживаются оба транспорта MCP - локальный stdio и удалённый HTTP.
- Страница «Коннекторы» построена как «список ↔ форма»: клик по плитке сервиса или пресета открывает форму на той же странице, и подключение появляется в списке только после нажатия «Создать» - сразу рабочее, с введёнными учётными данными. «Отмена» и «← Назад» возвращают к списку, ничего не создавая; редактирование открывается такой же формой на всю страницу. Три вкладки - «Общие сервисы» (плитки GitHub/SSH), «MCP-серверы» и «Подключения» (карточки всех сохранённых подключений с иконкой сервиса, состоянием учётных данных, проверкой, редактированием и удалением); выбранная вкладка не сбрасывается при кликах и сохранениях.

### 📎 Файлы в диалогах

- В диалоги оркестраторов загружаются файлы любого формата (до 100 МиБ на файл); агент сам решает, когда и как извлекать содержимое.

### 🔄 Обновления платформы

- Встроенный конвейер обновлений через публичный GitHub-репозиторий без токена: проверка, выборочная установка (файлы - по отдельности, пакеты кода - целиком), просмотр и откат.
- Применение только при холодном старте, каждый файл бэкапится, запись атомарная, сбой откатывается.

### 📊 Статистика

- Страница «Статистика»: расход токенов по периодам, поставщикам и моделям на основе диалогов помощников и сотрудников.

### 🛡️ Защита данных

- Страница «Доступы»: вход по паролю, интервал повторного запроса; во время выполнения задачи оркестратором авторизация не запрашивается.
- Персональная память лежит в `DATA_DIR/personal/`, рабочие данные сотрудников - в `DATA_DIR/agents_data/`; обе папки исключены из git (`.gitignore`), поэтому заметки не попадают ни в экспорт сотрудника, ни в репозиторий проекта. Запись проверяется на учётные данные - текст, похожий на токен или ключ, отклоняется, а сообщение об ошибке не повторяет найденный фрагмент.
- TLS-верификация включена по умолчанию; API-ключи хранятся в защищённом виде (или задаются через переменные окружения и не сохраняются в БД); секреты не отображаются в интерфейсе.

### 🎨 Интерфейс

- Темы оформления: светлая, тёмная, системная. Интерфейс на русском, английском и китайском языках.
- Единая «История» всех диалогов с фильтрами и поиском.
- Боковое меню собрано из четырёх блоков. **СОТРУДНИКИ** и **ПОМОЩНИКИ** показывают первые пять позиций, остальные прячутся в свёрнутом блоке «Все (N)». **МАРКЕТПЛЕЙС** раскрывает каталог пятью подразделами - сотрудники, помощники, навыки, базы знаний, коннекторы, - и клик по подразделу открывает витрину сразу на нужной вкладке, а выбранная вкладка подсвечивает пункт меню обратно. **НАСТРОЙКИ** держат три постоянных пункта (Провайдеры, Коннекторы, Обновления), остальные восемь собраны в свёрнутом «Ещё (8)», чтобы редкие страницы не занимали место в каждом сеансе.

## 📦 Быстрый старт

### ✅ Требования

- **Python 3.12 или новее.** Проверьте командой `python --version` (на Windows также подойдёт `py --version`). Если Python не установлен, скачайте его с [python.org](https://www.python.org/downloads/); при установке на Windows отметьте пункт **«Add Python to PATH»**.
- **Зависимости из `requirements.lock`** (включая **Streamlit 1.66.0 или новее**). Lock-файл фиксирует точные версии и их хэши - именно этот набор проверен тестами, поэтому установка из него воспроизводима на любой машине. При первом запуске приложение само проверяет установленные библиотеки и их версии: если чего-то не хватает или версия устарела, появится предупреждение с нужной командой - выполните её для стабильной работы платформы.

### 🪟 Windows (WSL не требуется)

1. **Скачайте репозиторий (Git не обязателен).** Страница репозитория → **Code → Download ZIP** → распакуйте архив в удобную папку. Либо клонируйте: `git clone https://github.com/TVD2100/sagaai-platform SagaAI`.

2. **Откройте терминал в папке проекта.** Зайдите в папку, затем Shift + правая кнопка мыши по пустому месту → «Открыть окно PowerShell здесь».

3. **Установите зависимости:** `pip install -r requirements.lock`.

4. **Запустите приложение:** `streamlit run app.py` и откройте [http://localhost:8501](http://localhost:8501/).

### 🐧 macOS / Linux

1. **Клонируйте репозиторий:** `git clone https://github.com/TVD2100/sagaai-platform SagaAI`, затем `cd SagaAI`.

2. **Установите зависимости:** `pip install -r requirements.lock`.

3. **Запустите приложение:** `streamlit run app.py` и откройте [http://localhost:8501](http://localhost:8501/).

4. **Задайте API-ключи** нужных AI-сервисов на странице «Настройки» - после этого можно создавать помощников, сотрудников и базы знаний.

> 💡 Если команда `streamlit` не найдена, запускайте через модуль Python: `python -m streamlit run app.py`.

### 🛠 Установка пакета и разработка

Шаги выше запускают платформу из копии и не ставят консольную команду.
Полная установка - та же последовательность плюс сам пакет:

```bash
pip install -r requirements.lock
pip install -e .
sagaai --version      # печатает версию платформы, например 2.37.0
```

- **Установка только в режиме `-e` (editable).** Платформа вычисляет каталоги
  данных (`defaults/`, `langs/`, `services/`, базы) от корня копии. Режим `-e`
  сохраняет это соответствие, обычная установка из wheel - нет.
- **`requirements.lock` - единственный источник версий** для установки.
  `requirements.txt` и `requirements-api.txt` описывают допустимые пределы
  версий и служат входом для пересборки lock.
- **Обновить lock после правки пределов:**

  ```bash
  pip install pip-tools
  pip-compile --generate-hashes -o requirements.lock \
      requirements.txt requirements-api.txt
  ```

  Пересобирать lock нужно под Python 3.12 - под ту же версию, на которой
  работает CI: `pip-compile` резолвит под свой собственный интерпретатор.
- **Проверить всё локально одной командой:** `python scripts/ci_check.py`.
  Она же выполняется в CI, поэтому зелёный локальный прогон и зелёный CI
  означают одно и то же.
- **Если установка из lock падает с `Could not find a version that
  satisfies the requirement`** при живой версии на PyPI, дело обычно в
  повреждённом кэше pip, а не в lock: повторите установку с
  `--no-cache-dir`.
- **Опциональные группы** ставятся как `pip install -e ".[api]"` (также
  `documents`, `selenium`, `ssh`, `dev`); полный набор для разработки -
  `pip install -e ".[api,documents,selenium,ssh,dev]"`.

## 🔐 Настройка безопасности

### Включение защиты паролем

**Способ 1 - страница «Доступы» (рекомендуется):** в боковом меню «🔐 Доступы» включите «Доступ по паролю», задайте пароль и подтверждение, настройте интервал повторного запроса и нажмите «Сохранить». Пароль хранится в БД в зашифрованном виде (Fernet).

**Способ 2 - переменная окружения** `SAGAAI_AUTH_PASSWORD`.

После включения интерфейс показывает форму входа. Пароль из формы имеет приоритет перед переменной окружения; при выключенном переключателе на странице «Доступы» пароль не запрашивается.

### TLS-верификация

По умолчанию все HTTPS-запросы к AI-сервисам проверяют сертификаты (`verify=True`). Отключать проверку не рекомендуется: без неё возможна MITM-атака с перехватом API-ключей и содержимого диалогов. При необходимости (корпоративный прокси, самоподписанный CA) есть два штатных способа.

**Свой CA-бандл.** Переменная `SAGAAI_GIGACHAT_CA_BUNDLE` задаёт путь к PEM-файлу с корневым сертификатом для запросов к GigaChat. По умолчанию используется встроенный `certs/russian_trusted_root_ca.pem` - Russian Trusted Root CA, которым подписаны эндпоинты GigaChat (этого корня нет в стандартном бандле `certifi`).

```
export SAGAAI_GIGACHAT_CA_BUNDLE=/path/to/corporate_ca.pem
streamlit run app.py
```

**Полное отключение проверки (крайняя мера).** Переменная `SAGAAI_VERIFY_TLS=false` отключает TLS-верификацию для всех запросов к AI-сервисам. Используйте только в доверенной сети.

| Пакет | Назначение |
| --- | --- |

**AI-провайдеры:** OpenAI-совместимые API (YandexAI, DeepSeek), GigaChat; веб-поиск DeepSeek - через Anthropic-совместимый endpoint (модель deepseek-flash).

**Обновления:** версии и хеши всех поставляемых файлов ведёт манифест `file_versions.json`; конвейер обновлений доставляет их пользователям через публичный GitHub-репозиторий без токена. Обновления применяются при холодном старте, с бэкапом и откатом при сбое.

**Тесты:** `python3 -m pytest` - полный регрессионный набор. Статический анализ: `python3 -m ruff check` (настройки в `ruff.toml`) и `pyright` в режиме `basic` (настройки в `pyproject.toml`), где предел числа находок задан в `pyright_budget.json`: он может падать, но не расти.

**Непрерывная интеграция:** все ворот качества собраны в одном скрипте - `python3 scripts/ci_check.py` проверяет линтер по `ruff.toml`, типы против бюджета находок, структурный бюджет крупных файлов, манифест версий, согласованность объявленных зависимостей с lock-файлом и прогоняет весь набор тестов одним процессом. Тот же скрипт вызывает GitHub Actions на каждый пуш в `main` и на каждый pull request (`.github/workflows/ci.yml`), поэтому локальный и серверный прогон не могут разойтись; `--only <проверка>` запускает подмножество, `--list` печатает имена проверок.
