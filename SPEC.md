# Спецификация требований (SPEC)

Документ поддерживается DevAgent и редактируется пользователем.

## Назначение системы

SagaAI - универсальный AI-ассистент с веб-интерфейсом на базе Streamlit.
Приложение позволяет:
- вести диалог с большими языковыми моделями (OpenAI-совместимые API и GigaChat);
- управлять **помощниками** (system-промптами) - создавать, редактировать,
  удалять, прикреплять к ним файлы;
- переключаться между несколькими языками интерфейса;
- просматривать историю чатов и управлять тредами;
- безопасно редактировать код через **DevAgent** - встроенного разработчика с
  автоматическими бэкапами и контролем изменений;
- в режиме **универсального разработчика** работать с любым сторонним
  проектом, лежащим в отдельной папке, - DevAgent анализирует проект, ведёт
  документацию, создаёт снапшоты и применяет изменения после явного
  утверждения пользователем (либо сразу после плана, если пользователь
  явно выбрал полностью автономный режим без согласования);
- создавать и использовать **оркестраторы** (автономных AI-агентов, в UI
  называемых сотрудниками) на принципах DevAgent, заточенных под узкие
  задачи, с собственными настройками (модели, системный промпт,
  инструменты, инструкции, функции);
- создавать и использовать **базы знаний (RAG)** - хранить документы в
  локальных базах, индексировать их эмбеддингами и искать релевантные
  фрагменты при ответе на запросы;
- получать **обновления платформы** через встроенный конвейер обновлений
  (манифест версий, проверка/загрузка/применение без токена, выборочная
  установка, бэкап и откат);
- управлять **доступом к приложению** на странице «Доступы» (доступ по
  паролю: пароль из формы каноничен, `SAGAAI_AUTH_PASSWORD` - запасной
  источник, интервал повторного запроса).

## Функциональные требования

### FR1 - Чат с AI-моделью
- Пользователь выбирает Помощник (или оставляет стандартный) и вводит
  запрос.
- Поддерживается прикрепление файлов (текстовых, PDF, офисных форматов) -
  их содержимое добавляется в контекст.
- Ответ модели рендерится в виде Markdown с подсветкой кода и кнопкой
  копирования.
- Возможность создать новый диалог в любой момент.

### FR2 - Управление помощниками
- Создание помощника: имя, описание, системный промпт, опциональные файлы.
- Редактирование и удаление существующих помощников.
- Файлы помощника хранятся на диске и прикрепляются к контексту при вызове.
- Помощники сортируются по времени последнего использования в связанных
  тредах.
- Секция «Помощники» в сайдбаре: первые 5 позиций всегда видимы,
  остальные - в свёрнутом блоке «Все (N)»; поле поиска отображается
  только при количестве помощников > 5.
- При создании помощника автоматически подбирается подходящий сервис и
  модель (модуль `assistant_model_resolver`): классификация сложности и
  необходимости web_search; без веб-поиска используется основная модель
  из настроек оркестратора, с веб-поиском - модель YandexAI (pro/lite по
  сложности).
- Промпт помощника можно улучшить автоматически: сервис `prompt_improver`
  использует основную модель DevAgent и инструкцию `prompt_improver` для
  генерации улучшенной версии промпта.

### FR3 - Многоязычность
- Интерфейс переводится через JSON-файлы (`langs/en.json`, `langs/ru.json`,
  `langs/zh-CN.json`); канонические копии хранятся в `defaults/langs/`.
- Язык выбирается в боковой панели; сохраняется в настройках.
- Функция `t()` в `core/i18n.py` обеспечивает двухуровневый fallback:
  1. Если перевод отсутствует в выбранном языке, берётся значение из
     английского файла (`en.json`) - канонического источника всех ключей.
  2. Если ключ отсутствует и в английском файле, возвращается сам ключ.
- **Английский файл (`en.json`) всегда должен содержать актуальный полный
  набор ключей.** Остальные языковые файлы могут отставать - недостающие
  строки автоматически подтягиваются из английского.

### FR4 - История чатов
- Все диалоги сохраняются в виде тредов с привязкой к помощнику.
- Список тредов доступен на странице истории; каждый тред можно открыть,
  удалить, либо удалить все треды сразу.
- Метаданные треда и сообщения хранятся в SQLite.
- Диалоги оркестраторов хранятся отдельно (БД `devagent.db`) и доступны на
  вкладке «История» соответствующей страницы оркестратора.
- Файлы, загруженные пользователем в диалог оркестратора, сохраняются как
  сырые байты в `history/<tid>/files` (единый источник вложений диалога;
  платформа не извлекает их содержимое).

### FR5 - Настройки
- Конфигурация API-ключей: endpoint, ключ, модель, температура.
- Возможность протестировать соединение до сохранения.
- Настройки сохраняются в конфигурационном хранилище (SQLite KV).
- Встроенные настройки DevAgent (основная модель, опциональные модели
  распознавания и генерации изображений, поисковая модель, температуры,
  системный промпт, эконом-режим, инструкции) живут на
  странице самого оркестратора - Настройки → Модели / Промпт /
  Эконом-режим / Инструкции.
- Страница «Настройки» в общем меню содержит только API-ключи и переменные
  окружения.

### FR6 - Оркестраторы (сотрудники)
- **Оркестратор** - автономный AI-агент (как DevAgent) со своим системным
  промптом, конфигурацией моделей, эконом-режимом, набором инструментов,
  инструкциями и пользовательскими функциями. В UI оркестраторы
  называются сотрудниками.
- Каждый оркестратор отображается **отдельной страницей в общем меню**
  (сайдбаре). DevAgent - встроенный оркестратор (slug `dev_agent`,
  `is_builtin=True`), всегда доступен и не может быть удалён.
- Секция «Сотрудники» в сайдбаре: первые 5 позиций всегда видимы,
  остальные - в свёрнутом блоке «Все (N)»; поле поиска отображается
  только при количестве сотрудников > 5.
- Порядок сотрудников стабилен между перезапусками и определяется
  активностью: по времени последнего диалога (последний тред в
  `devagent.db`), а при его отсутствии - по времени создания; новый
  сотрудник появляется вверху списка.
- Страница оркестратора содержит вкладки: **Чат**, **История** и
  **Навыки**; ссылка на отдельную страницу **Настройки**.
- Настройки моделей - сервис + модель + температура: основная модель
  используется на всех шагах; опционально назначаются модели
  распознавания и генерации изображений (по умолчанию не назначены);
  поисковая модель - для задач с веб-поиском (диапазон температуры
  определяется из файла описания сервиса).
- Системный промпт оркестратора редактируется в отдельной вкладке.
- К системному промпту каждого оркестратора при построении добавляется
  англоязычный блок `## Available tools` - перечень доступных инструментов
  (системные, workspace, инструменты включённых подключений, кастомные
  функции) с краткими правилами вызова. Каноничные промпты встроенных
  оркестраторов (`dev_agent/system_prompt.md`, YaAgent) не дублируют
  справочник таблицами инструментов: они ссылаются на автоматический
  блок и содержат только собственные правила использования.
- В настройках оркестратора (вкладка «Функции») системные функции показаны
  с чекбоксами включения/выключения; выбор сохраняется в
  `config['disabled_tools']`.
- Отключённые инструменты исключаются из промпта и реально блокируются
  диспетчером при вызове (ошибка `disabled: true` до выполнения;
  legacy-алиасы учитываются в обе стороны).
- Назначенные модели изображений используются системными инструментами
  `analyze_image` (распознавание: файлы проекта и вложения диалога; сервис
  объявляет каталог `vision_models`: YandexAI - `qwen3.6-35b-a3b` и
  `deepseek-v4.1-flash`, DeepSeek - `deepseek-flash` через выделенный
  chat/completions endpoint `vision_base_url` с `detail="original"`) и
  `generate_image` (генерация: синхронный OpenAI-совместимый Images API
  YandexAI, модель `aliceai-image-art-3.0`; результат сохраняется файлом -
  в workspace или в папке файлов диалога, base64 не возвращается - и
  сразу показывается в ленте чата (вне свёрнутого блока результата
  инструмента) с кнопкой скачивания); при незаданной
  модели возвращается ошибка `not_assigned` с подсказкой, где назначить
  модель (глобальная инструкция `multimodal_mode`).
- Эконом-режим настраивается отдельно для каждого оркестратора (tail
  messages, кэш-режим).
- Строка токенов в ленте чата собирает честный кэш-бакет провайдера на
  всех транспортах (bearer/DeepSeek - `prompt_tokens_details.cached_tokens`
  с фолбэком `prompt_cache_hit_tokens`, GigaChat - `precached_prompt_tokens`,
  Responses - `input_tokens_details.cached_tokens`); метки строки
  локализованы (`token_line_*` во всех языковых файлах), а кэш строки
  учитывает язык интерфейса.
- Инструкции оркестратора хранятся в папке оркестратора
  (`orchestrators/<slug>/instructions.json` и `*.md`) и управляются со
  страницы оркестратора.
- **Экспорт/импорт** реализован на уровне core API
  (`core.orchestrators.export_orchestrator` / `import_orchestrator`, формат
  `sagaai_orchestrator/v1`). **UI для экспорта/импорта оркестраторов
  намеренно отложен** - в интерфейсе соответствующие кнопки отсутствуют.
- При импорте с конфликтом slug генерируется новый (`slug_2`, `slug_3`,
  …); инструкции импортируются без перезаписи существующих (по id).
- Страница чата оркестратора имеет дублированную панель инструментов
  (сверху и снизу): web-поиск, эконом-режим, safety-режим, «Настройки»,
  «Новый диалог», «Копировать URL». Чекбоксы обеих панелей синхронизированы
  двусторонне (позиционные ключи виджетов, каноническое значение в
  session_state и персистентность в конфиге оркестратора).
- Кнопка «Копировать URL» формирует deep-link вида
  `?orchestrator=<slug>&thread=<tid>` (thread опционален). При открытии
  приложения с таким параметром `ui/app.py` загружает указанный диалог
  (или начинает новый), переключает страницу и убирает параметры из URL
  (обработка идемпотентна).
- Лента чата показывает панель выгрузки/копирования (кнопки **📥 MD / 📥 TXT** и **Copy MD / Copy TXT**) у каждого текстового ответа ассистента без вызовов инструментов, а не только у финального; сообщения с распознанными вызовами инструментов панели не получают, даже если содержат видимый текст, а у «живого» финального ответа панель скрыта до завершения цикла агента (`ui/pages/orchestrator.py`).
- Системный промпт встроенного `dev_agent` автоматически обновляется из
  единственного источника `dev_agent/system_prompt.md` при каждом старте
  приложения (отдельная копия в `defaults/` не поддерживается).
- Чат оркестратора принимает вложения **любого формата** (без фильтра
  типов): при отправке байты сохраняются в `history/<tid>/files`, в
  сообщение агента добавляется уведомление со списком файлов, а в
  персистентный префикс каждого запроса - тот же список. Платформа не
  парсит содержимое; агент сам решает, когда и как его извлечь
  (инструменты `list_thread_files` / `read_thread_file`, бинарные форматы -
  через `run_code`). Лимит одного файла - 100 МиБ.
- **Поиск по диалогам:** инструменты `search_in_threads` (поиск по
  сообщениям; по умолчанию - текущий диалог, без предварительных
  листингов; явный `thread_id` работает без списков; `scope` по
  оркестратору(ам) или всем диалогам; период по дате активности; regex;
  фильтр по роли), `list_threads` (список диалогов с пагинацией и
  счётчиками сообщений) и `read_thread` (окно сообщений с абсолютными
  индексами; по умолчанию - текущий диалог). Скрытые служебные сообщения
  (`tool_result` / `AUTO_CONTINUE`) по умолчанию исключаются из поиска и
  чтения. Контроль доступа: DevAgent видит все диалоги, остальные
  оркестраторы - только свои (чужие `thread_id` получают `Access denied`).
- **Прозрачные ретраи при обрывах связи:** LLM-запросы оркестраторов
  автоматически повторяются при `RequestTimeoutError` / `NetworkError` -
  пауза между попытками `SAGAAI_NETWORK_RETRY_DELAY` (по умолчанию 30 с),
  максимум `SAGAAI_NETWORK_RETRY_ATTEMPTS` попыток подряд (по умолчанию 3);
  в ленту чата добавляется событие `retrying_llm` (i18n-ключ
  `orch_retry_llm`). Сообщение пользователя сохраняется в историю ДО
  вызова модели, поэтому диалог не теряется даже после исчерпания всех
  попыток (`core/api_layer.py`, `core/assistant_tools.py`,
  `dev_agent/agent_loop.py`, `ui/pages/orchestrator.py`).
- **Ошибки Responses API не маскируются под пустой ответ.** Тело HTTP 200
  со статусом `failed` и/или объектом `error` (Yandex AI Studio, DeepSeek)
  поднимается как `ProviderResponseError` с кодом и текстом провайдера
  вместо молчаливого пустого ответа; то же касается native function-цикла
  ассистентов и проверки соединения в настройках (`(False, <текст>)`
  вместо OK). Пустые и whitespace-only сообщения истории исключаются из
  `input` запроса - каскад HTTP 400 «Content of input is empty» после
  сохранённого пустого ответа устранён (`core/api_layer.py`,
  `core/assistant_tools.py`, `core/api_errors.py`).


### FR7 - DevAgent (встроенный разработчик)
- DevAgent - встроенный оркестратор с slug `dev_agent`, работает как
  универсальный разработчик.
- Страница DevAgent - это `ui/pages/orchestrator.py` с вкладками
  Чат / История / Навыки и отдельной страницей Настройки
  (`ui/pages/orchestrator_settings.py`).
- Настройки моделей и промпта доступны на странице DevAgent → Настройки.
- Агент использует единую основную модель на всех шагах: служебная
  классификация шага (`classify_step_strength`) сохраняется для
  журналирования, но модель не переключает.
- Агент предлагает изменения как полную перезапись файла (`propose_file`)
  либо точечные правки (`apply_patch`); в автономном режиме изменения
  применяются после утверждения плана, в ручном - после явного одобрения
  пользователем. Если пользователь передал готовый план (в том числе
  файлом), агент один раз уточняет, следовать ли плану в точности или
  сначала проанализировать код; при выборе «следовать в точности» план
  пользователя записывается в журнал задачи дословно и исполняется без
  фазы утверждения. Если передан подробный план, спецификация или ТЗ без
  требования точного следования, агент спрашивает, действовать ли
  полностью автономно или согласовать итоговый план после анализа; при
  явном выборе «без согласования» план всё равно составляется, но фаза
  утверждения пропускается и исполнение начинается сразу.
- Все изменения автоматически бэкапятся; возможен откат как отдельных
  файлов, так и всей кодовой базы (снапшоты).
- Для сложных многоэтапных задач агент ведёт внешнюю память
  `TASK_STATE.md` (архитектура, план, прогресс, handoff); инъекция
  журнала бюджетирована, восстановление состояния - по компактному
  дайджесту (`task_state_read(compact=True)`), полное чтение - по
  требованию.
- Агент может отправлять **несколько независимых вызовов инструментов
  в одном сообщении (батч)**: раннер парсит каждый фенс-блок, выполняет
  вызовы по порядку и возвращает все результаты вместе одним сообщением;
  батчить разрешено только независимые вызовы (нет общего файла-адресата,
  нет зависимости от результатов соседнего вызова, нет вызовов с
  подтверждением; записи - по одной до подтверждения авто-применения).
  Если часть блоков батча не распарсилась, валидные вызовы исполняются,
  а к результатам добавляется предупреждение `partial_batch` с
  диагностикой по каждому сломанному блоку (включая `TRUNCATED` и
  несбалансированные скобки/строки).
- Цикл агента защищён от зацикливания: счётчик отказов по инструменту
  (без учёта аргументов) после трёх подряд неудачных вызовов одной
  функции добавляет подсказку сменить инструмент по fallback-цепочке
  (вплоть до `run_code`), успех сбрасывает счётчик; поток одинаковых
  вызовов в одном сообщении схлопывается в одну компактную ошибку
  `identical_blocks`/`identical_calls` без диспатча.

### FR8 - Универсальный разработчик
- Возможность переключения рабочей папки на любой внешний проект.
- Изоляция рабочей папки между параллельными диалогами: активная папка
  привязана к потоку диалога (thread_id), а не к глобальному состоянию
  процесса; переключение папки в одном диалоге не влияет на другие
  параллельные диалоги. Привязка сохраняется в БД и восстанавливается
  при повторном открытии диалога, в том числе после перезапуска.
- **Пустое состояние «папка не выбрана»:** новый или сброшенный диалог
  стартует без папки - файловые инструменты отвечают структурной ошибкой
  `workspace_not_selected` с подсказкой выбрать папку, а `run_code`/`run_test`
  с `code=` выполняются с нейтральным cwd; после выбора папки состояние
  снимается.
- **«Последняя папка» треда:** путь хранится в мете треда
  (`workspace`/`target_file`; `NULL` - пустое состояние) и восстанавливается
  при открытии диалога; диалог без папки или с исчезнувшей папкой
  открывается пустым и не наследует папку соседнего диалога. Одноразовая
  миграция очищает легаси-мету тредов остальных оркестраторов, указывающую
  на платформенные корни.
- **Недавние папки** скоупятся по оркестратору: у каждого сотрудника своё
  меню; пути платформенной установки не показываются другим оркестраторам.
- **Журналы задач и вложения диалога** при пустой папке живут в папке
  диалога (`history/<tid>/`) и не пишутся в чужие проекты.
- Автоматическое построение карты проекта (`PROJECT_MAP.md`), ведение
  `SPEC.md`, `ARCHITECTURE.md` и журнала изменений.
- Агент работает с выбранной папкой как с собственной кодовой базой,
  применяя все правила безопасности DevAgent.
- Инструмент поиска `search_in_files` сканирует текстовые файлы проекта
  (по умолчанию типовые текстовые расширения); явный список `extensions`
  переопределяет набор по умолчанию, что позволяет искать в `.csv`,
  `.xml`, `.log` и т.п. Поиск регистронезависимый, лимит результатов -
  100 (c `truncated: true` при достижении). Файлы в иных кодировках
  декодируются через UTF-8→cp1251 fallback; нечитаемые и слишком большие
  файлы пропускаются и учитываются счётчиками `files_unreadable` /
  `files_skipped_large`.

### FR9 - Создание помощников
- Динамическое обнаружение помощников (assistant detection) **отключено**.
  `detect_and_select_assistant()` всегда возвращает пустой результат.
- Создание помощника происходит только по **явному запросу пользователя**
  (например, «Создай Помощник проверки орфографии»).
- Для создания помощника DevAgent вызывает `create_assistant_for_task()`,
  который использует **Assistant Creator** (id: `assistant_creator`).
- Assistant Creator - **внутренняя инструкция** DevAgent-оркестратора
  (хранится в `defaults/orchestrators/dev_agent/instructions/assistant_creator.md`
  и рантайм-копии `orchestrators/dev_agent/instructions/`), не является
  пользовательским помощником. Его промпт определяет строгие критерии
  качества для генерации новых помощников.
- Перед созданием помощника `assistant_model_resolver` классифицирует
  задачу:
  - Определяет сложность (только для выбора pro/lite при веб-поиске).
  - Определяет необходимость web_search.
  - Подбирает подходящий сервис и модель:
    - Если явно указаны в запросе - используются они.
    - Если web_search не нужен - основная модель из настроек оркестратора.
    - Если web_search нужен - из YandexAI (pro/lite модель по сложности).
    - Иначе - первый доступный сервис с ключом.
- Новый Помощник сохраняется в БД и становится доступен для последующего
  использования.

### FR10 - Базы знаний (RAG)
- Пользователь может создавать **базы знаний** (RAG) - локальные хранилища
  документов с векторным индексом.
- База знаний хранится в папке данных (`DATA_DIR/rag_bases/<slug>/`):
  `manifest.json`, файлы документов, локальный SQLite-индекс `index.db`.
- Страница **«Хранилище»** (`ui/pages/storage.py`) позволяет:
  - просматривать список баз знаний;
  - создавать новую базу (имя, описание, эмбеддинг-модель);
  - загружать файлы в базу;
  - запускать индексацию (чанкинг + эмбеддинги);
  - тестировать семантический поиск.
- Индексация: `core/rag_chunker` разбивает текст на чанки,
  `core/rag_embeddings` вызывает Yandex Embeddings API (BYOK),
  `core/rag_indexer` сохраняет векторы в `core/rag_index`.
- Поиск: `core/rag_search` выполняет косинусное сходство по локальному
  индексу и строит контекст для LLM.
- DevAgent и оркестраторы могут обращаться к базам через инструменты
  `list_rag_bases()`, `rag_search()` и `rag_get_chunks()` (метаданные баз
  добавляются в системный промпт оркестратора блоком
  `Available RAG knowledge bases`).
- Результаты `rag_search` несут `chunk_id` и 0-based позицию чанка;
  `rag_get_chunks` добирает конкретные чанки (по `chunk_ids` или `source` +
  `chunk_indices`) для восстановления контекста вокруг находки - и в
  ассистентах (function-цикл), и в DevAgent.
- Статистика базы (счётчики чанков/эмбеддингов) кэшируется в meta-таблице
  локального индекса `index.db` и обновляется инкрементально при каждой
  записи: горячие пути рендера и API запрашивают базы без статистики
  (`with_stats=False`), поэтому интерфейс не сканирует большие индексы при
  каждом обновлении; полная статистика читается только при явном запросе
  (страница «Хранилище»).
- Инструкция **Rag Base Creator** (навык `rag_base_creator`) описывает
  процедуру создания и индексации баз знаний.

### FR11 - Коннекторы
- Пользователь может создавать **подключения** (коннекторы) к внешним
  сервисам (например, GitHub) - раздел настроек после «Хранилища».
- Подключение хранится в папке данных (`DATA_DIR/connectors/<id>/`):
  `manifest.json`; токен шифруется через `core.crypto.encrypt` и не
  попадает в публичные представления.
- Страница **«Коннекторы»** (`ui/pages/connectors.py`) позволяет:
  - просматривать список подключений;
  - создавать подключение (тип, имя, токен, аккаунт);
  - тестировать соединение;
  - изменять и удалять подключения.
- **Привязка к оркестраторам**: в настройках оркестратора (таб
  «Подключения») выбираются доступные подключения
  (`config['enabled_connections']`); связанные инструменты и блок
  `Available service connections` добавляются в системный промпт.
- **GitHub-коннектор:** единственный коннектор GitHub - REST
  (`core/github_connector_rest.py`, прямые запросы к REST API v3 через
  `requests`, без PyGithub). Legacy PyGithub-коннектор
  (`core/github_connector.py`, `core/github_tools.py`, инструменты
  `github_*`) полностью удалён.
- REST-коннектор реализует repo CRUD, чтение/запись файлов, метаданные,
  refs/коммиты/деревья и оптимизированную пакетную публикацию через Git Data
  API: все blobs создаются заранее, затем ОДНО дерево, ОДИН коммит и ОДНО
  обновление ref для всей пачки файлов (`batch_commit`; ветка создаётся,
  если репозиторий пуст). `batch_upsert` дополнительно сверяет локальные
  blob-SHA с удалённым деревом и пропускает неизменённые файлы (при полном
  совпадении коммит не создаётся). GET-запросы коннектора автоматически
  повторяются при сетевых сбоях (`requests.Timeout` / `ConnectionError`;
  до 3 попыток, паузы 0.5/1.5 с); write-методы и HTTP-ошибки не
  повторяются.
- Инструменты REST-коннектора для оркестраторов (`core/github_tools_rest.py`,
  префикс `ghr_*`): `ghr_list_repos`, `ghr_create_repo`, `ghr_read_file`,
  `ghr_upload_file`, `ghr_update_file`, `ghr_delete_file`, `ghr_list_files`,
  `ghr_batch_commit`, `ghr_batch_upsert`, `ghr_test_connection`,
  `ghr_get_repo_info`, `ghr_read_file_meta`, `ghr_get_ref`, `ghr_get_commit`,
  `ghr_get_tree`; каталог - `get_tools()`.
  Сервис подключения - `github_rest`; legacy-сервис `github` (PyGithub)
  удалён и больше не существует. Токен шифруется через `core.crypto` при
  сохранении соединения и никогда не попадает в результаты, ошибки или
  публичные представления.
- **SSH-коннектор:** сервис `ssh` - SSH/SFTP-подключения к серверам
  (`core/ssh_connector.py`, paramiko + SFTP, ленивый импорт). Конфигурация -
  `host`, `port` (1..65535), `username`; секреты - пароль или приватный ключ
  (+ опциональная парольная фраза), шифруются через `core.crypto` и не
  попадают в публичные представления.
- Инструменты SSH-коннектора для оркестраторов (`core/ssh_tools.py`, префикс
  `ssh_*`): `ssh_exec`, `ssh_list_dir`, `ssh_read_file`,
  `ssh_test_connection`, `ssh_upload_file`, `ssh_write_file`; каталог -
  `get_tools()`.
  Таймаут команды 60 с по умолчанию (максимум 300 с); stdout/stderr
  обрезаются до 100 КиБ, чтение файла - до 256 КиБ, запись - до 1 МиБ;
  `ssh_upload_file` потоково публикует локальный файл (до 50 МиБ) на сервер
  и по умолчанию проверяет перенос по sha256; `create_dirs=True` создаёт
  отсутствующие каталоги при записи.
- Страница «Коннекторы» для сервиса `ssh` показывает поля host/port/username
  и секреты (пароль или приватный ключ + парольная фраза); тест соединения
  выполняет реальное подключение.
- Инструкция `ssh_connector` (глобальная и встроенная у DevAgent) описывает
  работу с SSH-подключениями.

### FR12 - Библиотека навыков (Skills)
- Навыки лежат в `DATA_DIR/skills/<folder>/`, реестр - `skills/skills.json`;
  каждая запись хранит `developer` (правообладатель) и `adapted` (статус
  адаптации под SagaAI).
- Платформенные навыки из `defaults/skills/` импортируются с
  `developer=SagaAI`, `adapted=True`; сторонние - `developer=unknown`,
  `adapted=False`, пока DevAgent не завершит адаптацию.
- Неадаптированные навыки не попадают в блок `Available skills` системного
  промпта оркестратора: `get_enabled_skills_metadata()` возвращает только
  адаптированные записи. Инструмент `list_skills_library` при этом видит
  все навыки.
- Инструмент DevAgent `mark_skill_adapted(skill_id)` помечает навык как
  адаптированный (`core.skills_library.set_skill_adapted`).
- На странице библиотеки навыков для неадаптированных навыков есть кнопка
  «Адаптировать»: она формирует задачу адаптации и передаёт её в DevAgent
  (Skill Developer), который по завершении вызывает `mark_skill_adapted`.

### FR13 - Обновления платформы
- Обновления поставляются через публичный GitHub-репозиторий
  `TVD2100/sagaai-platform` по raw-ссылкам (без токена); канал указан в
  манифесте `file_versions.json`.
- Манифест описывает units (атомарные пакеты; исполняемый код - один пакет
  `core`) и selectable (по одному файлу: системные промпты, инструкции,
  пресеты, локализации, документация) с semver-версиями и sha256.
- Пользователь запускает проверку обновлений на странице «Обновления»:
  сравнение sha256/версий с установленными файлами; selectable-файлы можно
  выбрать по одному, пакеты - целиком.
- Выбранные файлы скачиваются и стейджатся (проверка sha256, каталог
  `.dev_agent/updates/pending/`); применение выполняется только при холодном
  старте приложения (хук в `app.py` до импорта Streamlit), живое приложение
  не затрагивается.
- Перед заменой файла создаётся бэкап
  (`.dev_agent/updates/backup/<run_id>/`), запись атомарная; при сбое -
  откат. Состояние применения - `state.json`, диагностика - `health.json`.

### FR14 - Доступ к приложению (страница «Доступы»)
- Страница **«Доступы»** (`ui/pages/access.py`, пункт меню «🔐 Доступы»
  перед «Обновления») управляет доступом по паролю.
- Блок «Доступ по паролю»: переключатель (по умолчанию выключен), поля
  пароля и подтверждения, интервал повторного запроса (по умолчанию 12
  часов, от 1 до 8760).
- Валидация: пароль и подтверждение должны совпадать; при включённом
  доступе пароль обязателен (если не задан ранее). При невалидном вводе
  настройки не сохраняются.
- Настройки хранятся в ConfigKV (`auth_enabled`, `auth_password`,
  `auth_reask_hours`); пароль шифруется Fernet (`core.crypto`) при
  сохранении.
- Приоритет пароля: значение формы (`auth_password`) канонично;
  `SAGAAI_AUTH_PASSWORD` используется только как запасной источник, если
  пароль формы пуст (`core.auth.resolve_auth_password`).
- После успешного входа пароль не запрашивается в течение интервала
  (`auth_reask_hours`); по истечении интервала - повторный запрос.
- Пока любой оркестратор выполняет задачу (агентный цикл активен),
  авторизация не запрашивается даже при истёкшем интервале
  (`core.auth.any_orchestrator_active`).
- Форма входа: `core.auth.require_auth()` вызывается в начале `main()`
  (`ui/app.py`) до рендера страниц; при выключенном доступе или
  аутентифицированной сессии - no-op.
- Это защита от случайного несанкционированного доступа, а не
  многопользовательская система (см. раздел «Ограничения»).

### FR15 - Защита от переполнения контекста LLM
- **M1 - политика размера результатов инструментов (спилл до отправки).**
  Результат, чей документ `{"tool_result": ...}` больше 20 000 символов,
  до первой отправки записывается целиком в
  `<workspace>/.dev_agent/tool_results/` (ротация до 100 последних
  файлов), а в контекст модели уходит ограниченное превью head+tail со
  `spill_path`: полный payload восстанавливается через `read_file`
  (offset/limit). Если запись спилла невозможна, результат длиннее
  200 000 символов не отдаётся в контекст: возвращается
  структурированная ошибка с фактическим размером и советом сузить
  аргументы (`result_too_large`, `result_size`). Политика применяется в
  `dev_agent/tool_executor.py` (диспетчер инструментов) и в
  `dev_agent/universal_agent.py` (custom-функции и инструменты
  подключений).
- **M2 - персист скрытых tool_result с сохранением проводной формы.**
  Результаты до 50 000 символов сохраняются в БД тредов дословно: при
  reload треда сообщение побайтово совпадает с отправленным проводом
  (resume-идентичность). Более крупные документы (аварийный путь, когда
  спилл недоступен) сохраняются краткой сводкой (статус, путь,
  применённость, размеры объёмных полей), а не сырым JSON; это
  защищает историю как от раздувания базы, так и от повторной загрузки
  сверхбольших payload'ов при reload тредов.
- **M3 - бюджет истории эконом-режима (порог + гистерезис).** Бюджет -
  минимум из легаси-доли (0.8×окна минус объявленный лимит вывода
  модели) и эффективного предела истории `history_cap(window, max_tokens,
  prompt_tokens) - 2048` (`_ECONOMY_GUARD_MARGIN`), то есть согласован с
  резервом pre-flight guard. Под бюджетом фронт истории не двигается;
  при превышении ведущие сообщения срезаются одним проходом до нижней
  ватерлинии (0.75×бюджета); в кэш-режиме срез дополнительно
  сворачивается в `state.economy_anchor`, поэтому фронт отправляемого
  окна остаётся на месте до нового перерастания. Служебная head-meta
  сохраняется всегда.
- **M4/M5 - pre-flight guard в api_layer.** Контекст запроса оценивается
  до отправки к провайдеру: резерв под вывод -
  `min(max_out, max(4096, 0.25×окна))`; при приближении к половине окна
  старые сообщения обрезаются, служебный head-блок эконом-меты не
  срезается; при превышении жёсткого порога (0.8 окна) и невозможности
  уложиться возвращается понятная ошибка `context_window_exceeded` без
  запроса к провайдеру; новый диалог не предлагается. Объявленные в
  каталогах сервисов лимиты вывода делают резерв реалистичным.

### FR16 - Совместимость GigaChat (payload, лимиты, видимость ошибок)
- GigaChat принимает ровно один system-промпт и только первым сообщением:
  `_gigachat_messages` (`core/api_layer.py`) фолдит в ведущее
  system-сообщение только ВЕДУЩИЕ system-блоки (системный промпт,
  эконом-мета) - в исходном порядке, а system-блок середины истории
  (task state, thread context) сохраняет позицию и отдаётся с ролью
  `user` (служебный контекст, не речь ассистента); префикс запроса при
  этом остаётся байтово стабильным от шага к шагу.
- Подряд идущие сообщения одинаковых ролей в GigaChat-payload
  схлопываются (склейка через пустую строку).
- `max_tokens` клампится по лимиту модели, при его отсутствии - по
  сервисному дефолту (`_clamp_max_tokens` в `core/api_layer.py`, до
  pre-flight guard); сервисы без объявленного лимита не затрагиваются.
- Ошибки LLM на первом шаге агентного цикла видны в ленте чата
  оркестратора: события шага (включая `error`) крепятся к сообщению
  пользователя текущего хода, если ответа ассистента ещё нет
  (`_attach_events` в `ui/pages/orchestrator.py`); ошибка не теряется при
  очистке loop_state.

  страница для всех оркестраторов (параметризуется slug), плюс
  `ui/pages/orchestrators.py` (управление списком) и
  `ui/pages/orchestrator_settings.py` (настройки).
- Встроенные сущности и канонические копии (промпты, переводы, сервисы,
  пресеты) лежат в `defaults/`; `core/defaults.py` и
  `core/default_imports.py` обеспечивают импорт «из коробки».
- RAG-подсистема: `core/rag*.py` (CRUD, чанкинг, эмбеддинги, индекс,
  индексатор, поиск) + страница `ui/pages/storage.py`.

### NFR2 - Тестируемость
- Полное покрытие модульными тестами (pytest).
- Моки Streamlit позволяют тестировать UI-логику без запуска реального
  сервера.
- Тесты запускаются в CI и при разработке.

### NFR3 - Безопасность при редактировании кода
- Защищённые файлы (ядро DevAgent) не могут быть изменены агентом.
- Каждое изменение файла создаёт бэкап с SHA-256 версионированием.
- Изменения применяются только после явного утверждения пользователем
  (в ручном режиме) либо после утверждения плана (в автономном режиме).
  Исключение - полностью автономный режим без согласования (pre-approved
  autonomous mode): пользователь явно отказывается от фазы утверждения,
  план составляется и исполнение начинается сразу; ручное применение
  (кнопка Apply) и подтверждения опасных команд продолжают действовать.
- Небезопасный код (`run_code`/`run_test`) проходит анализ в
  `core/dangerous.py`; опасные операции требуют подтверждения.

### NFR4 - Сохранность данных
- Все пользовательские данные (помощники, треды, конфигурация) хранятся
  в SQLite внутри папки данных.
- Оркестраторы хранятся в таблице `orchestrators` (slug, prompt_text,
  config_json, tools, max_steps, auto_apply, is_builtin, sort_order);
  папка-источник каждого оркестратора содержит `orchestrator.json`,
  `instructions.json`, функции и инструкции.
- Треды оркестраторов хранятся в отдельной БД `devagent.db`.
- Файлы помощников и загруженные пользователем файлы сохраняются на диске.
- Базы знаний (RAG) хранятся в `DATA_DIR/rag_bases/` с локальным индексом;
  каноническая база `yaagentai_2020` поставляется в `defaults/rag_bases/`.
- Бэкапы и снапшоты кода хранятся в `.dev_agent/backups/`.

### NFR5 - Интернационализация
- Вся видимая пользователю строка должна проходить через `t()`.
- **Английский (`en.json`) - канонический языковой файл.** Он всегда
  содержит полный актуальный набор ключей. При отсутствии перевода в
  другом языке `t()` автоматически подставляет строку из английского
  файла (fallback).
- Комментарии в коде - только на английском.

## Ограничения

- База данных - только SQLite; миграция на другие СУБД не предусмотрена.
- Аутентификация есть (страница «Доступы» или опциональный пароль
  `SAGAAI_AUTH_PASSWORD`), многопользовательский режим не предусмотрен.
- Приложение работает в окружении Streamlit; прямая работа из командной
  строки не поддерживается.
- Универсальный разработчик работает только с папками, доступными
  локально (в пределах файловой системы).
- Экспорт/импорт оркестраторов в UI отложен (доступен только в core API);
  новые оркестраторы появляются через импорт на уровне core или через
  DevAgent.
- Векторный поиск в RAG выполняется локально (SQLite + косинусное
  сходство); эмбеддинги генерируются удалённо через Yandex Embeddings API.
