# Архитектурное описание (ARCHITECTURE)

Документ поддерживается DevAgent и редактируется пользователем.

## Обзор

SagaAI построена по модульной архитектуре с чётким разделением на слои:

| Слой | Пакет | Назначение |
|------|-------|------------|
| Точка входа | `app.py` | Streamlit-конфигурация и запуск UI |
| Интерфейс | `ui/` | Страницы приложения + переиспользуемые компоненты |
| Бизнес-логика | `core/` | Работа с API, файлами, помощниками, тредами, оркестраторами, RAG, i18n - без зависимостей от Streamlit |
| Хранилище | `storage/` | SQLAlchemy ORM-модели, репозиторий, движок БД |
| Агент | `dev_agent/` | Цикл DevAgent, безопасный писатель, инструменты, подбор сервисов для помощников, внешняя память задач, изоляция рабочей папки по диалогам (пустое состояние «папка не выбрана», guard файловых инструментов) |
| Встроенное | `defaults/` | Канонические копии: промпты оркестраторов, переводы, сервисы, пресеты, RAG-базы, навыки |
| Тесты | `tests/` | Полный набор модульных и интеграционных тестов |
| Переводы | `langs/` | Рабочие JSON-файлы с переводами интерфейса (исходники - `defaults/langs/`) |
| Консоль | `sagaai/` | Третий вход в платформу: команды поверх `core/gateway/`, без Streamlit и HTTP-стека |

## Компоненты

### 1. Точка входа (`app.py` → `ui/app.py`)
- `app.py` задаёт конфигурацию страницы Streamlit, вызывает `ensure_data_dirs()`
  для создания структуры данных, затем делегирует управление `ui/app.py:main()`.
- `ui/app.py` инициализирует сессионное состояние Streamlit, загружает
  переменные окружения из shell-профилей (`load_env_from_shell_profiles`),
  выполняет начальное заполнение встроенных оркестраторов
  (`default_imports.ensure_all_defaults` / `ensure_builtin_orchestrators`),
  проверяет опциональные зависимости, рендерит боковую панель с навигацией
  (страницы + динамический список оркестраторов) и выбором языка.
- Отрисовка сайдбара разложена на подблоки (`_render_new_dialog_button`,
  `_render_active_dialog_indicator`, `_render_history_button`,
  `_render_employees_section`, `_render_assistants_section`,
  `_render_settings_section`, `_render_language_and_theme`),
  а переключение темы, восстановление состояния UI после перезагрузки и
  разбор deep-link-ссылок на диалог сотрудника живут в `ui/app_restore.py`
  и реэкспортируются через `ui.app`.
- После диспетчеризации страницы `main()` вызывает `render_flash()`
  (`ui/components/flash.py`): очередь уведомлений рисуется ОДИН раз за проход и
  именно в конце, поэтому подтверждение сохранения появляется под содержимым
  страницы, а не над её заголовком. Очередь живёт в `session_state` и переживает
  `st.rerun()`, который страница вызывает сразу после сохранения.

### 2а. Песочница исполнения и доступ агента (`core/sandbox/`, `storage/sandbox_journal.py`)

Изоляция, окружение и разрешения - три независимых слоя. Граница проводится
средствами ОС или контейнера, а не шаблонами по тексту программы: анализ
опасного кода (`core.dangerous`) решает, нужно ли подтверждение пользователя,
но не подменяет собой изоляцию. Окружение ребёнка - отдельное решение:
изолированный запуск строит его из allowlist, полный доступ передаёт
окружение платформы.

- **Профиль** называет требования запуска (уровень изоляции, сеть, запись) и
  потолки ресурсов. Профили объявлены в коде, а не в настройках сотрудника:
  гарантия не может зависеть от диалога.
- **Провайдер** объявляет достижимый уровень (`process`, `os`, `container`,
  `remote`) и выполняет подготовленный запрос. Провайдер не расширяет права:
  лимиты профиля он получает уже вычисленными.
- **Политика** выбирает самый сильный доступный провайдер и отказывает, если
  ни один не достигает требуемого уровня. Неизвестное имя профиля - тоже
  отказ: опечатка не должна превращаться в разрешающий режим по умолчанию.
  Профиль задаёт не только нижнюю границу изоляции, но и потолок: провайдер
  сильнее `max_isolation` не выбирается. Без потолка отключение песочницы
  работало бы только там, где изоляции нет вовсе, - на машине с рабочим
  `seatbelt` запуск молча поднимался бы до изолированного.
- **Журнал** (`sandbox_runs` в `sagaai.db`) хранит каждый запуск, включая
  отказ: иначе «нет записи» означало бы одновременно «не пытались» и
  «попытались и заблокировали». По строке журнала видны профиль, фактически
  применённые лимиты, провайдер, код возврата, длительность и путь к полному
  логу.

Инструменты `run_code`/`run_test` идут через `core.sandbox.runner`: решение о
запуске, выбор провайдера и запись в журнал выполняются в одном месте, поэтому
запуск не может пройти мимо записи. Аргументы инструмента (`timeout_s` и
прочие) только ужесточают профиль - модель не может выдать себе больший
таймаут или более широкие права.

Панель «Доступ агента к системе» открывает вкладку «Другое» страницы
настроек оркестратора. Единственное редактируемое значение верхнего
уровня - режим доступа: изолированный (`config.env_isolation = True`, по
умолчанию) или полный (`False`). Полный доступ передаёт дочернему процессу
окружение платформы, включая ключи провайдеров, и принудительно выбирает
профиль `off`: запуск идёт с правами платформы. Значения, которые ребёнок
печатает, вырезаются из результата инструмента (`exec_support.redact_secrets`)
- доступ даёт коду право пользоваться ключом, а не модели его прочитать.

Таблицы провайдеров и профилей живут в блоке «Подробности» и ничего не
сохраняют: они показывают, какие профили эта машина способна обеспечить и
каким провайдером, чтобы отказ был виден до запуска, а не после. Профиль
исполнения кода этого оркестратора хранится в `config.sandbox_profile`,
подставляется в каждый изолированный запуск и не действует при полном
доступе - селектор там заблокирован, потому что выбор не возымел бы силы.
Профиль, изоляцию которого машина не обеспечивает, выбрать нельзя: политика
отклонила бы запуск, и кнопка сохранения заблокирована.

Переключателя «Песочница» в панели чата больше нет: он и профиль были двумя
ручками одного факта и ни одна не отвечала на вопрос, который задаёт
пользователь - может ли агент дотянуться до машины. Панель чата показывает
режим доступа индикатором (изолированный, частичный, полный доступ) и ведёт
в настройку, где решение принимается. Старая запись `config.chat_sandbox`
остаётся в силе: снятый флаг по-прежнему снимает изоляцию ОС и при этом НЕ
даёт окружение платформы - такой случай показан баннером «частичный
доступ» с предложением выбрать режим явно. Ниже панель показывает активные
запуски с живым хвостом вывода и кнопкой остановки и последние записи
журнала вместе с отказами.

**Одно решение для всех путей запуска** (`core/sandbox/resolve.py`). Профиль,
окружение и гейт подтверждения - независимые настройки сотрудника, но читать
их конфиг самостоятельно не должен ни один вызывающий: `sandbox_profile(slug)`,
`env_isolation(slug)` и `safety_enabled(slug)` возвращают значения по
умолчанию, если ключ не записан (изолированное окружение, включённый гейт), а
`apply_to(dispatcher, slug)` проставляет все три на построенный диспетчер. Им пользуются
`build_child_dispatcher` (субагент), `build_dispatcher` (диалог) и
`_make_dispatcher` (расписание). Без этого слоя переключатель из панели чата
доходил только до диалога, а делегированный ребёнок продолжал работать в
профиле по умолчанию с включённым подтверждением - ребёнок не может нажать
Allow, поэтому запрет возвращался ему ошибкой инструмента и останавливал
работу.

**Гейт подтверждения** (`core.dangerous.tool_needs_confirmation`) решает,
нужно ли спросить пользователя, и вызывается из `dev_agent/tools/exec.py`
только при включённом `_safety_enabled`. Обычные команды цикла разработки в
list-форме (`python`, `node`, `php`, `pytest`, `ruff`, `git`, `mkdir`, `cp`,
`mv`, `cat`, `tar`, клиенты локальных БД) гейт не включают: `shell=True` и
строковая форма команды остаются опасными, потому что допускают конвейер и
перенаправление, а разрушительные и сетевые команды (`rm`, `dd`, `mkfs`,
`sudo`, `ssh`, `curl`, `docker`, `kubectl`, `terraform`) запрещены списком
запретов при любом профиле.

Провайдеры по уровням:

| Уровень | Провайдер | Что даёт |
|---------|----------|----------|
| `process` | `process` | Ничего не изолирует: только отсечение окружения и лимит времени |
| `os` | `seatbelt` (macOS), `bwrap` (Linux) | Песочница ядра: `network-off`, `write-confined` |
| `os` | `wsl` (Windows) | Запуск в дистрибутиве WSL2: `write-confined`, `network-off` только после удачной пробы `unshare -n` |
| `container` | `container` (Docker) | `network-off`, `write-confined`, `process-limit`: потолки числа процессов и памяти держит runtime, а не только ядро |

Контейнер получает не хостовый `argv`, а переведённый: хостовый интерпретатор
становится `python3` внутри образа, а пути, которые команда называет (скрипт
вне рабочей папки), монтируются только на чтение. Рабочая папка монтируется
на запись лишь при профиле с записью. Отмена останавливает контейнер по имени,
потому что клиент `docker run` - только прокси к демону.

На Windows хостовый `argv` тоже переводится: диск - в `/mnt/<буква>`, а
абсолютный путь, у которого нет соответствия внутри дистрибутива (сетевая
шара), - отказ. Запустить другой файл вместо проанализированного хуже, чем
не запустить ничего; отказ записывается в журнал как отказ.

Модель не должна узнавать о песочнице из неудачного запуска. В системный
промпт сотрудника добавляется блок `## Code execution sandbox`
(`core/sandbox/status.py`, вставка в `core/orchestrator_prompt.py` сразу
перед блоком текущей даты): профиль, провайдер, фактические гарантии, границы
записи, состояние сети и лимиты. Факты берутся из `policy.plan_run` - того же
решения, что принимает реальный запуск, поэтому подпись не может обещать
изоляцию, которой не будет. Отдельные ветки для отключённой песочницы,
неизвестного профиля и отказа политики: режим без изоляции называется прямо,
а не молчанием блока.

### 2б. Подтверждение операции из API (`core/gateway/approvals.py`)

Пауза на опасной операции (`confirmation_required`) существует потому, что
решение принимает человек. Браузер передаёт решение кнопкой внутри процесса,
где живёт цикл; HTTP-клиент такой кнопки не имеет, и без отдельного механизма
он мог бы только ждать таймаута.

Тикет подтверждения - файл на сервере, а не аргумент модели. Он привязан к:

- **запуску** (`run_id`): ответ нельзя перенести в другой запуск;
- **операции**: `tool` плюс хеш аргументов, без учёта `None`-полей, чтобы
  запаркованный вызов и повторный диспетчерский совпадали;
- **решению**: `allow` или `deny` - отказ тоже ответ, и он возвращается как
  `deny`, а не как «решения не было»;
- **сроку**: тикет истекает, и истёкший тикет не является решением.

Тикет одноразовый: повторный идентичный вызов требует нового решения.
Успешное возобновление снимает тикет, чтобы на диске не оставался стоящий
ответ для следующего такого же вызова.

Маршрут `POST /v1/runs/{run_id}/confirm` читает запаркованную операцию из
состояния запуска, а не из тела запроса: тело называет только решение, поэтому
подменить команду той, которую человек не видел, нельзя. Запуск продолжается
в фоне - шаг это вызов провайдера плюс его инструменты, а HTTP-запрос обязан
вернуться; ответ `202`.

### 3b. Бизнес-логика страниц (`core/chat_turn.py`, `core/orchestrator_step.py`)

Правила хода диалога не живут в модулях рендера. Страница собирает ввод и
показывает экран; что именно происходит с сообщением, решает core-слой:

- **`core/chat_turn.py`** - один ход чата с помощником. `turn_history`
  отдаёт историю треда в форме API (без служебных полей ленты), `run_chat_turn`
  вызывает провайдера с языком, файловым контекстом и колбэком расхода,
  `collect_tokens` собирает расход одного хода (отсутствие отчёта остаётся
  `None`, а не нулём), `persist_chat_turn` создаёт тред при необходимости и
  пишет пару сообщений в порядке «вопрос → ответ», вкладывая файл только когда
  есть и имя, и текст.
- **`core/orchestrator_step.py`** - запись одного шага агента в тред:
  `messages_to_persist` отсекает уже сохранённое по курсору (курсор за концом
  истории даёт пустой список, а не исключение), `message_row` - единственное
  место, где поля истории ложатся в поля хранилища, `persist_step_messages`
  пишет недостающие и возвращает новый курсор, поэтому повторный вызов после
  перерисовки ничего не дублирует.

Слой не рендерит и не знает про `st`: ошибку провайдера он пробрасывает, а
страница решает, как её показать. Именно это делает правила проверяемыми без
Streamlit и без сети (`tests/test_chat_turn_and_step.py`).

### 5. DevAgent (`dev_agent/`)
- `agent_loop.py` - фасад цикла: сохраняет все публичные и приватные имена
  (тесты и monkeypatch-точки тянут их через алиас модуля) и собирает
  `LoopRuntime` из собственных module-level атрибутов в момент вызова, поэтому
  подмена `agent_loop.send_request` продолжает действовать. Сама реализация -
  пакет `loop/`: `state.py` (AgentLoopState/AgentResult), `parse.py` (JSON-repair
  каскад, DSML, `parse_tool_calls`), `signals.py` (loop_status, признаки
  плана/вопроса, strength шага), `results.py` (кап tool-результатов и спиллы),
  `context.py` (эконом-режим, thread/task-state контекст, снапшоты),
  `delegation.py` (запуск подагентов), `notices.py` (доставка уведомлений) и
  `steps/` - `prepare` (нормализация истории, снапшоты), `models` (окно истории
  и вызов модели), `parsing` (разбор ответа), `executing` (диспетчеризация
  инструментов и счёт отказов), `runner` (итерация целиком), `runtime`
  (LoopRuntime) и `approvals` (решения по подтверждениям).
- Цикл с единой основной
  моделью, эконом-режим, approval-гейты (план, применение, подтверждение опасных
  операций); в режиме pre-approved autonomous mode фаза утверждения плана
  пропускается по явному выбору пользователя. Цикл несёт идентичность запуска
  (`run_id`/`parent_run_id`/`depth` в `state`) и умеет fan-out в фазе
  `executing`: независимые вызовы `spawn_agent` проверяются на права и
  аргументы ДО захвата пула, затем выполняются параллельно, а их события
  уходят в ленту с `run_id` ребёнка. Режим prompt-injection защиты ребёнок
  наследует от диалога: fan-out читает `state.enable_injection_protection` и
  передаёт его в `spawn_agent`/`resume_subagent`, сервис замораживает
  значение в записи запуска (одноразовый bypass просмотра не наследуется).
- `assistant_detector.py` - `detect_and_select_assistant()` **всегда
  возвращает пустой результат** (assistant detection отключён).
- `assistant_model_resolver.py` - автоматический подбор сервиса/модели для
  помощников: классификация (сложность, web_search); без веб-поиска -
  основная модель из настроек оркестратора, с веб-поиском - YandexAI
  (pro/lite по сложности).
- `task_state.py` - внешняя память задач: per-thread журнал
  `TASK_STATE__<thread_id>.md` (архитектура, план, прогресс, handoff,
  история завершённых задач), рендер/парсинг, бэкап перед записью. При
  пустом состоянии «папка не выбрана» журнал живёт в папке диалога
  (`history/<tid>/task_states/`). Компактный дайджест
  (`read_task_state(compact=True)`) и бюджеты секций ограничивают
  инъекцию `CURRENT TASK STATE`; полное чтение - по требованию.
  Идентификатор треда передаётся явно (`current_thread_id(thread_id)`,
  `ensure_task_state_file`/`archive_and_start_task`), а `config.ACTIVE_THREAD_ID`
  остаётся фолбэком; контекст-менеджер `thread_scope` пинит тред в текущем
  потоке Python, чтобы параллельные дочерние запуски не перезаписывали журнал
  друг друга.
  Удержание журналов (`prune_task_state_journals`): каркас журнала пишется
  заранее, для каждого треда, поэтому установка накапливает файлы, которые
  никто уже не прочитает. Уборка удаляет пустой журнал (нет содержимого
  Active Task и нет Task History) старше `PRUNE_MIN_AGE_DAYS` (7 дней) и
  журнал завершённого дочернего запуска, чей родительский журнал исчез
  (`<parent>__s<run>` без родителя - читать его больше некому). Живой
  диалог, свежие файлы, журналы с историей и файлы не-журналы не трогаются;
  удаление пустого родителя не каскадит на детей в том же проходе, поэтому
  незавершённый ребёнок не теряется. Обход покрывает и каталог проекта, и
  папки пустого состояния диалогов; `prune_task_state_journals_once`
  выполняет его один раз за процесс (хук в `agent_loop`).
- `tool_executor.py` - точка входа и реэкспорт набора инструментов DevAgent. Сам диспетчер (`ToolExecutor.dispatch`, маршрутизация вызова к обработчику, применение защит рабочей папки и опасных команд) остаётся здесь; тела инструментов разложены по пакету `dev_agent/tools/`, сгруппированному по предметным областям: `files.py`/`editing.py`/`patch.py` (чтение, запись, точечные правки, `apply_patch`), `exec.py` (`run_code`/`run_test`), `workspace.py` (рабочие папки и защита пустого состояния), `assistants.py`, `library.py` (навыки и инструкции), `catalog.py` (перечень инструментов и их схемы), `args.py` (приведение числовых аргументов), `text_utils.py` (общие помощники текста), `rag.py`, `history.py`, `web_search.py`, `url_fetch.py`, `images.py`, `clock.py`, `task_state.py`. Миксины получают зависимости через `deps.py`: `build_deps` читает фасад на каждом вызове, поэтому тесты и обработчики, вызванные в обход `dispatch`, видят настоящие функции, а не `None` из умолчаний dataclass.

  Инструменты: `propose_file`,
  `apply_patch`, `verify_file`, `run_code`/`run_test`, `read_document`
  (текст документа по пути с окном строк, через `core.document_text`),
  инструменты помощников/оркестраторов/навыков, `web_search()`, RAG-инструменты
  (`list_rag_bases`/`rag_search`), мультимодальные инструменты
  (`analyze_image`/`generate_image`), history-инструменты. Описание `run_code`
  помечено как средство последней очереди: для документов, исходников, текста,
  изображений и вложений диалога есть специализированные инструменты.
- `safe_writer.py` - безопасная запись файлов (проверка защищённых файлов,
  staging, бэкап, верификация).
- `backup_manager.py` - управление версиями файлов на основе SHA-256.
- `workspace_tools.py` - инструменты для внешних проектов: set_workspace,
  build_project_map (AST-разбор символов с regex-фолбэком, лимит 200
  символов на файл, фильтр состава `include_paths`/`scope_note`,
  sha256-отпечаток содержимого в шапке, extra-секция для файлов вне
  текстового скана), снапшоты, ведение документации.
- `workspace_binding.py` - привязка рабочей папки к потоку диалога:
  per-thread реестр состояний под RLock, контекст-менеджер
  `thread_context` (снапшот конфига -> применение состояния потока ->
  восстановление), `ensure_thread_active`; персистентность привязок
  делегирована `core.threads_devagent`. Дочерний запуск получает
  собственное связывание через `bind_child_thread` (рабочая папка родителя,
  свой производный тред `{parent}__s{run_id[:8]}`, без `target_file`) и
  освобождает его `unbind_thread` по завершении. Это же связывание создаёт
  строку индекса треда ребёнка (`kind="subagent"`, `parent_thread_id`,
  относительный `transcript_path`, рабочая папка) - идемпотентно и
  терпимо к сбою хранилища, до первого шага ребёнка: без строки любой
  читатель транскрипта отвечает «Thread not found», даже когда файл
  переписки полностью записан.
- `universal_agent.py` - `load_system_prompt()` (единый файл
  `dev_agent/system_prompt.md`), `build_assistant_dict_from_config()`,
  `UniversalDevAgent` (core + workspace + orchestrator tools, включая
  `extract_document_images`: картинки документа сохраняются файлами под
  `.dev_agent/doc_images/`, а распознавание остаётся за `analyze_image`).
  Фасад держит диспетчеризацию и состояние, а чистые части вынесены в
  соседние модули пакета: `tool_catalog_data.py` (каталог инструментов и
  белые списки имён аргументов), `tool_validation.py` (проверка вызова до
  выполнения - отключённые инструменты, имена аргументов, права на
  делегирование; свободна от состояния диспетчера, поэтому цикл агента
  импортирует её напрямую), `document_tools.py` (помощники
  `extract_document_images`: выбор источника, решение о рендере страниц,
  слияние рендеров с внедрёнными картинками), `thread_scope.py` (правила
  адресации `search_in_threads`) и `tool_registry.py` (помощники реестра
  connection-инструментов и записи памяти).
- `system_prompt.md` - канонический системный промпт DevAgent (v3.30):
  цикл анализа перед планом (рой read-only субагентов -> архитектура -> спека
  изменения в `.dev_agent/scratch/task_spec.md` -> план -> сверка спеки
  в отчёте), проверка линтерами
  проекта до тестовых уровней и автономное ведение утверждённой серии
  элементов с картой в `<task_dir>/series.md`;
  docs-first workflow (перед началом работы читать `AGENT.md`, если он есть,
  затем `PROJECT_MAP.md`), обязательная секция «Documentation» в финальном отчёте,
  режим pre-approved autonomous mode (при подробном ТЗ агент явно
  спрашивает «автономно или с согласованием плана»; при выборе «без
  согласования» план составляется, но фаза утверждения пропускается).
- `config.py` - разрешение путей, защищённые файлы, runtime-директории.
- `llm_utils.py` - унифицированный вызов LLM (контракт assistant-словаря).

### 7. RAG-подсистема (`core/rag*.py`, `ui/pages/storage.py`)
- **База знаний** - папка `DATA_DIR/rag_bases/<slug>/`:
  `manifest.json` (поле `search_mode`), файлы документов, локальный
  SQLite-индекс `index.db`.
- **Режимы поиска** (`search_mode` в манифесте; отсутствие поля = `bm25`,
  миграция на чтении): `bm25` - собственная лексическая реализация
  (`core/rag_bm25`: Unicode-токенизация ru/en, k1=1.5/b=0.75, без
  API-ключей); `vector` - косинусное сходство по эмбеддингам;
  `hybrid` - Reciprocal Rank Fusion (k=60) обоих ранжирований с
  деградацией до `bm25` при недоступности эмбеддингов. Хиты несут `mode`.
- **Анализ текста в лексическом поиске** (схема `bm25_version = 3`,
  полезависимый BM25F): кириллица стеммится консервативным суффиксным
  стеммером (своя реализация, без внешних зависимостей; латиница не
  трогается), служебные слова отбрасываются (русский/английский
  стоп-список). Тело чанка и его самоописывающая шапка (`Документ`/
  `Продукт`/`Заголовок`/`Раздел`) индексируются как ДВА отдельных поля
  со своими df и средней длиной: повтор шапки в каждом чанке обрушивает
  IDF только внутри поля шапки, а IDF доменного термина тела
  сохраняется; при этом имя продукта или раздела, встречающееся лишь в
  шапке, остаётся находимым (раньше такой чанк был недостижим).
  Служебный `Фрагмент` (маркер N/M) в индекс не входит. Многословные
  запросы получают координационный множитель (совпадение всех
  содержательных терминов ранжируется выше частичного). Индексы старой
  схемы (v1/v2, а также таблицы без поля `field`) пересобираются лениво
  один раз.
- **Активность базы** (`active`) учитывает режим: `bm25` и `hybrid`
  остаются активными и без ключей провайдера (`hybrid` работает по своей
  лексической половине), ключи требуются только режиму `vector`.
- **Индексация**: `rag_chunker` (чанкинг) → `rag_indexer` пишет чанки в
  `rag_index` всегда и поддерживает BM25-структуры (`core/rag_bm25`;
  ленивая первая сборка для баз старых версий, далее инкрементальные
  хуки add/update/delete); в режимах `vector`/`hybrid` дополнительно
  получает эмбеддинги Yandex Embeddings API (BYOK).
- **Поиск**: `rag_search` диспетчеризует по режиму базы и собирает
  контекст для LLM; заголовки контекста несут `chunk_id` и 0-based
  позицию найденного чанка.
- **Добор контекста**: `rag_get_chunks` - выборка конкретных чанков без
  эмбеддингов (по `chunk_ids` или `source` + `chunk_indices`) поверх
  `core.rag_index.fetch_chunks`; доступен и DevAgent, и function-циклу
  ассистентов.
- **Инструменты DevAgent**: `list_rag_bases()`, `rag_search()`,
  `rag_get_chunks()`; метаданные баз попадают в системный промпт
  оркестратора (`Available RAG knowledge bases`).
- **Статистика без полных сканов**: счётчики чанков/эмбеддингов кэшируются
  в meta-таблице `index.db` и обновляются инкрементально при каждой записи;
  API `list_bases` / `get_base_slug` / `list_bases_with_activity` принимают
  `with_stats` - горячие пути рендера и API запрашивают базы без статистики,
  полный расчёт выполняется только при явном запросе одной базы или на
  странице «Хранилище».
- **Навык Rag Base Creator** (`defaults/skills/rag_base_creator/`) описывает
  процедуру создания и индексации баз.

### 8. Библиотека навыков и адаптация (`core/skills_library.py`, `ui/pages/skills_library.py`)
- **Навык** - папка `DATA_DIR/skills/<folder>/` + запись в реестре
  `skills/skills.json` с полями `developer` (правообладатель) и `adapted`
  (статус адаптации под SagaAI).
- **Импорт**: платформенные навыки (из `defaults/skills/`) получают
  `developer=SagaAI`, `adapted=True`; сторонние - `developer=unknown`,
  `adapted=False`.
- **Папка встроенного навыка** - имя его пресета (`rag_base_creator`), а не
  отображаемое название: каталог адресует тот же навык по этому имени, и
  установка из каталога обязана попасть в ту же папку. Сидинг
  останавливают маркер `source: marketplace/<id>` и уже занятая папка -
  иначе рядом появилась бы вторая копия с суффиксом.
- **Фильтрация промптов**: `get_enabled_skills_metadata()` возвращает только
  адаптированные навыки; блок `Available skills` в системном промпте
  оркестратора строится из них. Инструмент `list_skills_library` видит все
  навыки.
- **Поток адаптации**: кнопка «Адаптировать» на странице библиотеки
  передаёт задачу в DevAgent (Skill Developer) → DevAgent выполняет
  адаптацию и вызывает инструмент `mark_skill_adapted(skill_id)` →
  `set_skill_adapted()` обновляет реестр, и навык появляется в промпте.

### 8a. Маркетплейс сущностей (`core/marketplace/`, `ui/pages/marketplace.py`)

Каталог с установкой, обновлением и откатом. Устанавливаются четыре типа
сущностей: навык (`skill`), агент (`agent`), база знаний (`rag`) и
MCP-сервер (`mcp`).

- **Модули пакета.** `semver` (разбор и сравнение версий), `source`
  (транспорт каталога: индекс, сущность, пакет), `catalog` (вид для
  витрины), `verify` (sha256-манифест пакета и целостность установки),
  `store` (каталог данных, бэкапы, журнал, кэш пакета), `registry` (строки
  `marketplace_installed` и `marketplace_removed`), `installer` (установка
  навыка с журналом и общий диспетчер `install_entity`), `agent_installer`
  (фасад установки агента: папка, строка реестра, откат при сбое),
  `agent_package` (вид агента и разбор пакета), `agent_preflight`
  (предполётные проверки вида, платформы, лицензии и кода), `agent_areas`
  (запись папки и удаление устаревших файлов), `agent_orchestrator`
  (сотрудник: мерж конфига, инструкции, functions), `agent_assistant`
  (помощник: `manifest.json`, `prompt.md`, вложения), `install_seed`
  (модельный базис и переводы имени из карточки поверх пакета), `agent_run`
  (журнал прогона и строка реестра), `package_pin` (закрепление кэша пакета
  как базы обновления), `rag_installer` (манифест, источник, индекс),
  `rag_area` (проверки и запись папки базы знаний), `mcp_installer`
  (регистрация пресета без секретов), `mcp_removal` (удаление пресета
  при деинсталляции), `conflicts` (матрица конфликтов),
  `conflict_state` (что установлено, где папка и что правил пользователь),
  `conflict_fork` (форк и возврат своей версии), `updates` (обновления),
  `rollback` (откат прогона), `bootstrap` (холодный старт), `config`
  (настройки и выключатель).
- **Диспетчер типов.** `installer.install_entity` по полю `type` направляет
  работу в свой установщик, а кортеж `SUPPORTED_TYPES` перечисляет все
  четыре типа и читается витриной и планировщиком пакетов - вместо
  пробного вызова.
- **Путь установки.** Журнал прогона пишется до изменения файлов → пакет
  копируется во временную папку и сверяется по sha256 → результат
  переносится атомарно (`os.replace`) → строка `marketplace_installed` и
  `skills.json` библиотеки обновляются одной транзакцией.
- **Идентичность сущности.** Ключ - `id` каталога, а не папка и не имя:
  папка (`runtime_slug`) производна и может смениться, а имя правится
  пользователем. Поэтому переименование навыка не рвёт связь с каталогом,
  а форк получает собственный id `<id>#forkN`.
- **Виды агента.** Поле `agent_kind` различает сотрудника
  (`orchestrator`) и помощника (`assistant`). Сотрудник ставится папкой
  оркестратора с мержем конфига, инструкциями и functions; помощник -
  папкой `DATA_DIR/assistants/<slug>` (`manifest.json`, `prompt.md`,
  `files/*.txt`) и строкой в таблице `assistants`. Вид идёт по цепочке
  манифест → индекс каталога → карточка витрины → строка реестра → строка
  «Обновлений», поэтому витрина подписывает карточку, не скачивая пакет.
  Отсутствие поля читается как `orchestrator`: так описаны записи,
  созданные до его появления. Установка проверяет вид до первого
  изменения файлов - смена вида у установленной сущности запрещена
  (`agent_kind_changed`), потому что вид определяет и папку, и таблицу.
  Вложения помощника принимаются только текстовыми (`files/*.txt`):
  хранилище держит их как `.txt`, и пакет с другим расширением
  отклоняется целиком. При обновлении пользовательские вложения
  сохраняются, а отредактированный промпт не перезаписывается.
- **Что установка сотрудника добавляет к пакету.** Пакет - это замысел
  автора, платформа добавляет к нему три вещи, все до импорта папки
  (`core/marketplace/install_seed.py`): модельный базис
  (`_seed_platform_config` заполняет только отсутствующие ключи модели тем
  же дефолтом, на котором работает среда исполнения), переводы имени из
  карточки каталога (`_apply_entity_names` заполняет `name_ru` / `name_zh`,
  когда имя пакета повторяет английское имя карточки) и `config_defaults`
  манифеста. Ключ пакета всегда сильнее любого из трёх:
  авторский конфиг не переписывается, а сотрудник без модельных ключей
  стартует на платформенном дефолте вместо блокировки на странице чата.
- **Локальные правки.** `files_json` хранит хэши установленных файлов;
  расхождение с диском означает правку пользователя. Сравнение идёт по
  содержимому, а не по времени изменения - касание файла не делает
  установку «изменённой».
- **Три разрешения конфликта.** `keep_mine` оставляет файлы
  пользователя и обновляет остальные; `take_catalog` заменяет всё, но
  сначала бэкапит каждый заменяемый файл - иначе откат вернул бы только
  те, что попали в бэкап; `fork` создаёт новую сущность и приводит
  оригинал к каталогу.
- **Обновления.** Проверка сравнивает версии по semver, раскладывает
  находки по секциям `skill`/`agent`/`rag`/`mcp` и принимает ссылку как
  `type:id`, так и голым id (тип тогда ищется по реестру). Навык
  обновляется через резолвер конфликтов, остальные типы - переустановкой
  новой версии собственным установщиком, потому что база и агент
  заменяются целиком. Отказ по одной сущности (несовместимая платформа,
  требование кода при `allow_code=false`, непринятая лицензия) не отменяет
  остальные - она попадает в список недоступных с причиной.
- **MCP-сущность = пресет.** Установка не создаёт подключение: пакет
  описывает сервер (`preset`: транспорт, url/command, `secret_env_fields`,
  иконка) и пишется файлом в пользовательский корень пресетов, а строка
  реестра хранит `runtime_slug` = id пресета. Встроенный пресет с тем же
  сервером делает установку no-op - платформа уже поставляет эту плитку.
  Подключения пользователь создаёт из плитки сам, каждое со своими
  секретами; деинсталляция удаляет только пользовательский файл пресета
  (`mcp_removal.remove_preset`) и не трогает созданные подключения.
  Строки реестра прежних версий хранили id подключения: для них
  `mcp_removal.remove_connection` сохраняет старое правило - черновик без
  заполненных учётных данных удаляется, настроенное подключение остаётся.
- **Журнал и откат.** Журнал ограничен: 20 записей для навыков, 3 для баз
  знаний (прогон базы знаний на порядок тяжелее). Откат восстанавливает
  файлы, строку реестра и `skills.json` байт в байт; незавершённый прогон
  восстанавливается на холодном старте (`app.py` до импорта Streamlit).
- **Кэш пакета как база обновления.** Проверка обновления отвечает, что
  пользователь изменил, сравнивая установленный конфиг с манифестом
  установленной версии, а манифест читается из кэша пакета. У кэша есть срок
  жизни, поэтому установка закрепляет пакет (`core/marketplace/package_pin.py`,
  `store.pin_package`) в момент
  записи строки реестра: без закрепления установка старше срока кэша
  отвечала бы «изменено всё» и обновление молча ничего не переносило бы.
  Прежняя версия освобождается (`store.pin_package(sha, False)`) только когда на неё
  не ссылается ни одна установка - общий пакет двух агентов не вытесняется.
- **Удаление.** Маркер в `marketplace_removed` читает
  `core/default_imports.ensure_default_skills`, поэтому удалённый навык не
  воскрешается встроенным импортом.
- **Подразделы витрины.** Пять подразделов - сотрудники, помощники, навыки,
  базы знаний, коннекторы - описываются списком `(ключ, тип, вид агента,
  подпись)` и работают одновременно как вкладки страницы и как пункты блока
  «МАРКЕТПЛЕЙС» в боковом меню. Сотрудники и помощники делят тип `agent`, но
  фильтруются ещё и по `agent_kind`: они ставятся в разные места, и общий
  список смешивал бы два продукта. Обе стороны пишут ключ `mp_section`
  (подсветка меню), а запрос из меню идёт отдельным ключом
  `mp_section_target`: страница снимает его до создания вкладок и передаёт
  метку через `default`, потому что записать состояние виджета после его
  создания Streamlit не разрешает.
- **Блок «Дополнительно».** Рекомендуемый набор рисуется в карточке
  (`_render_bundle`): подпись позиции собирается из имени, версии,
  переведённого названия типа (`mp_type_<type>`) и состояния; галочка стоит
  по `default_selected`, недоступные позиции остаются видимыми и
  неактивными, чтобы намерение набора не пропадало. План набора кэшируется в
  `session_state` по карточке и сбрасывается после установки или обновления
  каталога - иначе каждый клик читал бы по манифесту на члена набора.
- **Одна кнопка установки.** Кнопка карточки одна: `_install_button`
  вызывает `_install_together`, и одно нажатие ставит сущность через
  `installer.install_entity`, а затем отмеченные позиции набора через
  `bundles.install`. Два шага намеренно разные: установщик сущности отвечает
  `noop` на уже стоящую версию, а набор - это единый прогон с откатом, и
  сбой в нём не трогает сущность, установленную до него. У уже установленной
  сущности та же кнопка ставит только отмеченное (`only_members=True`).
- **Раскрытие карточки живёт в состоянии сессии** (`mp_open_<id>`), а не в
  результате нажатия текущего прогона. Каждое действие - установка, сброс,
  удаление - запускает перерисовку, где кнопка «Подробнее» уже не нажата;
  карточка, свёрнутая по этому признаку, возвращалась до кнопки установки и
  проглатывала нажатие, поэтому установка не срабатывала и сообщения не
  появлялось.
- **Выключатель.** `marketplace.enabled` закрывает блок «МАРКЕТПЛЕЙС» в
  боковом меню, разовый сидинг реестра и обновление кэша при импорте
  встроенных оркестраторов.
- **Наборы** (`bundles`). Рекомендуемый набор каталога - список сущностей с
  флагом `optional`. `preview_bundle` показывает каждую позицию с её
  состоянием (`install`/`installed`/`update`/`incompatible`/`unavailable`)
  и только отмеченные строки попадают в `install_bundle`. Сбой позднего
  члена откатывает все члены прогона, а ранее установленные сущности не
  трогаются - иначе повторная установка набора снимала бы работающую
  конфигурацию.
- **Миграция встроенных сущностей** (`migration`). `LEGACY_DEFAULTS`
  сопоставляет пару (тип, id) с записью, которая уже стоит на диске: при
  включённом маркетплейсе `core/default_imports` больше не считает такие
  сущности отдельными от каталога, а заводит им строку реестра с
  синтетической версией `legacy` - ниже первого релиза, чтобы обновление
  оставалось настоящим. Навык `rag_base_creator` сеется в папку со своим
  именем и потому усыновляется наравне с оркестратором и базой, а каталог
  видит занятую папку и предлагает `adopt` вместо второй копии. Маркер
  `marketplace_removed` проверяется раньше и побеждает - иначе удалённое
  вернулось бы первым же стартом.
- **Публикация каталога** (`publish`). Каталог живёт в отдельном
  репозитории; `scripts/marketplace_publish.py` собирает индекс и пакеты,
  считает хэши и публикует одним коммитом, а модуль `publish` держит
  чистую логику сборки, чтобы её можно было проверить без сети. Подписаны
  `index.json` и каждый `entity.json`: рядом с файлом лежит `<файл>.sig` с
  алгоритмом, `key_id` (выводится из открытого ключа) и подписью сырых
  байтов файла, поэтому любая правка после публикации ломает подпись.
  `--init-key` создаёт пару ключей, private остаётся вне репозитория, public
  уезжает в `keys/<key_id>.pub`. Флаг `--export-standalone` пишет копию
  публикатора, не зависящую от платформы, - её и коммитят в репозиторий
  каталога, поэтому логика сборки не расходится между двумя местами.
  Бинарные пакеты публикуются отдельным коммитом с передачей байтов в
  base64: инструмент пакетной загрузки текстовых файлов бинарный файл
  отклоняет.
- **Проверка подписи** (`attest`). Клиент проверяет байты, которые получил:
  `MarketplaceSource` сверяет `.sig` до разбора JSON, поэтому подменённый
  манифест не доходит ни до парсера, ни до установщика. Кольцо ключей
  читается из `keys/*.pem` самой установки (`marketplace.signature_keyring`
  и `SAGAII_SIGNATURE_KEYRING` перенаправляют его на частное зеркало);
  несколько ключей в кольце - это штатная ротация. Канал `stable` и флаг
  `marketplace.require_signature` превращают непройденную проверку в
  отказ, каналы разработки записывают отчёт и продолжают. Гейт установки
  (`attest.install_gate`) срабатывает до скачивания пакета, поэтому на
  строгом канале неподписанная сущность не тратит ни одного запроса.
- **Манифест обновлений.** `scripts/sign_release.py` подписывает и проверяет
  `file_versions.json`: апдейтер скачивает `file_versions.json.sig` рядом с
  манифестом и применяет ту же политику каналов, поэтому `stable`-канал не
  ставит обновление без доверенной подписи.
- **Якорь доверия поставлен.** Публичная половина релизного ключа лежит в
  `keys/ed25519-public.pem` (`key_id` выводится из самого ключа); приватная
  хранится вне репозитория (`~/.sagaai/ed25519.pem`, `0600`) и передаётся
  путём или через `SAGAII_SIGNING_KEY`. Подпись манифеста - sidecar по
  построению: запись `file_versions.json.sig` внутри подписываемого манифеста
  сделала бы первый релиз зависимым от подписи предыдущего, поэтому
  `scripts/verify_manifest.py` держит её в `COVERAGE_SKIP`.
- **Сеть.** Старт приложения офлайновый: каталог читается только по
  нажатию кнопки на витрине или на странице «Обновления».

### 8b. Консоль (`sagaai/`, `bin/sagaai`)

Третий транспорт платформы рядом с UI и HTTP API. Слой тонкий намеренно:
он разбирает аргументы, решает, что можно делать без человека, и печатает
результат - вся работа уходит в готовые модули.

| Модуль | Ответственность |
| --- | --- |
| `cli.py` | сборка парсера из реестра команд, перевод исключений в коды возврата |
| `console.py` | единственный писатель stdout: человеческий отчёт и ровно один JSON-объект в режиме `--json` |
| `errors.py`, `exit_codes.py` | `CliError` с полями `code`/`message`/`hint` и фиксированные коды 0/1/2/3 |
| `commands/_common.py` | подтверждение, корень установки, проверка запущенной платформы, трансляция отказа шлюза |
| `commands/<name>.py` | `register(parser, add_global_flags)` + `execute(args, console)` на команду |

- **Направление зависимостей.** `sagaai/` → `core/gateway/` → `core/orchestration/`;
  отдельно `sagaai/` → `core/updater.py`, `core/updater_apply.py`,
  `core/api_token_store.py`, `core/paths.py`, `core/dependency_check.py`.
  Обратных стрелок нет, поэтому консоль не может сломать интерфейс.
- **Почему без Streamlit и FastAPI.** Импорт Streamlit тянет сервер
  интерфейса, импорт FastAPI - HTTP-стек; ни то, ни другое не нужно, чтобы
  выдать задачу или снять снимок базы. `sagaai ui` запускает интерфейс
  дочерним процессом, `sagaai serve` импортирует `core/gateway_launcher`
  лениво. Границу проверяет `tests/test_cli_imports.py` в подпроцессе с
  заблокированными пакетами.
- **Расширение ядра.** Для консоли добавлены `core/gateway/bootstrap.py`
  (холодный старт без UI), `core/gateway/diagnostics.py` (диагностика
  только чтением), `core/gateway/backup.py` (снимки баз через движок
  SQLite) и `core/gateway/dialog.run_dialog()` - блокирующий запуск
  поверх того же шлюза, которым пользуются UI и API.
- **Снимки как данные.** Каталог снимков живёт в `DATA_DIR/backups/databases/`,
  а не в корне установки: `SAGAAI_DATA_DIR` покрывает тогда всё состояние,
  а `SAGAAI_INSTALL_ROOT` остаётся про код.

## Поток данных

### Чат с LLM
Пользователь → `ui/pages/chat.py` → `core/api_layer` → LLM API → ответ и
сохранение треда через `storage/repository`.

### Цикл оркестратора (DevAgent)
1. Пользователь ставит задачу на странице оркестратора.
2. `ui/pages/orchestrator.py` создаёт `AgentLoopState`, заполняет
   `strong_assistant` (единая модель; `weak_assistant` - совместимый
   алиас-копия) через `core/orchestrators.build_assistant_dicts(slug)`.
3. `agent_loop.py` сохраняет сообщение пользователя в историю, переходит
   в фазу `calling_llm` и отправляет запрос основной моделью; при
   обрыве связи (`RequestTimeoutError` / `NetworkError`) запрос повторяется
   прозрачно (`retry_call` в `core/api_http.py`, реэкспортирован через
`core/api_layer.py`), в ленту чата идёт событие
   `retrying_llm`. Если тело HTTP 200 помечено `status == "incomplete"`
   (усечение по лимиту токенов) и видимого текста нет, запрос повторяется
   РОВНО ОДИН раз с `reasoning_effort='none'`, в ленту идёт событие
   `incomplete_retry`.
4. Перед шагом LLM `refresh_context_snapshots` добавляет в историю
   изменившиеся снапшоты task state / thread context скрытыми
   system-сообщениями (append-only: проводная последовательность
   запроса N+1 - строгое расширение запроса N); если последняя копия
   снапшота вытеснена из окна, в хвост добавляется одна свежая копия.
5. LLM → `parse_tool_calls` → `tool_executor` → результаты → повтор до
   терминального статуса (`loop_status` или approval-гейт).

### RAG-запрос
Пользователь (или агент) → `ui/pages/storage.py` / `rag_search()` →
`core/rag_search` → локальный индекс `index.db` → релевантные чанки →
контекст для LLM.

### Навигация оркестраторов
`ui/app.py` → `core/orchestrators.list_orchestrators()` + треды
`core/threads_devagent.list_devagent_threads()` → `core/orchestrator_nav.py`
строит меню: первые 5 сотрудников (сортировка по времени последнего
диалога, иначе по времени создания - новый сотрудник вверху), остальные -
в свёрнутом блоке «Все (N)»; поле поиска появляется только при количестве
сотрудников > 5. Каждый оркестратор →
`ui/pages/orchestrator.page_orchestrator(slug)`. Секция «Помощники»
работает по тем же правилам (`core/assistant_nav.py`).

### Импорт встроенных сущностей
`defaults/` - канонический источник для дефолтных оркестраторов
(`defaults/orchestrators/*/`, например YaAgent - orchestrator.json +
system_prompt.md), переводов, сервисов, помощников, навыков и RAG-баз
(`defaults/rag_bases/yaagentai_2020/`). Исключение -
системный промпт встроенного DevAgent: он хранится в одном месте -
`dev_agent/system_prompt.md` (рядом с кодом агента), а в
`defaults/orchestrators/dev_agent/` лежат только его инструкции.
Рантайм-папки оркестраторов (DATA_DIR/orchestrators/) создаются при первом
запуске из defaults/ и в репозитории не хранятся.

Встроенные оркестраторы ввозятся идемпотентно
(`ensure_default_orchestrators()`): сущность создаётся, если её нет, и не
трогается, если она уже есть. Повторный запуск возвращает статус `exists`
без второй копии, а удалённый пользователем сотрудник не возвращается.
**Universal-Agent** (`defaults/orchestrators/universal_agent/`) -
универсальный исполнитель, который ставится вместе с платформой так же, как
YaAgent. Он одновременно присутствует в каталоге Marketplace под тем же
идентификатором: предустановленная копия усыновляется каталогом (запись без
второй установки, версия `0.9.0`, канал `legacy`), поэтому витрина
показывает обновление, а не предложение поставить второй экземпляр, а
установка из каталога обновляет ту же папку. Позиция `sort_order`
назначается платформой при создании и в пакет каталога не входит -
служебное поле раскладки, а не часть сущности.

## Решения и принципы

### Архитектура оркестраторов
- **`core/orchestrators.py`** - публичная поверхность API оркестраторов.
  Реализация разложена по темам на фасад и восемь модулей-спутников: фасад
  держит импорт-блок, реэкспорты и тонкие обёртки, а тела живут в
  `orchestrator_defaults` (константы, дефолтный конфиг, ленивый кэш имён
  инструментов), `orchestrator_store` (чтение, запись, синхронизация папки),
  `orchestrator_links` (навыки, подключения, RAG-базы, делегирование),
  `orchestrator_prompt` (сборка системного промпта и `build_assistant_dicts`),
  `orchestrator_models` (модель, web-search, fetch, эконом-режим),
  `orchestrator_strong` (разрешение пары «провайдер-модель» сотрудника:
  настроенная пара, затем устаревшие ключи `service`/`model`, затем
  платформенный дефолт),
  `orchestrator_transfer` (экспорт и импорт бандла), `orchestrator_instr`
  (инструкции и функции) и `orchestrator_builtin` (встроенные оркестраторы и
  мост к конфигу DevAgent).
- **Подмена имён core API** - через слой `core/orchestrator_shared.py`, по тому
  же принципу, что и у страницы. Тесты адресуют API объектом модуля
  (`monkeypatch.setattr(orch_mod, "get_orchestrator", ...)`) и строковым путём
  (`patch("core.orchestrators._get_services")`), поэтому спутник объявляет
  заимствованное подменяемое имя через `late("имя")` и разрешает его на
  фасаде в момент вызова; имя, у которого есть `_impl`-версия, фасад
  оборачивает тонкой функцией. Имя, которое спутник определяет сам
  (`build_assistant_dicts` в `orchestrator_prompt`, `delete_orchestrator` в
  `orchestrator_store`), в late не нуждается: подмена на фасаде заменяет
  обёртку, а собственное тело спутника вызывается через неё же.
- **`ui/pages/orchestrator.py`** - универсальная страница,
  параметризуемая slug; отдельные `orchestrators.py`/`orchestrator_settings.py` -
  список и настройки. Страница разложена по темам на фасад и девять
  модулей-спутников: фасад (`orchestrator.py`) держит импорт-блок, обёртки и
  две точки входа `page_orchestrator`/`page_devagent`, а тела живут в
  `orchestrator_state` (session_state и кэш economy), `orchestrator_folder`
  (выбор папки), `orchestrator_loop` (шаг агента, дерево диалога, запуски
  субагентов), `orchestrator_feed` (лента событий), `orchestrator_chat`
  (вкладка чата), `orchestrator_chat_input` (ввод, вложения, строка токенов),
  `orchestrator_settings_models`, `orchestrator_settings_orch` и
  `orchestrator_settings_delegation` (вкладки настроек).
- **Подмена имён страницы** - через слой `ui/pages/orchestrator_shared.py`.
  Тесты и обработчики адресуют страницу объектом модуля
  (`monkeypatch.setattr(orch_mod, "t", ...)`), поэтому тело, вынесенное в
  другой файл, читало бы СВОИ глобальные имена и не видело подмены. Каждый
  модуль объявляет подменяемое имя один раз (`_do_step = late("_do_step")`,
  `st = st_proxy()`) и разрешает его на фасаде в момент вызова; `bind_facade`
  привязывает слой к объекту фасада, чтобы вторая живая копия пакета (тесты,
  чистящие `sys.modules`) не перехватывала подмену. Имя, у которого есть
  `_impl`-версия, фасад оборачивает тонкой функцией - подмена на фасаде
  доходит до реализации.
  Шаг агента (`_do_step`) разложен на фазы с сохранением порядка операций над
  `session_state`: флаги шага, сборка состояния, регистрация корневого запуска,
  обработка запроса остановки, сам шаг, персист шага в тред и фиксация
  состояния. Лента событий рендерится таблицей `_EVENT_RENDERERS` - по
  рендереру на тип события; `tool_call` и `tool_result` обрабатываются до
  таблицы, потому что пара «вызов + результат» и есть основа ленты.
- **`ui/pages/orchestrator_text.py`** - чистые помощники страницы: очистка
  вывода модели от служебной разметки, превью аргументов и тела результата,
  группировка событий по запускам, карта ключей `session_state` диалога
  (`build_state_keys`). Без Streamlit и без переводимых строк;
  страница реэкспортирует все имена, поэтому тесты и лента обращаются к ним
  через `ui.pages.orchestrator`.
- **`core/prompt_blocks.py`** - чистые блоки текста системного промпта:
  правила диалога родителя и ребёнка, вводные блоки каталогов
  `spawn_agent` / `invoke_assistant` / `verify_result`, кортежи названий дней
  и месяцев, помощники строки даты и смещения UTC. Модуль без базы, без
  Streamlit и без подменяемых имён - `core/orchestrators.py` реэкспортирует
  его имена под историческими приватными алиасами.
- **`storage/models.py:Orchestrator`** - модель с полями `slug`, `prompt_text`,
  `config_json`, `tools`, `max_steps`, `auto_apply`, `is_builtin`, `sort_order`.
- Экспорт/импорт оркестраторов реализован в core API, **UI отложен** -
  кнопки экспорта/импорта в интерфейсе намеренно отсутствуют.
- Старые `load_devagent_config()` / `save_devagent_config()` - прокси на
  оркестратор `dev_agent`.
- Правки промпта встроенного оркестратора (DevAgent) переживают перезапуск:
  при редактировании промпта через UI `save_orchestrator()` ставит в config
  маркер `prompt_user_edited`, и `ensure_builtin_orchestrators()` на старте не
  перезаписывает `prompt_text` из `dev_agent/system_prompt.md`, пока маркер
  установлен. Сброс маркера и возврат к поставляемому промпту -
  `reset_builtin_prompt(slug)` (кнопка сброса на вкладке «Промпт»). Прочие
  разделы настроек (модели, эконом-режим, функции, max_steps, навыки,
  подключения) старт не затрагивает: они бэкфиллятся только при отсутствии
  значения.

### Единая модель и модели изображений
Агент использует единую основную модель на всех шагах; служебная
классификация `classify_step_strength()` сохраняется для журналирования и
модель не переключает. Дополнительно в конфигурации оркестратора могут быть
назначены `vision_service`/`vision_model` (распознавание изображений) и
`image_service`/`image_model` (генерация изображений); пустые значения -
«не назначена». Legacy-ключи `weak_*` читаются как алиасы основной модели.
Поставляемые дефолты DevAgent (канонический бандл
`orchestrators/dev_agent/orchestrator.json` → фолбэк
`_DEVAGENT_FALLBACK_DEFAULTS` в `core/config.py`, дублируется в
`_devagent_default_config()` и первом запуске `ensure_builtin_orchestrators()`):
основная модель DeepSeek/`deepseek-flash` с `strong_reasoning_effort`
`xhigh` и лимитом вывода 384 000 токенов, распознавание изображений
DeepSeek/`deepseek-flash`, генерация изображений не назначена
(`image_service`/`image_model` пусты), поисковая модель
DeepSeek/`deepseek-flash` с `search_temperature` 0.4,
`search_max_tool_calls` 3 и `search_reasoning_effort` `high`. Бэкфилл на
старте заполняет только поля без значения, поэтому уже выбранные
пользователем модели и настройки экономии не перезаписываются.
Назначенные модели используются системными инструментами `analyze_image`
(файлы проекта и вложения диалога; JPEG/PNG/WebP, до 5 изображений и
10 МБ каждое; ответ оборачивается в фенс `DATA_FROM_IMAGE`; каталоги
`vision_models`: YandexAI - `qwen3.6-35b-a3b` и `deepseek-v4.1-flash`, DeepSeek - `deepseek-flash` через выделенный `vision_base_url` с `detail="original"`) и `generate_image` (синхронный OpenAI-совместимый Images API
YandexAI, единственная модель `aliceai-image-art-3.0`; результат сохраняется
файлом - в workspace или в папку файлов диалога, base64 не возвращается -
и показывается в чате с кнопкой скачивания) через `core/multimodal.py`
и транспорты `core/api_layer.py`.
Правила применения, сценарии «модель не назначена» / «модель не умеет» и
согласие на установку зависимостей - в глобальной инструкции
`multimodal_mode` (`defaults/instructions/multimodal_mode.md`).

### Защиты цикла агента от зацикливания
- `AgentLoopState.tool_fail_counts` - счётчик подряд идущих отказов по каждому
  инструменту (без учёта аргументов). После `_MAX_CONSECUTIVE_ERRORS` (3)
  неудачных вызовов одной функции ошибка дополняется подсказкой перейти по
  fallback-цепочке (`apply_patch` → `propose_file` → `run_code`), а успешный
  вызов сбрасывает счётчик инструмента.
- Детекторы `_identical_block_count` / `_dominant_duplicate_call` определяют
  флуд одинаковых вызовов в одном ответе LLM; такой поток схлопывается в одну
  компактную ошибку `identical_blocks`/`identical_calls` без диспатча.
- **Батч-протокол вызовов.** `parse_tool_calls()` разбирает КАЖДЫЙ
  фенс-блок сообщения по отдельности; независимые вызовы (read-only и
  прочие, см. условия в промпте) исполняются по порядку, а результаты
  склеиваются в одно user-сообщение. Если часть блоков не распарсилась,
  `AgentLoopState.partial_parse_warning` (собирается в parsing-фазе,
  дописывается в executing-фазе один раз) возвращает рядом с результатами
  предупреждение `partial_batch` с диагностикой по каждому сломанному
  блоку (`_unparsed_tool_json_diagnostics`: truncation, несбалансированные
  скобки/строки, невалидный JSON). Диагностика срабатывает только когда
  есть исполненные вызовы и ни один из них не был JSON-отремонтирован,
  чтобы не дублировать авто-ремонт.
- Системный промпт DevAgent v3.30 дополняет механизм правилами: закрытый шаг
  не пересказывается, не более 3 попыток на функцию, прозовый
  `loop_status: continue` продолжает цикл, независимые вызовы можно
  батчить, ветка принятия готового плана пользователя дословно;
  восстановление состояния - по компактному дайджесту
  (`task_state_read(compact=True)`), дисциплина микровызовов - окна
  `read_file(offset/limit)` и `PRAGMA table_info` перед прямым SQL.

### Прозрачные ретраи при обрывах связи
LLM-запросы обёрнуты в `retry_call` (`core/api_http.py`, реэкспортирован
через `core/api_layer.py`): повторяются
только `RequestTimeoutError` и `NetworkError`, пауза между попытками -
`SAGAAI_NETWORK_RETRY_DELAY` (по умолчанию 30 с), максимум
`SAGAAI_NETWORK_RETRY_ATTEMPTS` попыток подряд (по умолчанию 3); последнее
исключение помечается атрибутом `attempts`. Колбэк `retry_callback`
протягивается из `dev_agent/agent_loop.py` через `core/api_layer._do_request`
и генерирует событие `retrying_llm`, которое рендерит
`ui/pages/orchestrator.py` (i18n-ключ `orch_retry_llm`). POST-запросы Yandex
Responses (`core/assistant_tools.py`) обёрнуты тем же механизмом. Сообщение
пользователя персистится в историю ДО вызова модели - при исчерпании всех
попыток диалог не теряется, а продолжается со следующего сообщения.

Отдельный необязательный `incomplete_callback` (по образцу
`usage_callback`/`sanitized_callback`) сообщает вызывающему о теле HTTP 200
со статусом `incomplete` (`_responses_incomplete_details`, reason обычно
`max_output_tokens`), которое иначе выглядело бы как обычный пустой ответ.
`dev_agent/agent_loop.py` подписывается на него и при отсутствии видимого
текста делает один восстановительный повтор с пониженным `reasoning_effort`.

### Web-search модель (search_service/model)
Отдельная пара service/model для задач с веб-поиском, хранится в
конфигурации оркестратора; используется `tool_executor.web_search()`.
У DeepSeek встроенный инструмент `web_search` в Responses API молча
игнорируется, поэтому веб-поиск для DeepSeek выполняется отдельным
запросом к Anthropic-совместимому endpoint (`web_search_base_url`,
`https://api.deepseek.com/anthropic/v1/messages`) с моделью
`deepseek-flash`; ветка выбирается в `tool_executor.web_search()` по
`auth_type == "deepseek_responses"`.

### Fetch-модель (fetch_service/fetch_model) и url_fetch
Необязательная пара service/model для загрузки веб-страниц, хранится в
конфигурации оркестратора. Поддержку объявляет сам профиль сервиса:
каталог `fetch_models` плюс endpoint `fetch_base_url`
(`https://api.deepseek.com/v1/tools/fetch` в `defaults/services/deepseek.json`).
Транспорт - `core/url_fetch.py::fetch_page_content()`: POST `{"url": ...}`
с Bearer-ключом сервиса, ответ `{"title", "content"}` (Markdown), ошибки -
через контракт `APIError` (`ApiKeyMissingError`, `ProviderHTTPError`,
`RequestTimeoutError`, `NetworkError`, `ProviderResponseError`), проверка TLS
по общей политике платформы.

Второй, независимый источник возможности - флаг `fetch_selenium`
(чек-бокс «Использовать Selenium»): страница открывается в headless-браузере,
собирается её видимый текст, а Markdown формирует основная модель
оркестратора (`llm_service` / `llm_model` из `get_fetch_config()`).
Selenium - опциональная зависимость: при её отсутствии ветка возвращает
структурированную ошибку `SeleniumUnavailableError` с подсказкой об установке.
На вкладке «Модели» чек-бокс рисуется первым: пока он включён, селекторы
пары `fetch_service` / `fetch_model` скрыты (подпись
`orch_fetch_selenium_main_model` объясняет, что Markdown формирует основная
модель), а сохранённая пара не сбрасывается и возвращается на место после
снятия флажка.

Инструмент называется `url_fetch` (`dev_agent/tool_executor.py`), прежнее имя
`page_fetch` сохранено как legacy-алиас (с ним же резолвятся `disabled_tools`).
Ветки выбора: адрес с PDF-расширением или `application/pdf` в ответе -
скачивание с лимитом размера и извлечение текста через `pypdf`
с разбивкой `### Page N`; иначе при включённом Selenium - рендер браузером;
иначе - Search/Fetch API провайдера. Прямые загрузки проходят SSRF-гард
`validate_fetch_url()`: схема http/https, длина до 8192 символов, без
логина и пароля, локальные и приватные адреса запрещены (loopback, частные
диапазоны, link-local, служебные суффиксы `.local`/`.internal`/`.lan`) - без
DNS-резолвинга, поэтому проверка детерминирована и работает офлайн.

Каталог `core/orchestrator_tools.py` помечает инструмент как capability-gated
(`_CONDITIONAL_TOOLS`) и включает его в `build_tool_catalog()`,
`list_system_tools()` и блок `## Available tools`, когда
`core.orchestrators.get_fetch_config()` вернул `configured=True` - то есть
назначена модель либо включён Selenium. Снятие обоих источников (или
исчезновение модели из каталога провайдера) убирает инструмент из промпта и
из диспетчера; UI-секция «Модель для загрузки страниц» на вкладке «Модели»
предлагает только сервисы с `fetch_models` (при включённом Selenium секция
заменена подписью об основной модели - см. выше).

### Типизированные границы и бюджет статического анализа

Правило: если форма данных пересекает границу модуля, пакета или
транспорта, она объявляется моделью, а не собирается по ключам на каждой
стороне. Модель - единственное место, где перечислены поля; потребитель
читает её, а не догадывается о содержимом словаря. Уровней два, и граница
между ними проведена осознанно: dataclass'ы ядра (`core/gateway/dto.py`)
описывают данные внутри платформы, pydantic-схемы (`server/schemas.py`) -
провод: валидацию недоверенного ввода и схему OpenAPI. Соединяют их явные
мапперы в `schemas.py`, поэтому расхождение уровней - это диф в одном
файле, а не молчаливое изменение API.

Неизменность публичного JSON проверяют golden-тесты
(`tests/test_api_golden.py`, снимок `tests/golden/api_contract.json`): они
фиксируют ответы двадцати операций и падают на любом изменении. Это не
запрет менять контракт, а требование менять его осознанно - вместе со
снимком в диффе.

Статический анализ (`pyright`, режим `basic`, пакеты `core`, `server`,
`storage`, `sagaai`) держит бюджет находок в `pyright_budget.json`.
Бюджет, а не ноль: в проекте есть места, где аннотация не добавляет
ничего, и требование нуля вынудило бы либо остановить работу, либо
расставить подавления, под которыми скрылись бы настоящие ошибки.
Проверка падает только на рост числа; снижение бюджета - отдельный
осознанный коммит.

### Изоляция глобального состояния между тестами

Часть кода меняет состояние процесса, а не только свои данные: `dev_agent.config`
хранит активную рабочую папку и признак `WORKSPACE_SELECTED`, реестр
привязок - папку каждого диалога. Отрисовка страницы оркестратора, сброс
диалога и переход в пустое состояние переключают это состояние.

Утёкший `WORKSPACE_SELECTED=False` блокирует файловые инструменты во всех
последующих тестах того же прогона, поэтому симптом проявляется далеко от
причины - падением постороннего файла, который проверяет guard. Правило
разделения ответственности:

- `tests/conftest.py` поставляет фикстуру `_restore_dev_agent_state`, но
  **не включает** её через `autouse`: снимок состояния стоит времени, и
  autouse-хук заставлял бы платить за него каждый тест набора, скрывая,
  каким тестам восстановление действительно нужно;
- модуль, который вызывает `apply_paths` или `_reset_dialog`, либо просит
  эту фикстуру по имени, либо снимает и возвращает состояние сам;
- `tests/scenarios/conftest.py` держит autouse-хук на всю папку: сценарии
  отрисовывают настоящие страницы, и переключение состояния - это и есть
  проверяемое поведение, поэтому восстановление живёт на уровне папки.

`tests/test_test_state_isolation.py` закрепляет правило: разбирает тестовые
модули через AST, находит вызовы переключателей и требует восстановления от
каждого, кто их делает. Новый тест-нарушитель падает с именем файла в
сообщении, а не через десяток чужих падений.

### Структурный бюджет и golden-снимки поведения

Разделение крупного модуля на части опасно не тем, что код перестанет
компилироваться, а тем, что поведение изменится незаметно: порядок
событий в интерфейсе, состав истории на проводе, подсказка, которую
модель получает в следующем шаге. Две проверки закрывают именно этот
зазор.

`refactor_budget.json` задаёт для файлов, которые ещё предстоит
разделить, три потолка: длину файла, длину самой длинной функции и
максимальную цикломатическую сложность. Сложность меряет тот же `ruff`
правилом `C901`, отдельной зависимости для этого нет; временный конфиг
включает только это правило, поэтому репозиторный `ruff.toml` не
меняется. Бюджет - потолок, а не цель: значение может упасть, и тогда
его правят в том же коммите, но вырасти оно не может, иначе разделение
можно тихо откатить обратно. Проверка
`python scripts/refactor_budget.py` отвечает тем же трёхзначным исходом,
что и остальные ворота, и входит в общий прогон шагом `budget`.

Список файлов сам по себе дырявый: новый модуль с гигантской функцией в
него не попадает и проходит мимо гейта. Поэтому рядом с `limits` лежит
секция `global` с двумя потолками, измеряемыми по всему дереву
исходников, - `max_function_lines` и `max_cc`. Сканируются все `.py` вне
каталогов данных и вне `tests`: длинная тестовая фикстура - норма, а
потолок, поднятый под неё, перестал бы защищать код. Обе величины
меряются по одному и тому же списку файлов, поэтому у каждой есть
названный владелец (`longest_function`, `most_complex`), и он попадает в
сообщение об ошибке. Секция необязательна: бюджет без неё работает как
раньше, а значения по-прежнему можно только понижать.

`tests/test_loop_golden_payloads.py` фиксирует наблюдаемое поведение
цикла агента на восьми сценариях: что уходит модели (сообщение, история,
файловый контекст, признак защиты от инъекций, набор колбэков), какие
вызовы диспетчера делаются и в каком порядке, и какую
последовательность событий получает интерфейс. Снимки лежат в
`tests/fixtures/loop_golden/`; обновляются они только явно -
`python scripts/capture_loop_golden.py`, который перезаписывает их и
сразу же проверяет воспроизводимость. Снимок на уровне полезной
нагрузки, а не на уровне вызовов внутренних функций: разбиение шага на
функции не меняет снимок, переупорядочивание событий - меняет.

### Воспроизводимая сборка и зависимости

Установка задаётся тремя файлами с разделёнными ролями.
`requirements.txt` и `requirements-api.txt` - человекочитаемые пределы
версий: нижняя граница совпадает с минимумом в реестре
`core/dependency_check.py` (это сравнивает тест), верхняя не даёт
следующему мажору ключевого пакета установиться молча.
`requirements.lock` - то, что действительно ставится: каждая прямая и
транзитивная библиотека с точной версией и sha256 каждого файла,
сгенерированная `pip-compile --generate-hashes` из ОБОИХ файлов пределов.
Установка идёт с `--require-hashes`, поэтому подмена файла на зеркале
ломает установку, а не тесты.

`pyproject.toml` (PEP 621) объявляет сам пакет: имя `sagaai-platform`,
версию через `attr core.version.__version__` (одна точка правды),
четыре обязательные зависимости и необязательные группы
`api`/`documents`/`selenium`/`ssh`/`dev`. Пакеты перечислены явно:
плоская раскладка с корневым `__init__.py` не выводится автообнаружением,
и догадка молча теряет подпакет.

Поддерживается только editable-установка (`pip install -e .`):
`core/paths.py` вычисляет каталоги данных от родителя пакета `core`, и в
обычной установке этим родителем стал бы `site-packages`, где нет ни
`defaults/`, ни `langs/`, ни `services/`. Консольная команда
`sagaai = sagaai.cli:main` появляется вместе с пакетом; `bin/sagaai`
остаётся лаунчером для не установленной копии.

`scripts/ci_check.py` - единственный источник проверок: workflow только
вызывает его, поэтому проверку нельзя добавить в одно место и забыть в
другом. Сам workflow - автоматизация этого репозитория, а не поставляемый
файл: установка его не запускает, а канал публикации не может передать
workflow-файл вообще. Поэтому `.github/` не входит в манифест версий -
иначе манифест обещал бы файл, который ни одна установка не получит, и
единственный недоступный файл сорвал бы весь прогон обновления.

Проверки идут в порядке от дешёвых к дорогим: `ruff` (стиль),
`types` (`pyright` против бюджета находок), `budget` (структурный бюджет
крупных файлов), `manifest` (схема, хэши, покрытие `file_versions.json`),
`lock` и `tests` (весь набор одним процессом - модули держат глобальное
состояние, и параллельные воркеры дают отказы, которых в одном процессе
нет). Каждая проверка отвечает одним из трёх исходов: прошла, провалилась
или не смогла выполниться в этом окружении; третье отличается от второго,
потому что отсутствующий инструмент - это не ошибка кода.

Сверка lock с ОБОИМИ файлами пределов входит в тот же набор: объявленный
дистрибутив, отсутствующий в lock, закреплённый вне своего диапазона или
без хэшей, валит конвейер. CI ставит окружение из lock, а не из
`requirements.txt`, поэтому «зелено локально» и «зелено в CI» означают
одно и то же.

### Персональная память и рабочая папка (два хранилища)

Память разделена на два хранилища с разными правилами жизни. Персональный
слой (`core/personal_memory.py`) хранит заметки о том, КАК работать: он лежит
в `DATA_DIR/personal/` (в `.gitignore`), не экспортируется и удаляется вместе
с установкой. Рабочая папка роли (`MEMORY_DIR`, резолвер
`resolve_data_dir`) хранит рабочие данные: реестры, карточки, журналы. По
умолчанию она ЦЕНТРАЛЬНАЯ - `DATA_DIR/agents_data/<slug>/`: папка принадлежит
установке, поэтому одна и та же роль имеет одну и ту же память в любом
проекте, и смена рабочего проекта не уносит данные. Роль, чьи материалы
обязаны ехать вместе с проектом, указывает это явно (`workspace:<подпуть>`).

- **Области персонального слоя.** `user` (карточка владельца, общая для всех
  сотрудников), `orchestrator:<slug>` (личная память сотрудника),
  `project:<hash12>` (заметки о рабочем проекте, ключ - первые 12 символов
  sha256 абсолютного пути), `connector:<id>` (адаптер: текст физически лежит
  в `DATA_DIR/connectors/<id>/memory.md` и обслуживается API коннекторов).
- **Запись.** `write_memory` проверяет область, права, секреты и размер
  (64 КиБ), копирует текущую версию в `personal/.backups/<kind>__<key>/`,
  пишет атомарно (temp + `os.replace`) и увеличивает `revision` в шапке.
  `read_memory` возвращает текст с метками и умеет резать вывод
  (`max_chars`), `memory_meta` отдаёт размер и свежесть без текста.
- **Права.** Сотрудник пишет только свои области; чужая область сотрудника
  даёт `another employee`. Внутренние вызовы (сборка промпта, UI, миграция)
  передают пустой `caller_slug` и считаются доверенными: разграничение
  доступа агента - работа диспетчера инструментов, а не файлового слоя.
- **Инъекция в промпт.** `build_assistant_dicts` вызывает
  `_extend_prompt_with_personal_card` (карточка `## Owner profile` из области
  `user`, секции `Rules`/`Preferences`/`Environment`/`Notes`, потолок 2500
  символов; при пустой карточке блок опускается) и
  `_extend_prompt_with_memory` (блок `## Memory`). Второй блок выводится
  всегда: он задаёт правило «когда писать» - после поправки владельца,
  после решения, важного в следующий раз, после обнаруженного ограничения -
  и без него на чистой установке практика заметок не начинается. Блок также
  называет состояние своей области (пусто либо размер, ревизия, дата),
  перечисляет области и запрещает молча перезаписывать общую карточку
  владельца. Текст заметок сотрудника в промпт не попадает: он читается
  инструментом, иначе каждая реплика оплачивала бы весь накопленный объём.
  При сбое слоя памяти блок деградирует до «область пуста», а не исчезает.
- **Инструменты.** `get_personal_memory`, `set_personal_memory`
  (`mode='replace'|'append'`), `list_personal_memory` в
  `dev_agent/universal_agent.py`; область `current` разрешается в область
  активного сотрудника и является значением по умолчанию для чтения.
  Инструменты не входят в `WORKSPACE_REQUIRED_TOOLS` - память доступна
  и в пустом состоянии. Область `user` общая, поэтому её перезапись
  требует флага `overwrite_owner_profile` (принимается булево или строка
  `'true'`/`'1'`/`'yes'`/`'on'`), а дополнение через `append` разрешено
  всем: иначе один сотрудник стёр бы правила, записанные другим.
- **Рабочая папка.** `resolve_data_dir` выбирает путь по первому совпадению:
  маркер `MEMORY_DIR:` в промпте → `config.memory_dir` → центральный
  `DATA_DIR/agents_data/<slug>/`. Префикс `workspace:<подпуть>` разрешается
  от активного проекта, `central:<подпуть>` - от центрального корня, `.`
  означает корень проекта, абсолютный путь берётся как есть, любой другой
  относительный путь идёт от рабочего проекта (исторический смысл явного
  значения). Ответ содержит `source`, `scope` (central/workspace/external),
  `outside_workspace`, `legacy` (старая `<проект>/<slug>_data` с файлами)
  и `conflicts` - папки, где после смены пути остались файлы: данные не
  переносятся молча, пользователь видит предупреждение. Пустые папки не
  создаются. Если папка недоступна, роль сообщает об этом и не заводит новую
  молча; заметки о том, КАК работать, в это время идут в персональную
  память, которая от рабочей папки не зависит.
- **Доступ инструментов.** Рабочая папка - второй разрешённый корень файловых
  инструментов наряду с проектом: путь адресуется префиксом `memory:`
  (`memory:registry.md`) либо абсолютным путём внутри папки. Разрешение
  выполняет `config.to_project_relative` / `resolve_in_project`; всё, что вне
  обоих корней, отклоняется, включая папку другого сотрудника. Инструменты
  работают и в пустом состоянии (проект не выбран): рабочая память не
  зависит от проекта, иначе сотрудник не смог бы прочитать собственный
  реестр до выбора папки.
- **Инъекция в промпт.** `_extend_prompt_with_working_memory` дописывает блок
  `## Working memory` каждому сотруднику: путь, источник и область, схему
  адресации `memory:`, состояние папки и предупреждение о legacy-папке. Путь
  объявляет платформа, поэтому промпт роли его не повторяет - скопированный
  путь устаревает при первом же переносе.
- **Перенос старой раскладки.** `core/memory_migration.py` строит план
  (только чтение) и копирует файлы с проверкой совпадения до отчёта об
  успехе; исходная папка никогда не удаляется модулем. Конфликт (в целевой
  папке уже есть файлы) сообщается, но не разрешается слиянием. Центральный
  корень `agents_data` сам оканчивается на `_data`, поэтому legacy-папкой он
  не считается: распознавание идёт по пути, а не по имени. Иначе установка,
  где `DATA_DIR` совпадает с корнем проекта, принимала бы его за папку
  сотрудника `agents` и предлагала слить данные всех ролей в
  `agents_data/agents/`. Настоящая `<проект>/<slug>_data` рядом с ним
  по-прежнему попадает в план. Точка входа -
  `scripts/migrate_agent_data.py` (по умолчанию dry-run, запись только
  с `--apply`).
- **Каскад и жизненный цикл.** `delete_orchestrator` архивирует личную
  память в `personal/.archive/`; `create_orchestrator`/`save_orchestrator`
  принимают `memory_dir` и хранят его в `config.memory_dir` (пустое значение
  удаляет ключ). Профили структуры данных (ПОТОК / ДЕЛО / ИССЛЕДОВАНИЕ)
  и правило роста папок задаёт 7-я секция инструкции `employee_creator`.

### Внешняя память задач (журнал TASK_STATE__<thread_id>.md)
Для каждой задачи DevAgent ведёт per-thread журнал в скрытой папке проекта
`.dev_agent/task_states/TASK_STATE__<thread_id>.md` (имя содержит ID треда;
ID и путь передаются мета-блоком системного промпта). Файл никогда не
удаляется: по завершении задача архивируется в Task History того же файла,
новая задача в том же треде дописывается туда же. Каждый этап плана может
хранить обобщающий `- context:` (нужен следующему этапу при обрезанной
истории). Журнал автоматически создаётся платформой и инжектится в контекст
перед каждым шагом.

### Изоляция рабочей папки и пустое состояние
Активная папка привязана к потоку диалога: реестр состояний -
`dev_agent/workspace_binding.py` (RLock, `thread_context`, `ensure_thread_active`),
персистентность - мета треда `workspace`/`target_file` в `devagent.db`
(`core/threads_devagent.py`, `storage/repository_devagent.py`). Новый или
сброшенный диалог стартует в пустом состоянии «папка не выбрана»:
`config.NEUTRAL_ROOT` + `WORKSPACE_SELECTED=False`; файловые инструменты
отвечают структурной ошибкой `workspace_not_selected` (guard в
`dev_agent/tool_executor.py` и `dev_agent/universal_agent.py`), а
`run_code`/`run_test` с `code=` выполняются с нейтральным cwd. Два корня
исключены из запрета: рабочий каталог сотрудника (`memory:`) и папка файлов
текущего диалога (`thread:`) - они живут в установке и никогда не зависели от
проекта, поэтому чтение собственных реестров и вложений доступно до выбора
папки. Проверка путей вынесена в `dev_agent/tools/path_scope.py`: предикат
применяется к КАЖДОМУ аргументу-пути вызова, и одного проектного пути в
пакете достаточно для отказа - половина разрешённого пакета прочла бы файл,
который пользователь не открывал. Диалог без
папки или с исчезнувшей папкой открывается пустым; одноразовая миграция
очищает легаси-мету тредов с платформенными корнями. Недавние папки
(`core/recent_workspaces.py`) скоупятся по оркестратору; журналы задач и
вложения диалога при пустой папке живут в `history/<tid>/`.

### Выбор папки в чате ("Выбор папки")
Под полем ввода чата - статичный селектор `ui/pages/orchestrator.py`:
«Авто», до 10 недавних папок оркестратора и последним пунктом нативный
выбор папки (`core/folder_dialog.py`; без GUI пункт скрыт, остаётся ручной
ввод пути). Отдельной кнопки рядом с полем ввода нет: кнопка в этой зоне
читается как «прикрепить файл» (рядом скрепка-загрузчик), поэтому диалог
открывается пунктом-действием внутри селектора (`FOLDER_PICKER_BROWSE`).
Пункт-действие не является значением: после выбора или отмены счётчик
`folder_picker_counter` меняет ключ виджета, и селектор возвращается к
выбранной папке.
Смена папки в селекторе не трогает рабочую папку сразу: путь применяется
автоматически при отправке сообщения (до вызова модели) - `set_workspace`
вызывает UI-слой, а не агент, - после чего селектор возвращается в «Авто», а
активная папка видна под полем. Уже действующая папка повторно не
применяется; отображаемый путь берётся из привязки треда
(`workspace_binding`), поэтому временное переключение папки агентом не
конфликтует с выбором в интерфейсе.

### Панель инструментов чата
Панель рендерится один раз и остаётся липкой сверху: web-поиск, песочница,
safety-режим, защита от инъекций, «Настройки», «Новый диалог», «Копировать
URL». Ключ виджета
чекбокса совпадает с каноническим слотом `orch_<slug>_<pref>`, откуда цикл
агента читает значение, а `_save_chat_pref` персистит его в конфиг
оркестратора (`chat_web_search`, `chat_sandbox`, `chat_safety_mode`,
`chat_injection_guard`).
Переключатели независимы: «Песочница» управляет изоляцией запуска,
«Безопасный режим» - подтверждением опасных команд; снятие одного не
снимает второй. Подсказки панели называют это прямо, потому что связка
неочевидна: пользователь, снявший песочницу, ждёт, что запуск перестанет
спрашивать разрешение, и получает обратное.
Эконом-режим переключателя не имеет: компактный контекст - штатный режим
чата, константа `ECONOMY_MODE_ALWAYS_ON` передаётся в `AgentLoopState` и в
расчёт строки токенов всегда. Исторический ключ конфига
`chat_economy_mode` больше не читается, поэтому сохранённое в старых
установках значение не может выключить режим.

### Файлы во вводе чата
Загрузчик вложений встроен в само поле ввода: `ui/pages/orchestrator.py`
вызывает `st.chat_input(accept_file="multiple")` - Streamlit показывает
иконку-скрепку с всплывающей подсказкой, а результат приходит объектом с
полями `.text` и `.files`. Отдельный блок `st.file_uploader` и подпись
«Прикрепить файлы любого формата…» удалены, как и пред-отправочные чипы
вложений. Хелпер `_split_chat_prompt` нормализует ответ виджета в пару
`(text, files)`, поэтому отправка срабатывает при непустом тексте ИЛИ
непустом списке файлов. Байты файлов сохраняются в `history/<tid>/files`
без разбора (лимит `MAX_THREAD_FILE_BYTES` - 100 МиБ на файл), а если текста
нет, задачей становится i18n-строка `orch_attach_only_message` с именами
вложений.

Чтение вложений штатное, без обхода через `run_code`: `read_thread_file`
извлекает текст документов через `core.document_text` (PDF, DOCX, PPTX,
XLSX, XLS, RTF, ODT, HTML), а `read_document` делает то же самое для любого
файла на диске по абсолютному пути с окном строк. `run_code` помечен в
каталоге как средство последней очереди - текстовые и документные форматы
читаются специализированными инструментами.

Картинки документа читаются отдельным шагом. `extract_document_images`
(`UniversalDevAgent._extract_document_images`, ядро -
`core/document_images.py`) достаёт встроенные изображения из PDF, DOCX,
PPTX и XLSX, раскладывает их файлами PNG в
`<проект>/.dev_agent/doc_images/<документ>-<хеш>/` и возвращает манифест
без base64: привязку к странице/слайду/листу, размеры, предупреждения и
готовые группы `batches` по 5 путей - столько `analyze_image` принимает за
один вызов. Распознавание остаётся за `analyze_image`, который возвращает
текст, обёрнутый в `DATA_BEGIN: DATA_FROM_IMAGE`; инструмент лишь готовит
файлы. Для сканов есть рендер страниц (`ocr='auto'` - только когда у PDF
нет ни текстового слоя, ни извлекаемых картинок, `ocr='force'` - всегда):
рендер страницы замещает встроенные картинки той же страницы, поэтому один
и тот же материал не оплачивается дважды.

### Авто-прокрутка ленты чата
Лента истории растёт под липкой нижней панелью (блок «Выбор папки» + поле
ввода + тулбар, `st.bottom`). Пока агент работает, `ui/pages/orchestrator.py`
эмитит в `_render_chat_tab` клиентский скрипт `core.feed_autoscroll` через
`st.html(unsafe_allow_javascript=True)`: скрипт исполняется в главном
документе, поэтому видит скролл-контейнер приложения (устаревший
`st.components.v1.html` работал в песочнице iframe, до контейнера не доставал
и на каждый вызов писал предупреждение об удалении). Скролл-контейнер
ищется по `[data-testid="stAppScrollToBottomContainer"]` и `#stMain` - в
Streamlit 1.66 это узел `main`, где тестид перекрывает `stMain`, а класса
`section.main` нет; берётся первый реально прокручиваемый элемент. Скрипт
единожды вешает слушатели `scroll`/`wheel`/`touchmove` на родительское окно
и хранит флаг паузы в `sessionStorage` (переживает повторный вывод скрипта
на каждом rerun). Ручная прокрутка вверх (> порога
`AUTOSCROLL_THRESHOLD_PX`) ставит слежение на паузу, возврат к низу -
возобновляет. При отправке сообщения флаг `scroll_bottom` форсирует один
прокрут вниз независимо от паузы. Отступ снизу модуль не задаёт: Streamlit
1.66 сам резервирует место под липкой нижней панелью, а ручной
`padding-bottom` давал двойной отступ и большую пустоту в ленте.

### RAG: локальные базы знаний
Индексация локальная (SQLite: собственный BM25-индекс + опциональные
векторы), эмбеддинги - удалённо через Yandex Embeddings API (BYOK, режимы
vector/hybrid). Базы хранятся в `DATA_DIR/rag_bases/`.

### Коннекторы
- **`core/connectors.py`** - CRUD подключений: папка
  `DATA_DIR/connectors/<id>/manifest.json`; токен шифруется через
  `core.crypto.encrypt` и не попадает в публичные представления.
- **`core/github_connector_rest.py`** - единственный прямой REST-коннектор
  (requests, REST API v3, `X-GitHub-Api-Version: 2022-11-28`, Bearer).
  Реализует repo CRUD, чтение/запись файлов и метаданных, плюс Git Data API:
  `get_ref`, `get_commit`, `get_tree`, `create_ref` (произвольный ref -
  ветка или тег) и `create_tag` (лёгкий или аннотированный через
  `POST /git/tags`), а также оптимизированная пакетная публикация
  `batch_commit` (blobs -> одно дерево с чанкингом по 9000 записей -> один
  коммит -> PATCH ref; ветка создаётся через POST /git/refs для пустого
  репозитория) и `batch_upsert` (дифф по blob-SHA с пропуском неизменённых).
  Ошибки - `GithubRestError` (наследник ValueError) со статусом; токен
  расшифровывается внутри модуля и не попадает в результаты/ошибки.
- **`core/github_tools_rest.py`** - инструменты `ghr_*` (18 штук:
  `ghr_list_repos`, `ghr_create_repo`, `ghr_read_file`, `ghr_upload_file`,
  `ghr_update_file`, `ghr_delete_file`, `ghr_list_files`, `ghr_batch_commit`,

- **Пресеты (`core/connector_presets.py`)** - шаблоны без секретов из

  (`core/orchestrator_tools.py`); статические и динамические

- **UI**: `ui/pages/connectors.py` - страница по модели
  `список ↔ форма` (как страница помощников): режим страницы лежит в
  `session_state` (`connectors_view` = `list` | `create` | `edit`), и
  форма ЗАМЕНЯЕТ список на той же странице, а не открывается в
  экспандере или на другой вкладке.
  Список - три вкладки («General services», «MCP servers»,
  «Connections»). `st.tabs` создаётся stateful: `on_change="rerun"`
  делает вкладки виджетом с состоянием, `key` даёт стабильную
  идентичность, а `default=<метка>` переключает вкладку по запросу.
  Без `on_change="rerun"` (значение по умолчанию) виджет состояния не
  хранит вообще, поэтому любой rerun открывал первую вкладку, и
  переключение из кода было невозможно; хранимое значение сбрасывается
  ДО создания виджета - единственный момент, когда Streamlit разрешает
  менять состояние виджета.
  «General services»: плитки сервисов с иконкой и описанием
  (github_rest, ssh; `mcp` исключён) - клик только открывает форму
  создания, в БД ничего не пишется. «MCP servers»: плитки пресетов
  рядами по три (иконка + имя + описание; встроенные и поставленные из
  маркетплейса) и плитка «+ Свой
  MCP-сервер»; клик открывает ту же форму с конфигурацией пресета и

  command/args/env_json или http url/auth_header/env_json).
  «Connections»: карточки ВСЕХ сохранённых подключений с иконкой
  сервиса, индикатором учётных данных, предупреждением о pending,
  тестом (запуск сервера/опрос HTTP-эндпоинта и каталог
  инструментов), редактированием и удалением.
- **Создание и редактирование в UI:** форма `create` собирает имя,
  аккаунт и поля сервиса/пресета и вызывает `create_connection` (или
  `instantiate_preset(..., pending=False)`) ТОЛЬКО по кнопке «Создать»,

  без промежуточного черновика. Форма `edit` вызывает
  `update_connection` по «Сохранить». «Отмена» и «← Назад»
  возвращают к списку, не записывая ничего; после сохранения список
  открывается на вкладке «Connections» через `default`. Ошибка
  сохранения оставляет форму открытой с введёнными значениями.
  Черновики `pending`, созданные DevAgent из чата
  (`instantiate_preset` по умолчанию `pending=True`), заполняются
  через ту же форму кнопкой «Заполнить учётные данные».
- **Ошибки MCP HTTP:** код 401/403 дополняется подсказкой о
  credentials - для эндпоинта GitHub Copilot классические PAT
  `ghp_*` не поддерживаются, нужен fine-grained `github_pat_*`; тело
  ответа (первые 300 символов) включается в сообщение, секреты не
  раскрываются.
- **Инструкция `mcp_connector`** (встроенная DevAgent) - флоу работы с
  MCP-подключениями: пресеты, черновики и заполнение учётных данных
  пользователем, http-транспорт, правила безопасности.

### Загрузка ключей из shell-профилей
`env_loader` читает ~/.zshrc и др., не перезаписывает существующие.

### Универсальный разработчик
PROJECT_MAP.md, AGENT.md, ARCHITECTURE.md, CHANGELOG.md, снапшоты. Перед
началом работы над проектом читается `AGENT.md` (ключевая информация для
агентов), затем `PROJECT_MAP.md` (файлы и
ответственность); финальный отчёт завершается
секцией «Documentation» с перечнем документов, требующих обновления.
Карта проекта - генерируемый документ: состав ограничен публикуемыми файлами,
sha256-отпечаток шапки сигнализирует об устаревании, ручная правка запрещена -
обновление только регенерацией.

### Каталог инструментов и gating (`core/orchestrator_tools.py`)
Блок `## Available tools` добавляется к промпту каждого оркестратора
(`_extend_prompt_with_tools` -> `render_available_tools_block`) и перечисляет
доступные инструменты (core, workspace, подключения, кастомные функции).
Каноничные промпты (`dev_agent/system_prompt.md` v3.30, YaAgent v2.11) не
дублируют этот справочник: их раздел справочника ссылается на
автоматический блок, оставляя в промпте только собственные правила
использования инструментов (форматы вызова, fallback-цепочки).
Чёрный список `config['disabled_tools']` исключает инструменты из каталога,
а диспетчер (`dev_agent/universal_agent.py`) блокирует их вызов ошибкой
`disabled: true` (гейт до выполнения; legacy-алиасы в обе стороны). Вкладка
Функции показывает системные функции с чекбоксами и кнопкой Сохранить.

### Текущая дата в системном промпте (`core/orchestrators.py`)
Модель не имеет часов: без явной даты любой ответ про «сегодня», «завтра»
или «на этой неделе» - догадка либо чтение файла, который записал дату
СОЗДАНИЯ, а не текущую. Роль, ведущая сводку расписания, устаревает молча:
файл выглядит авторитетно и продолжает отвечать за прошедший день.

Блок `## Current date` дописывает `_extend_prompt_with_current_date` - для
КАЖДОГО сотрудника, поэтому роль не носит дату в собственном промпте и не
расходится с ней. Блок состоит из факта и не содержит правил использования:
системный промпт и без того велик, а сама формулировка не требует пояснений.

- **Формулировка.** `Today is Monday, 02 November 2026.` - день недели и
  месяц названы словами (`WEEKDAY_NAMES`, `MONTH_NAMES` из
  `core/prompt_blocks.py`), а не выведены
  через `strftime('%A')`: локаль процесса не должна менять текст промпта.
  Вторая строка - `Installation timezone: MSK (UTC+03:00).`
- **Положение.** Блок добавляется ПОСЛЕДНИМ, после каталога инструментов.
  Это единственный блок, меняющийся со временем: когда он стоит в хвосте,
  смена суток инвалидирует только хвост префикса провайдерского кэша, а не
  весь промпт.
- **Только дата, без времени суток.** Времени в блоке нет намеренно: метка
  с точностью до минуты ломала бы кэш префикса на каждом шаге. Время суток
  и точный день недели для произвольного момента отдаёт инструмент.
- **Выключатель.** `config['current_date_enabled']` (булево либо строка
  `'false'`/`'no'`/`'off'`/`'0'`) убирает блок у конкретного сотрудника;
  по умолчанию блок включён. Выключатель действует только на промпт и не
  влияет на инструмент.
- **Инструмент `current_datetime`** (`dev_agent/tool_executor.py`) отвечает
  на вопросы, которые факт решить не может: время суток, день недели
  заданной даты, сколько дней до срока. Он читает те же таблицы имён и ту же
  функцию `_current_date_line`, поэтому промпт и инструмент не могут
  разойтись. Ответ: `iso`, `date` (`ДД.ММ.ГГГГ`), `date_iso`, `weekday`,
  `weekday_ru`, `time`, `timezone`, `utc_offset`, `epoch`, `date_line`.
  `disabled_tools` убирает инструмент из каталога, оставляя блок даты.
- **Отношение к файлам памяти.** Дата берётся только из системного времени.
  Сводки, кэши и журналы (`TODAY.md` и подобные) дату своего создания не
  задают: роль сравнивает их дату с блоком и при расхождении считает файл
  устаревшим.

### Мультиагентная оркестрация (`core/orchestration/`)
Запуск агента из агента описан единым контрактом, отделённым от UI и от
цикла оркестратора. Пакет `core/orchestration/` держит четыре слоя:

- **`contracts.py`** - типы конвейера: `AgentBrief` (цель, ограничения,
  входные артефакты `Dict[str, str]`, критерии готовности), `SpawnRequest`
  (`agent_slug`, `brief`, `parent_run_id`, `depth`), `InvokeRequest`
  (`system`, `user`, `context_files`, `parent_run_id`), `Artifact`,
  `AgentRunResult` (`run_id`, `status`, `stop_reason`, `summary`,
  `artifacts_out`, `steps_used`, `error_code`) и `CancelReport`. Все
  структуры сериализуются в dict: результат инструмента уходит в ленту как
  данные, а не как объект.
- **`invoke.py`** - `invoke_once()`: один вызов модели без цикла
  инструментов, без RAG и без доступа к файлам. Контекст передаётся
  вызывающим явно (`context_files` -> блоки `### File: <name>`); документ
  (PDF, DOCX, PPTX, XLSX, RTF, ODT, HTML) читается через
  `core.document_text`, поэтому один файл - это один вызов, без дробления
  текста на части. Нечитаемый файл попадает в `skipped_files`, а не
  срывает вызов. Сервис и модель резолвятся по конфигурации родителя.
- **`service.py`** - `OrchestrationService`: реестр запусков и их дерево.
  `ensure_run()` регистрирует корневой запуск диалога, `run()` запускает
  ребёнка, `cancel(cascade=True)` отменяет поддерево, `subscribe()` отдаёт
  события в ленту, `release_tree()` освобождает записи и семафоры после
  завершения диалога. Идентификаторы: `run_id` - уникальный, тред ребёнка -
  производный `{parent}__s{run_id[:8]}` (свой журнал, рабочая папка
  родителя). Запуск ребёнка собирается в `child_runner.py`, чистые
  помощники бутстрапа - в `child_text.py`; фасад реэкспортирует их, поэтому
  вызывающий код по-прежнему работает через `core.orchestration.service`.
- **`child_runner.py`** - дочерняя сторона запуска: собирает диспетчер
  ребёнка с суженным каталогом инструментов и его вызовом провайдера,
  открывает приёмник транскрипта и область журнала, восстанавливает
  состояние резюма, прокручивает цикл ребёнка, пересылает его события в
  ленту родителя и превращает итоговое состояние в `AgentRunResult`, где
  припаркованный вопрос отличается от незавершённого запуска.
- **`child_text.py`** - чистые помощники бутстрапа ребёнка без состояния
  сервиса: производный тред ребёнка и его папка файлов, текст задачи
  ребёнка с уже разрешённой папкой загрузок - одни и те же строки для
  запуска и для резюма.
- **`tools.py`** - обёртки инструментов `spawn_agent`, `invoke_assistant`,
  `cancel_subagent` и `read_subagent_thread` с правами доступа:
  `agent_not_allowed`, `unknown_agent`, `assistant_not_allowed`,
  `unknown_assistant`, `invalid_args`, `not_implemented`, `not_your_run`.
  Права проверяются до захвата ресурсов, поэтому отклонённый вызов не
  занимает слот пула.
- **Управление запущенным ребёнком.** `cancel_subagent` не ждёт бюджета
  запуска, а ставит флаг отмены в записи (`cancel_reason`), который цикл
  ребёнка проверяет на границах шагов: вызов инструмента, уже начатый,
  завершается, после чего запуск и его потомки (`cascade`) уходят в
  `cancelled`. `read_subagent_thread` читает переписку ребёнка из
  файлового хранилища транскриптов (`core.orchestration.transcript_reader`),
  подставляя `child_thread_id` из записи запуска: журнал показывает план, а
  переписка - что ребёнок реально сказал и вызвал. Ребёнок со строкой, но
  ещё без файла переписки отвечает пустым окном с пояснением (он не сделал
  ни шага, а не «не существует»); ребёнок без строки индекса - кодом
  `resume_unavailable` и указанием читать журнал, потому что файл без
  строки недостижим для любого читателя. Оба инструмента адресуют
  только запуски своей корневой ветки (`_resolve_run_root` + `_confine_run`),
  чужой запуск отвечает `not_your_run`; отмена уже завершённого - успешный
  ответ `cancelled=false`, чтобы модель не повторяла вызов.

**Хранилище транскриптов (`dev_agent/transcript.py`).** Переписка ребёнка не
ложится в `devagent.db`: у производного треда нет строки диалога, а общий
SQLite превратился бы в узкое место, как только десяток субагентов пишет
одновременно. Вместо этого каждый шаг ребёнка дописывается в файл
`<history>/<parent>/subagents/<child>/transcript.jsonl` - по строке на
запись, `O_APPEND` под локом на путь. Такой формат даёт три свойства, ради
которых он и выбран: запись не блокирует чтение других тредов, обрыв
процесса портит максимум последнюю строку, а объём ограничен диском, а не
базой. Строка содержит только переписку (роль, содержимое, вызовы
инструментов); префикс `__DEVAGENT_EVENTS__` с событиями рендера
отбрасывается - это данные UI, а не история, и на реальных замерах они
занимали около половины объёма сообщения.

Сегменты ротируются по размеру (`transcript.N.jsonl`) и сжимаются в `.gz`,
когда перестают быть активными; номер сегмента сохраняется при сжатии,
поэтому порядок чтения не зависит от суффикса, а читатель открывает `.gz`
прозрачно через `gzip`. Сжатие не считается активностью: сегмент сохраняет
время последней реальной записи, иначе тред выглядел бы свежим после каждой
уборки и никогда не вышел бы из окна хранения. Ретеншен (`sweep`) по
умолчанию работает в режиме отчёта, режет только целые холодные сегменты
самых тихих тредов (активный файл неприкосновенен) и сообщает о папках, чья
строка в индексе исчезла, вместо того чтобы удалять их молча: в такой папке
могут лежать загрузки, которые пользователь ещё откроет.

**Переход на новый формат базы (`core/devagent_db_archive.py`).** База,
написанная до появления файлового хранилища, хранит текст переписки внутри
себя, и эти две раскладки не могут жить в одном файле. Переписывать сотни
мегабайт на месте рискованно, поэтому переход сделан заменой: старый файл
уходит в архив рядом с собой, новая пустая база создаётся заново. Ничего не
теряется - архив содержит полную прежнюю базу целиком, а одноразовое
уведомление при запуске называет его путь и число сохранённых диалогов; без
этого сообщения пустой список диалогов читался бы как потеря данных.

Раскладка помечается в заголовке самого файла (`PRAGMA user_version`): `0` -
запись до файлового хранилища, `1` - текущая. Устаревший файл без диалогов в
старой раскладке (пустая база или все треды уже с путём к транскрипту) просто
помечается на месте и остаётся - архив оправдан только реальной разницей
раскладок, поэтому повторный запуск ничего не трогает.

Деструктивная часть подчинена двум правилам. Архив проверяется до удаления
оригинала (член на месте, размер совпадает, `testzip` проходит), а пишется
через временный файл с `os.replace`, так что падение на любом шаге оставляет
либо прежнее состояние, либо целый архив. Копирование и замена идут под
эксклюзивной блокировкой SQLite, а `wal_checkpoint` выполняется отдельным
соединением ДО неё: внутри `BEGIN EXCLUSIVE` SQLite отказывает в чекпоинте, и
молча пропущенный чекпоинт - это ровно тот случай, когда сообщения, живущие
только в `-wal`, не попадают в копию основного файла. База, заблокированная
другим запущенным экземпляром, отменяет переход, а не гоняется с ним. Если
рядом уже лежит побайтово совпадающий архив (сверяются размер и CRC-32
члена), он переиспользуется вместо второй копии.

**Переход основной базы (`core/chat_db_archive.py`).** Главная база устроена
иначе: в ней кроме переписки живут помощники, настройки, подключения и реестр
маркетплейса, поэтому замена файла здесь недопустима - пользователь потерял бы
всё, кроме диалогов. Переход сделан переносом: файл целиком пакуется в
проверенный zip рядом с собой (оригинал остаётся на месте), каждый диалог
пишется в свой транскрипт под одной блокировкой записи, индексные колонки
заполняются, и только после этого перенесённые строки `messages` удаляются.
Отказ на любом шаге - нечитаемый архив, занятая блокировка, ошибка записи
транскрипта - оставляет строки в таблице, а неперенесённый диалог продолжает
читаться из неё как раньше. Раскладка помечается в `PRAGMA user_version` той же
схемой, что и у `devagent.db` (`0` - до файлового хранилища, `1` - текущая),
поэтому повторный запуск ничего не делает. Одноразовое уведомление называет
путь архива и число перенесённых диалогов.

**Индекс.** Тред ребёнка получает строку в таблице `threads` сразу при
связывании (`bind_child_thread`), с `kind="subagent"`,
`parent_thread_id`, рабочей папкой и относительным `transcript_path`. Это
не строка диалога: `repo_devagent_list_threads` отбирает только
`parent_thread_id IS NULL`, поэтому ребёнок не появляется в списке
диалогов. `transcript_sink` дальше только обновляет счётчики и путь, а
читатель (`transcript_reader`) адресует переписку именно через эту строку -
файл без строки недостижим, поэтому её создание вынесено на момент
связывания, а не на первый закрытый шаг. Строка нужна и ретеншену, чтобы
отличить живой тред от осиротевшей папки.

**Восстановление.** Чекпоинт (номер шага, записанные файлы, статус) пишется
в тот же файл отдельной записью, поэтому упавший ребёнок восстанавливается
из двух источников: переписка отвечает «что он делал», чекпоинт - «где
остановился». `resume.build_resume` получает чекпоинт через инъекцию
`read_checkpoint` и добавляет к подсказке шаг и уже созданные файлы, чтобы
продолжение не переписывало готовое. Оборванная последняя строка
пропускается при чтении: потерять один шаг лучше, чем весь тред.

**Лимиты делегирования** хранятся в конфигурации оркестратора и читаются
через `get_delegation_limits(slug)` (шесть ключей): `max_depth` - глубина
дерева от диалога (0 - делегирование запрещено, по умолчанию 1),
`max_active_subagents` - одновременные дети и одноразовые вызовы (семафор
дерева; по умолчанию 5, чтобы веер из 4-7 агентов не упирался в четвёртый
запуск), `subagent_max_steps` - шагов на ребёнка (по умолчанию 300; выше
реального расхода, чтобы связывающим ограничением был бюджет времени, а не
счётчик), `total_subagent_runs` - суммарное число запусков в дереве (по
умолчанию 64), `subagent_timeout_seconds` - сколько ребёнку разрешено
работать (по умолчанию и не более часа: дольше родитель всё равно не
прождёт), `subagent_budget_tokens` - потолок токенов ребёнка (0 - без
потолка). Сеттер кламп-ит значения к допустимому диапазону: нулевой пул
защёлкнул бы первый же запуск.

**Права.** `spawn_agent` доступен всегда (делегирование самому себе
структурно), `invoke_assistant` появляется в каталоге только при непустом
`allowed_assistants`; `allowed_agents` перечисляет сотрудников, которым
разрешён запуск. Само-слаг в списке не хранится, а список помощников
сверяется с живыми карточками при записи, поэтому удалённый помощник не
остаётся в правах. Каталог инструментов и диспетчер читают один и тот же
источник, так что модель не получает инструмент, который будет отклонён.

**Fan-out.** В фазе `executing` цикл группирует независимые вызовы
`spawn_agent`: сначала проверяются права и аргументы всего набора, затем
захватываются слоты пула и дети выполняются параллельно; события
помечаются `run_id` ребёнка, и лента группирует их по запускам. Дочерний
запуск получает собственное связывание рабочей папки и собственный журнал
задач, а по завершении освобождает и то, и другое.

**Задание субагенту.** `_build_child_task_text()` собирает текст запуска из
цели, брифа и входных артефактов и добавляет блок «Контекст запуска» с
АБСОЛЮТНЫМИ путями: рабочая папка родителя и папка файлов диалога родителя
(`history/<thread_id>/files`). Субагент стартует с чистым контекстом, его
собственный диалог не содержит вложений родителя, поэтому относительный путь
или имя файла без каталога для него - тупик; описание `spawn_agent` требует
абсолютные пути прямо в контракте.

**Блок делегирования в промпте.** `_extend_prompt_with_delegation()` в
`core/orchestrators.py` собирает до трёх разделов: `## Available agents
(spawn_agent)` - сам сотрудник (самоделегирование разрешено всегда) плюс
`allowed_agents` с именами; `## Available assistants (invoke_assistant)` -
`allowed_assistants` с id и именами карточек и напоминанием передавать документ
файлом в `context_files`; `## Verifying delegated work` - правило проверки
результатов веера. Раздел помощников появляется только при непустом списке,
поэтому промпт не обещает вызов, который среда отклонит. Тексты разделов живут
в `core/prompt_blocks.py`, сборка - в `_agent_delegation_lines`,
`_assistant_delegation_lines` и `_verify_delegation_lines`.

**Проверка результата веера.** Веер даёт N результатов за один шаг, но не
проверку: сводку ребёнка родитель принимает на слово. Отдельный шаг после
веера закрывает разрыв - `verify_result(run_id, criteria)` в
`core/orchestration/verify.py` запускает агента-верификатора и возвращает
`Verdict{target_run_id, verifier_run_id, verdict, reasons, checked, summary}`.
Вердикт принимает три значения (`passed`, `failed`, `inconclusive`), и
`inconclusive` - честный ответ «проверить не удалось», а не ошибка: родитель
не вправе выдать его за успех.

Независимость обеспечена тем, что верификатор НЕ видит: на вход идут
`summary`, артефакты (путь, вид, digest), `error_code`, `steps_used`,
`tokens_used` и критерии, но не транскрипт и не журнал целевого запуска.
Проверяющий, читающий ход мысли исполнителя, соглашается с ним вместо
проверки результата; содержимое артефактов он читает своими инструментами по
абсолютному пути. `build_verifier_brief` собирает бриф из `AgentRunResult`,
который по контракту переписку не несёт, поэтому граница задана типом, а не
соглашением.

Разбор ответа (`parse_verdict`) консервативен: ищется последний разбираемый
JSON-объект (модель может предварить его рассуждением); отсутствие JSON,
неизвестное значение вердикта и `reasons` не-списком дают `inconclusive`;
`passed` при непустых `reasons` превращается в `failed` - правило не даёт
подписать результат и в том же ответе перечислить его дефекты.

Порядок отказов задан контрактом и проверяется до запуска: пустой `run_id`
(`invalid_args`), неназначенный верификатор (`verifier_not_configured` -
агент по умолчанию не подставляется, иначе молчаливая подстановка скрыла бы,
что проверять некому), неизвестный запуск (`run_not_found` - код `poll`),
незавершённый запуск (`run_not_finished` с текущим статусом) и запуск-
верификатор (`invalid_args`). Проверка проверки распознаётся по слагу агента
и по маркеру цели `VERIFIER_GOAL_PREFIX`, поэтому переназначение настройки не
открывает обходной путь; в каталоге ребёнка инструмент выключен
(`CHILD_DISABLED_TOOLS`).

Запуск идёт через `service.run` - тем же путём, что `spawn_agent`, поэтому
глубина, пул и суммарные запуски действуют как для любого ребёнка. Дерево
берётся из треда целевого запуска (или из его корня): верификатор,
повешенный на другое дерево, сбрасывал бы лимиты при каждой проверке. Сбой
верификатора не ломает веер - ответ `ok: true` с вердиктом `inconclusive` и
кодом сбоя в причинах; `ok: false` остаётся только за нарушениями контракта.

Инструмент виден лишь при непустом `verifier_agent` (геттер/сеттер рядом с
`allowed_agents`, слаг не обязан входить в список вызываемых - право
проверять отдельное), а в промпт добавляется абзац
`## Verifying delegated work`. Вызов исполняется в фазе веера
(`_TREE_CALL_NAMES`), а не внутри `dispatch`: запуск ребёнка под
захваченной блокировкой связывания рабочей папки дал бы клинч.

**Раскладка инструментов по темам.** Пакет инструментов делегирования
вырос до 1770 строк в одном модуле, и держать в нём пять несвязанных тем
стало дороже, чем разделить. Реализация живёт в модулях `tools_*`,
нарезанных по теме: `tools_rights` (кого можно вызывать), `tools_records`
(чтение записи запуска и проверка видимости), `tools_spawn` (запуск
ребёнка и одноразовый вызов помощника), `tools_status` (отчёт о
состоянии), `tools_journal` (чтение транскрипта), `tools_control` (отмена
и продолжение), `tools_dialog` (протокол вопросов), `tools_wait`
(ожидание), `tools_notes` (текст, который несёт результат), `tools_catalog`
(записи каталога). Константы вынесены в `tools_constants`.

`core/orchestration/tools.py` остался ФАСАДОМ на 155 строк: он
реэкспортирует все 45 имён и не содержит ни одной своей функции. Это не
косметика - фасад остаётся единственным местом, где имена СВЯЗАНЫ.
Цикл агента и каталог импортируют инструменты оттуда, а тесты подменяют
`tools.spawn_agent` и `tools.time`; локальная ссылка в модуле реализации
заморозила бы оригинал и подмена стала бы невидимой. По той же причине
часы читаются через `tools_clock`, который берёт атрибут фасада в момент
вызова, а `resume_subagent` обращается к `spawn_agent` через фасад, а не
через импорт. Обратный импорт - из модуля реализации в фасад на уровне
модуля - закрыл бы цикл, поэтому он запрещён и проверяется тестом.

### Фоновые субагенты: наблюдение, извещения и продолжение

Блокирующий `spawn_agent` удобен, когда результат нужен сразу, но два
исследования по разным модулям складываются в сумму ожиданий. Поэтому запуск
умеет работать в фоне, а диалог - наблюдать за ним и продолжать его.

**Durable store (`runs.py`).** Запись запуска (`start`, `heartbeat`,
`finish`) пишется атомарно в `<runtime>/orchestration/runs/<root_run_id>/`;
имя файла начинается с миллисекундной метки, поэтому записи одного запуска
сортируются по имени, а дубликаты, появившиеся при гонке двух писателей,
убираются при сохранении (остаётся самый свежий). Чтение применяет `heal()`:
признаки мёртвого `running` - heartbeat старше
`max(STALE_MIN_SECONDS, timeout + STALE_GRACE_SECONDS)`, чужой `boot_id`
(процесс перезапущен) или отсутствующий `pid`. Окно нарочно равно ОДНОМУ
бюджету запуска плюс запас: умножение бюджета на два делало часовой запуск
неотличимым от зависшего ещё на час. Heartbeat освежается по ходу
шага ребёнка (не чаще раза в минуту), поэтому здоровый долгий запуск не
попадает под вердикт о зависании. Такой запуск переводится в
`failed/stale_run`, а причина сохраняется в записи, чтобы оператор отличал
падение от зависания. `prune_root()` и `remove_older_than()` чистят историю
лениво, при старте сервиса, а не на пути завершения воркера.

**Вердикт живости (`is_live`, `liveness_window`, `demote_if_dead`).**
Ремонт файла ждёт целый бюджет запуска, а статус нужно показать сразу,
поэтому у читателя отдельное и гораздо более короткое окно
(`max(STALE_MIN_SECONDS, 3 x HEARTBEAT_INTERVAL_SECONDS)`). Запись
`running`, у которой нет живого двойника в реестре процесса, - остаток
умершего потока, и выдавать её за идущую работу нельзя. Вердикт не пишет
на диск: `demote_if_dead` возвращает копию записи с `failed/stale_run` и
`stale_reason=unverifiable`, а сам файл чинит `heal()`, когда heartbeat
станет однозначно мёртвым. Живой двойник в реестре - более сильный
признак, чем любая метка времени: блокирующий ребёнок держит запись в
памяти до возврата, поэтому таймер heartbeat заводится только фоновому
запуску - иначе долгий вызов инструмента выглядит как зависание. На
старте процесса `sweep_dead_runs()` один раз проходит по всему хранилищу
(`list_runs(limit=0)`, без потолка в 50 записей) и чинит записи прошлых
процессов: после перезапуска их потоки не существуют.

**Корневой запуск диалога (`close_root_run`).** Корень - это ОДИН шаг
диалога, и воркера, который написал бы ему финальный статус, нет. Без
явного закрытия запись оставалась `running` на диске навсегда, и строка
«работают субагенты» переживала завершение шага. `release_tree()` поэтому
сначала закрывает корень (`done/completed`), и только затем решает,
отложить ли освобождение из-за живых детей. Идентификатор диалога
переживает шаги, поэтому `ensure_run()` переоткрывает терминальную
корневую запись (`running`, чистые `stop_reason`/`error_code`/`summary`,
свежие метки): иначе следующий шаг унаследовал бы статус предыдущего.

**Сервис.** `start()` создаёт запись и запускает воркер в отдельном потоке,
`poll()` отдаёт запись без блокировки, `wait()` ждёт терминального статуса с
таймаутом. Ящик извещений живёт в дереве (`post_notification`,
`take_notifications`, `has_notifications`), а право опубликовать извещение
захватывается один раз атомарным `claim_notice` (`O_CREAT | O_EXCL`):
одинаковый статус не может быть показан дважды ни воркером, ни UI.

**Извещение в диалоге.** `drain_subagent_notices(state)` вызывается в фазе
`calling_llm` и переносит почту дерева в скрытое system-сообщение
`[SUBAGENT_NOTICE:<run_id>:<status>]` (`role=system`, `hidden=True`,
`_notice=True`). Родитель узнаёт о завершении ребёнка на ближайшем вызове
модели, а не шагом позже, и шаг при этом не уходит в `awaiting_user`:
видимой реплики пользователя не появляется.

**Продолжение (`resume.py`).** `build_resume()` собирает продолжение из
журнала ребёнка, прочитанного по абсолютному пути из записи запуска -
штатное чтение журнала резолвит файл от активного треда процесса и вернуло
бы журнал родителя. Заголовки шагов нормализуются (план пишет
`### Step 2 - ...`, прогресс - `- [~] Step 2 - ... (status: ...)`), поэтому
сравнение «сделано / осталось» не зависит от формы записи. Готовые шаги
уходят в «Already done, do NOT redo», незавершённые - в «Still pending»,
подсказка обрезается до `MAX_HINT_CHARS = 1200`. Запуск без цели и без
незавершённых шагов отклоняется (`resume_unavailable`), а не продолжается
вслепую. Новый запуск наследует `root_run_id`, глубину и счётчики
(`resumed_from`, `resume_depth`), поэтому бюджет дерева расходуется дальше,
а не обнуляется; цепочка продолжений ограничена `MAX_RESUME_CHAIN = 2`
(`resume_chain_limit`).

**Инструменты наблюдения (`tools.py`).** `subagent_status` отвечает на три
вопроса одним вызовом - один запуск, всё дерево (`root_run_id`) или
ожидание терминального статуса до `MAX_STATUS_WAIT_SECONDS = 30` секунд;
истёкшее ожидание возвращается как `timed_out`, а не как ошибка.
`read_subagent_state` отдаёт журнал ребёнка (по разделам, до
`MAX_STATE_CHARS = 6000` символов). `resume_subagent` принимает
необязательный `request` - без него продолжается исходная цель.

**Сбор результата (`subagent_result`).** `subagent_status` отвечает на
вопрос «что происходит», а не «что произведено»: его запись - это
бухгалтерия запуска, где `summary` усечена до 2000 символов ради файла,
перезаписываемого на каждом heartbeat, а `artifacts` отсутствуют вовсе.
Поэтому тело результата отдаёт отдельный инструмент
`subagent_result(run_id, wait_seconds=0)`:

- **Одна форма.** Ответ собирается через `AgentRunResult.to_dict()` - тот же
  объект из 12 полей, который возвращает блокирующий `spawn_agent`
  (итоговый текст, артефакты, `steps_used`, `tokens_used`, `error_code`,
  `retryable`). Две формы одного ответа заставляли бы модель угадывать, что
  она читает.
- **Незавершённый запуск результата не отдаёт.** Ответ - `ready=false`,
  текущий статус и запись запуска, причём ключа `result` в нём НЕТ: пустое
  поле подставилось бы под «результат», а отсутствующее - нет. Частичная
  работа, выданная за результат, выглядит как успех и потому опаснее
  явной ошибки; `awaiting_input` дополнительно отправляет в журнал и
  `resume_subagent`, а не в «результат».
- **Ограниченное ожидание.** `wait_seconds` усекается тем же
  `MAX_STATUS_WAIT_SECONDS = 30`; таймаут не ошибка - он возвращает
  `ready=false` со свежим состоянием, поэтому опрос по кругу не нужен.
- **Результат переживает реестр.** `RunRecord.to_record()` добавляет
  вложенный объект `result` (полный `summary`, `artifacts`, ресурсы), когда
  запуск терминален: пока запуск жив, запись переписывается на каждом
  heartbeat и остаётся компактной, а терминальная пишется один раз. Обратное
  преобразование живёт в ОДНОМ месте - `contracts.result_from_record`,
  которым пользуются и сбор результата, и верификатор, поэтому ответ не
  зависит от того, пришёл он из реестра или с диска. Старая запись без
  вложенного объекта читается по верхнеуровневым полям, а инструмент честно
  помечает `note`, что сводка могла быть усечена, вместо того чтобы выдать
  её за полную.
- **Та же граница прав.** `_confine_run` до чтения: запуск чужой ветки
  отвечает `not_your_run`, неизвестный - `run_not_found` (а не «не готово»:
  это разные решения).

**Ожидание (`sleep`).** Вместо холостых вызовов `subagent_status` родитель
может заснуть до события или таймаута: `sleep(seconds=..., until=...)`
блокирует шаг, а сколько именно ждать, решает вызывающий - ребёнок это
полноценный агент, а не команда, и он может работать десятки минут. Потолок
`MAX_SLEEP_SECONDS = 3600` секунд (час) страхует лишь от случайного
зависания шага; превышение усекается с пометкой `clamped`, а не
отклоняется. Событийной модели в ядре нет, поэтому ожидание - опрос с
нарастающим интервалом: на каждом тике проверяется `is_cancelled`,
терминальные запуски дерева (`list_records`) и наличие извещений
(`has_notifications`). Ящик только читается: `take_notifications` не
вызывается, иначе `sleep` украл бы извещение у следующего шага. Ответ
содержит `woken_by` (`event` / `timeout` / `cancelled`) и `finished` -
только идентификаторы ставших терминальными запусков, без `summary` и
`artifacts`: тело результата читается `subagent_result` (или
`read_subagent_state`, если нужен журнал). Таймаут ничего не отменяет. Инструмент разрешён и
детям, а корень дерева (ключ ящика и списка запусков) вычисляется по
`root_run_id` записи родителя - ребёнок знает только родителя, и промах
ключом был бы молчаливым.

**Пояснения к статусу (`run_note`).** Голое слово статуса не позволяет
принять решение: `failed` может значить «повтори» и «не повторяй никогда»,
а `running` рядом с истёкшим ожиданием неотличим от зависания. Поэтому
результаты `spawn_agent`, `subagent_status`, `read_subagent_state` и
`resume_subagent` несут поле `note`, которое переводит состояние в
следующий шаг (`_attach_note`, `_note_for_payload`, `_journal_note`).
Разбор строится на `status`, `error_code`, `retryable` и `steps_used`:
исключение цикла (`internal_error`) объявляется дефектом платформы, который
не лечится повтором; сбой провайдера - поводом на одну изменённую попытку;
`max_steps` отправляет делить задачу (продолжение не добавляет шагов);
`timeout` - сужать объём; `awaiting_input` - читать журнал и продолжать;
пустой или отсутствующий журнал прямо говорит, что это НЕ значит, что
ребёнок ничего не делал. Пояснение живёт рядом с данными, поэтому
работает для каждого сотрудника без правки его системного промпта.

**Сбой и завершение ребёнка.** Исключение внутри цикла ребёнка
перехватывается в `_execute_child` и превращается в невоспроизводимый
повтором результат: `status=failed`, `error_code=internal_error`,
`retryable=False`, текст исключения в `summary`. Сбой провайдера приходит
из самого цикла с `provider_error` и остаётся `retryable`, поэтому
вызывающий отличает «платформа сломалась» от «провайдер не ответил».
`child_thread_id` и `workspace` фиксируются в записи запуска ДО старта
работы, а если раннер не вернул тред в результате, `_execute_child`
подставляет его сам - результат и запись не расходятся.

**Итог в журнале ребёнка.** `finish_run` вызывает
`_record_child_handoff`, который дописывает в раздел `Handoff` абзац
`Runtime outcome (run <id>)` (`dev_agent.task_state.record_runtime_handoff`):
статус, `stop_reason`, `error_code`, число шагов, `retryable`, сводку и
незакрытые пункты. Запись идемпотентна по `run_id`, не затирает текст
самого ребёнка и выполняется best effort - сломанный журнал не превращает
завершённый запуск в failed. Это единственный канал, который работает для
ребёнка, вообще не писавшего журнал (read-only задание, падение до первого
`task_state_init`).

**Автономия ребёнка.** У субагента нет человека, который нажмёт
«Разрешить», поэтому `state.child_mode` меняет поведение цикла: вызов,
требующий подтверждения, не останавливает работу, а возвращает отказ
`confirmation_required` с требованием переписать операцию без
подтверждения либо сообщить о блокере. Каталог инструментов ребёнка
дополнительно урезан (`child_disabled_tools`): создавать и изменять
сотрудников, помощников, навыки и подключения он не может. Вопрос
человека ребёнку недоступен; вопрос СВОЕМУ агенту - отдельный инструмент
`ask_parent` (см. ниже).

**Диалог: парковка, распаковка, доставка вопроса.** Вопрос ребёнка - это
не новый прогон и не `resume_subagent`, а пауза внутри того же прогона.

- **Парковка.** `ask_parent(question, options, done, blocked)` валидирует
  вопрос (непустой, в пределах `question_max_chars`) и проверяет бюджет
  раундов; затем `OrchestrationService.park_run` переводит запись в
  `awaiting_input` с `await_reason="question"`, сохраняет текст вопроса,
  варианты, «что сделано», «на чём застрял», номер раунда и абсолютный
  `deadline`. Прогон останавливается на границе шага: тред, журнал и
  записанные файлы остаются на месте, `run_id` не меняется. Результат
  инструмента возвращает `parked=true` и текущее число израсходованных
  раундов, чтобы ребёнок видел остаток бюджета.
- **Распаковка.** `answer_child(run_id, answer)` (только для родителя-
  владельца дерева) проверяет, что прогон ждёт ответа ИМЕННО на вопрос и
  что `deadline` не истёк; ответ клампится по `answer_max_chars` и
  доставляется как сообщение пользователя `[PARENT ANSWER] ...`,
  после чего цикл ребёнка продолжается с того же шага. Если ребёнок
  спрашивает снова, ответ инструмента несёт следующий вопрос
  (`parked=true`) и подсказку: ответить ещё раз либо потребовать
  закончить с тем, что есть.
- **Восстановление разговора.** Состояние ребёнка живёт в памяти реестра
  ЭТОГО процесса; после перезапуска оно восстанавливается из транскрипта
  ребёнка (`read_transcript`), поэтому ответ не начинает работу заново.
  Первый ответ поднимает запись в реестр (`revive_parked_run`), а корень
  дерева восстанавливается по идентификатору диалога
  (`roots_for_thread(thread_id)`) - сессия его не помнит. Ожидающий прогон
  не держит ни потока, ни слота пула: при распаковке дерево пересоздаётся.
- **Доставка вопроса родителю.** Блокирующий `spawn_agent` возвращает
  вопрос прямо в результате (`status=awaiting_input`, поле `question`),
  поэтому ответ можно дать в том же шаге. Фоновый ребёнок кладёт
  извещение в ящик дерева, и цикл родителя получает его скрытым
  system-сообщением `[SUBAGENT_NOTICE:<run>:<status>]` на следующем шаге -
  опрос не нужен. Право на извещение захватывается атомарно
  (`runs.claim_notice`), а ключ захвата несёт номер раунда, поэтому два
  вопроса одного прогона дают два отдельных извещения, а не теряются.
- **Вопрос - это данные.** Текст вопроса приходит родителю в границах
  `[DATA_BEGIN: subagent_question] ... [DATA_END]` - и в результате, и в
  извещении: ребёнок читает файлы и веб-страницы и может процитировать
  чужие команды. Запись хранит текст без обёртки: границы - транспорт, а
  не содержимое. Системного канала у вопроса нет.
- **Срок и уборка.** По истечении `answer_wait_seconds`
  (`expire_parked`, `runs.expire_unanswered`) прогон завершается как
  `failed/answer_not_received` с текстом вопроса в сводке; частичный
  результат и записанные файлы сохраняются, отложенный релиз дерева
  снимается, слот лимита ожидающих освобождается. Уборка выполняется на
  путях чтения, поэтому брошенный вопрос не занимает ни место в
  интерфейсе, ни слот ожиданий. Поздний ответ отвергается с тем же кодом
  и НЕ оживляет прогон: иначе об одном прогоне было бы две правды.
  Осиротевшее ожидание без родителя переводится в `failed`.
- **Лимиты диалога** (`core/orchestration/contracts.py`): `dialog_rounds`
  (5, считается по вопросам), `question_max_chars` (1500),
  `answer_max_chars` (4000), `answer_wait_seconds` (900),
  `max_parked_runs` (8). Значения клампятся: некорректное или
  отсутствующее даёт документированный дефолт, а не отключение
  ограничения. На спавне лимиты диалога замораживаются в записи прогона
  (`RunRecord.dialog_limits`), потому что ответ может прийти от другого
  процесса с чужим конфигом; конкурентность, глубина и таймаут остаются
  живыми.
- **Отмена.** `cancel_subagent`, в том числе каскадом, переводит
  ожидающий прогон в `cancelled` с причиной: ожидание не переживает
  отмену задачи.

**Интерфейс.** Статус-строка диалога показывает живые фоновые запуски,
скрытые извещения помечаются плашкой `_notice`, а обновление статуса идёт
через `st.fragment` - страница не перезапускается целиком. Ожидающие
ответа прогоны показываются отдельной строкой «ждут ответа: N» с агентом,
коротким `run_id` и текстом вопроса (до трёх строк, дальше сводка);
опрос не засыпает, пока такие прогоны есть. В ленте шага вопрос
раскрывается блоком с пометкой «вопрос субагента», вариантами, «что
сделано» и «на чём застрял». Состояние ожидания переживает перезагрузку
страницы: корень дерева берётся из меты диалога, а не из сессии.

### Поиск по диалогам (thread-search tools)
Три инструмента оркестраторов открывают историю диалогов: `search_in_threads`
(поиск по сообщениям), `list_threads` (список диалогов с пагинацией и
счётчиками) и `read_thread` (окно сообщений с абсолютными индексами). Без
`thread_id` все три работают с текущим диалогом
(`dev_agent.config.ACTIVE_THREAD_ID`) и не требуют предварительных
листингов; `scope` расширяет охват до одного оркестратора, списка
оркестраторов или всех диалогов. Read-side слой -
`core/threads_devagent.py` (`search_thread_messages`, `list_threads_filtered`,
`read_thread_window`), SQL-выборки - в `storage/repository_devagent.py`
(`repo_devagent_list_threads_filtered`, `repo_devagent_count_messages`,
`repo_devagent_load_threads_messages`, `repo_devagent_load_messages_window`).
Контроль доступа задаёт параметр `allowed_slugs`: DevAgent (`dev_agent`) видит
все диалоги, остальные оркестраторы - только свои; чужой `thread_id`
получает `Access denied`. Скрытые служебные сообщения (`tool_result` /
`AUTO_CONTINUE`) исключаются из поиска и чтения по умолчанию.

### Защита от переполнения контекста LLM (M1-M5)
Пятиуровневая защита от HTTP 400 «context length exceeded» (инцидент
1 053 249 > 1 048 576 токенов из-за tool_result на 1,65 млн символов):

- **M1 - политика размера результатов инструментов (спилл до отправки).**
  `dev_agent/tool_executor.py` и `dev_agent/universal_agent.py` пропускают
  результат через `_apply_tool_result_cap`: документ больше
  `_TOOL_RESULT_INLINE_LIMIT` (35 000 символов) до первой отправки
  записывается целиком в `<workspace>/.dev_agent/tool_results/` (ротация
  до 100 последних файлов), а модели уходит ограниченное превью
  head+tail со `spill_path` (полный payload восстанавливается через
  `read_file` с offset/limit). Аварийный фолбэк: если запись спилла не
  удалась, результат выше `MAX_TOOL_RESULT_CHARS` (200 000) заменяется
  ошибкой `result_too_large`/`result_size` без payload.
- **M2 - персист скрытых tool_result с сохранением проводной формы
  (resume-идентичность).** `summarize_tool_result_for_storage`
  (`dev_agent/agent_loop.py`) + оба пути записи `core/threads_devagent.py`
  обрабатывают каждое сообщение пакета по отдельности: документы до
  50 000 символов (включая все спилл-превью) сохраняются в БД
  байт-в-байт, так что после reload треда отправляемая форма совпадает с
  записанной; более крупные документы (аварийный путь) сжимаются до
  сводки (status, path, applied, размеры bulk-полей).
- **M3/B4 - единый бюджет истории (порог + гистерезис).**
  `build_economy_context` (`dev_agent/agent_loop.py`) +
  `_enforce_history_token_budget` берут бюджет из общей формулы
  `core.context_guard.history_cap` = `0.75 × (окно - лимит вывода) -
  промпт` (`input_budget`); вычитается `_ECONOMY_GUARD_MARGIN` (2048) под
  пользовательское сообщение. Под бюджетом список не меняется; при
  превышении ведущие сообщения режутся за один проход, причём в
  кэш-режиме фронт сбрасывается до `tail` сообщений - тот же сброс, что
  даёт переполнение окна `tail × multiplier` (единый триггер резета, а
  не отдельный глубокий срез); если и `tail` не укладывается, срез
  продолжается до нижней ватерлинии `0.75×бюджета`. Срез сворачивается в
  `economy_anchor` (фронт окна стабилен). Служебная head-мета -
  всегда. Одна формула для экономики и guard'а означает, что guard никогда
  не сдвигает фронт экономического payload'а.
- **M4/M5 - pre-flight guard в api_layer.** `core/context_guard.py`
  (apply_context_guard, `input_ceiling`/`input_budget`/`history_cap`) +
  `ContextWindowError` в `core/api_errors.py`; вызов из `send_request` до
  отправки. Резерв вывода - `min(max_out, max(4096, 0.25×окна))`;
  служебный head-блок эконом-меты не срезается; мягкий трим на 0.75
  окна, жёсткий предел 0.9 окна (выше общего бюджета, чтобы экономический
  payload проходил без среза), понятная ошибка без нового диалога;
  публичный `history_cap(window, max_tokens, prompt_tokens)` отдаёт
  эффективный предел истории.

### Запуск задач по расписанию (`core/schedules/`)
Владелец один раз описывает задачу, исполнителя и периодичность, а платформа
сама открывает диалог в нужный момент. Правило запускает **обычный диалог**
выбранного сотрудника (`kind=dialog`, без родителя), поэтому результат виден
в «Истории» наравне с диалогами, начатыми вручную; отдельного хранилища
переписки у расписаний нет.

Слои разделены так же, как в остальной платформе:

- **Значение правила** - `core/schedules/model.py`: интервал (число и
  единица), маска запрещённых дней недели и её пресеты, тихие часы,
  счётчики и сериализация строки. Канонизация текста тихих часов и
  пресетов держится здесь, чтобы два одинаковых по смыслу правила
  сравнивались равными.
- **Арифметика момента** - `core/schedules/calc.py`. Единственный источник
  истины о том, когда правило срабатывает: `compute_next_run` шагает по
  интервалу в зоне правила, применяет маску дней и сдвигает точку за
  пределы тихих часов. Предпросмотр в форме и движок запуска вызывают один
  и тот же код, поэтому обещанное и случившееся не расходятся, а сервер в
  другой зоне не меняет «09:00» на другое время.
- **Хранилище** - `core/schedules/store.py` и таблицы `schedules`,
  `schedule_runs`. Претензия на точку атомарна на уровне базы (уникальный
  ключ правила и планового момента), поэтому повторный тик после
  перезапуска или второй процесс ничего не удваивают. `settle_schedule`
  пишет счётчики и следующий момент отдельно от строки истории.
- **Исполнение** - `core/schedules/runner.py`: открыть строку истории,
  создать поток, прогнать цикл агента, записать исход. Три сбоя подряд
  дают `error_hold`, исчерпание `max_runs` - `finished`. Ручной запуск
  проходит тот же путь, но не двигает `next_run_at`: сетка остаётся там,
  где её оставил владелец, а счётчики узнают о запуске.
- **Планировщик** - `core/schedules/daemon.py`: один фоновый поток на
  процесс, идемпотентный `bootstrap`, сердцебиение для `is_alive`,
  `tick_once` забирает дозревшие правила и тратит на каждое отдельный
  воркер (счётчик `running_workers` нужен и для остановки, и для тестов).
- **Форма** - `core/schedules/form.py` без Streamlit: разбор и вывод
  локального момента, предпросмотр следующих точек, пресеты дней и
  подпись интервала. Страница (`ui/pages/schedules.py`) только рисует то,
  что посчитал этот слой.

Пропущенная точка не догоняется: если платформа была выключена, в историю
пишется `skipped` с причиной `missed`, а сетка уезжает вперёд. Иначе
десять часов простоя превратились бы в десять запусков подряд - ровно то,
чего владелец не ждёт от правила «раз в день».

### HTTP API v1 и фасад запуска (`core/gateway/`, `server/`)

Слой разделён по направлению зависимостей: `server/` → `core/gateway/` →
`core/orchestration/` → `dev_agent/`. Ни один слой не импортирует
вышестоящий, поэтому HTTP-транспорт и UI пользуются одним и тем же
контрактом запуска, а не двумя его копиями.

- **`core/orchestration/dialog_runner.py`** - транспортно-нейтральный
  драйвер одного шага диалога. Принимает тред, сообщение и колбэки;
  возвращает исход шага. Не знает ни про Streamlit, ни про HTTP.
- **`core/gateway/`** - фасад над `core/orchestration/`, публичный
  in-process API: `dialog.py` (запуск и закрытие диалога, освобождение
  слота), `runs.py`/`threads.py` (состояние прогонов и сообщения),
  `entities.py` (оркестраторы и помощники), `health.py`, `dto.py`
  (Pydantic-модели публичных ответов) и `errors.py` (`GatewayError` с
  кодом, статусом и плоским конвертом `details`). Фасад импортируется без
  `streamlit`, `fastapi` и `pydantic` - это проверяется тестом.

**Модели как контракт.** Публичный ответ описан моделями на двух уровнях, и
граница между ними проведена осознанно. `core/gateway/dto.py` - dataclass'ы
ядра: они описывают форму данных внутри платформы и могут получить поле по
внутренней причине. `server/schemas.py` - pydantic-модели провода: валидация
недоверенного ввода и схема OpenAPI, которых у типа ядра быть не должно.
Связывают их явные мапперы в конце `schemas.py`, поэтому расхождение - это
диф в одном файле, а не молчаливое изменение API.

У прежней схемы (голый словарь, собранный каждым участником) не было места,
где перечислены поля: форма существовала как договорённость, и расхождение
обнаруживалось запросом от клиента, а не сборкой. Теперь объявленная модель -
единственное место, где поля названы; необъявленное поле не появится
случайно, а переименование ломает тест, а не потребителя.

**Golden-тесты контракта.** `tests/test_api_golden.py` записывает точный
публичный JSON двадцати операций в `tests/golden/api_contract.json` и
падает на любом его изменении. Волатильные поля (время, идентификаторы
запросов) заменяются типовым тегом, а не отбрасываются, поэтому смена типа
поля тоже видна. Смысл снимка - разрешить внутренний рефакторинг: пока
публичный JSON совпадает, переписывать реализацию безопасно. Пересборка -
осознанное действие (`UPDATE_GOLDEN=1 pytest tests/test_api_golden.py`),
которое видно в диффе. Отдельный тест фиксирует сам инвариант: сериализация
модели через HTTP-слой (`jsonable_encoder`) даёт тот же результат, что и
дамп модели - это и есть допущение, на котором держится переход на
`response_model`.
- **`server/`** - HTTP API v1 на FastAPI. `app.py` собирает приложение
  (`create_app()`): lifespan поднимает каталоги, БД и оркестрационный
  сервис; `HostGuard` отсекает DNS-rebinding; `RequestContext`
  проставляет `X-Request-Id` и access-лог на шаблоне маршрута;
  `RedactFilter` вычищает секреты из логов. `auth.py` - Bearer-токен с
  кэшем настроек (5 с) и троттлингом 10 попыток/60 с, fail-closed 503.
  `instance_lock.py` не даёт запустить второй процесс на том же порту
  (flock, exit 3). Маршруты: `agents`, `dialogs`, `runs`, `threads`,
  `health`.

Эквивалентность UI: HTTP-слой не дублирует логику запуска, а вызывает тот
же фасад, что и страница чата, поэтому ответ не зависит от транспорта.
Ошибки отдаются единым конвертом (`code`, `message`, `details`) с
HTTP-статусом из `GatewayError`; ошибка валидации FastAPI переводится в
`400 invalid_request`, а не в `422`. Токены доступа хранятся отдельно
(`core/api_token_store.py`), не в конфиге платформы.

Запуск - отдельный процесс (`core/gateway_launcher.py`), зависимости -
в `requirements-api.txt` (те же версии закреплены в `requirements.lock`),
чтобы FastAPI не попадал в базовую установку. Способ установки -
`pip install -e ".[api]"` или установка из lock.

**Схемы ответов** (`server/schemas.py`) объявляют `response_model` для
каждого маршрута. Маршрут больше не собирает словарь и не отдаёт его:
он возвращает модель, и FastAPI сериализует её один раз. Объявленный
`response_model` - это и есть документация OpenAPI, описывающая то, что
маршрут действительно отдаёт, и одновременно причина, по которой
пропущенное поле становится отказом теста, а не сюрпризом для клиента.

**Статический анализ.** `pyright` работает в режиме `basic` по пакетам
`core`, `server`, `storage`, `sagaai` (настройки - в `pyproject.toml`).
Число находок держит бюджет `pyright_budget.json`, а не ноль: у проекта
есть места, где аннотация ничего не добавляет (колбэки Streamlit, модели
SQLAlchemy), и требование нуля вынудило бы либо остановить работу, либо
массово расставить подавления, под которыми скрылись бы настоящие ошибки.
Проверка падает только на РОСТ числа - исправление всегда проходит без
правки бюджета, а снижение отмечают отдельным коммитом. Бюджет, которого
нет в дереве, означает, что проверка ещё не введена, и это не ошибка.

### Экспорт/импорт оркестраторов (core API)
Формат `sagaai_orchestrator/v1` (JSON). Slug-конфликты разрешаются
генерацией нового (`slug_2`, ...). Инструкции импортируются без
перезаписи существующих. UI-интерфейс для экспорта/импорта намеренно
отложен.
