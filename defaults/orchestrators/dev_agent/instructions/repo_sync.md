# Repo Sync - правка и публикация файлов sagaai-platform

Эта инструкция обязательна для КАЖДОЙ задачи, которая меняет файлы локальной
копии репозитория **sagaai-platform** (каноничная рабочая папка
`sagaai_github_clean_copy_*`). Она дополняет инструкцию `local_repo_guide` и
описывает конвейер обновлений, построенный вокруг манифеста
**`file_versions.json`** (корень репозитория).

Принцип: GitHub `TVD2100/sagaai-platform` - источник истины и канал доставки
(публичный репо, MIT); правки делаются локально в чистой копии; публикуются
через инструменты GitHub (github_read_file / github_upload_file /
github_update_file) ТОЛЬКО после явного согласия пользователя; пользователи
получают обновления без токена по raw-ссылкам, указанным в манифесте
(`channel`), через встроенный апдейтер (`core/updater.py` + хук в `app.py`).

---

## 1. Манифест file_versions.json - единый источник версий

Структура:
```json
{
  "app_version": "0.1.0-preview.2",
  "channel": "https://raw.githubusercontent.com/TVD2100/sagaai-platform/main",
  "release_note": {"ru": "...", "en": "..."},
  "units": { "core": {"version": "1.0.0", "note": {"ru": "...", "en": "..."},
                        "files": {"<путь>": {"version": "...", "sha256": "..."}} } },
  "selectable": { "<путь>": {"version": "...", "sha256": "...", "note": {"ru": "...", "en": "..."}} }
}
```

- **units.core** - весь исполняемый код (core/, storage/, ui/, dev_agent/*.py,
  app.py, tests/, scripts/, requirements.txt, pytest.ini, __init__.py,
  assets/, certs/). У пользователя такие файлы обновляются ТОЛЬКО единым
  пакетом. При правке любого файла пакета bump-ить версию конкретного файла;
  версию самого пакета (`units.core.version`) - при значимом релизе пакета.
- **selectable** - всё остальное поставляемое содержимое (системные промпты,
  инструкции, пресеты assistants/skills/rag_bases, локализации, документация).
  Пользователь может выбрать/отказаться от каждого файла отдельно.
- Версии файлов - semver. У системных промптов версия в манифесте обязана
  совпадать с версией в заголовке файла (`# DevAgent - System Prompt (v3.7)`
  → `"3.7"`); в первую очередь правь заголовок, потом манифест.

Инструмент сопровождения манифеста: `python3 scripts/verify_manifest.py`
(именно `python3`, а не `python`):
- `--init` - первичная генерация манифеста (один раз);
- `--add <путь>` - регистрация нового файла (после git add+commit файла);
- `--fix-hashes` - пересчёт устаревших sha256 после правок (после bump версий);
- обычный запуск - проверка схемы, покрытия репо, хэшей, консистентности
  app_version (должен совпадать с core/version.py);
- `--json` / `--strict` - машинный вывод / строгий режим для новых файлов.

Ошибки верификатора = блокер публикации.

---

## 2. Проверка свежести ПЕРЕД правкой (обязательна)

1. Убедись, что workspace - каноничная копия (корень = git-репо с remote
   origin https://github.com/TVD2100/sagaai-platform.git).
2. `git -C <корень> fetch origin` и проверь `git status --porcelain`: незакоммиченные
   правки должны быть задокументированы (commit) или зафиксированы с пользователем.
3. Сравни локальный манифест с манифестом на GitHub:
   `github_read_file(connector_id='3df44a61', repo='TVD2100/sagaai-platform', path='file_versions.json')`.
   - **Идентичны** → копия синхронна, можно править.
   - **Локальная копия новее** (есть файлы с большей версией / другого
     содержимого только локально) → СТОП: на GitHub невыложенные правки;
     сначала решить с пользователем, публиковать ли их, править поверх нельзя.
   - **GitHub новее** (файл на GitHub иной, чем локально) → локальная копия
     устарела: скачай актуальный файл через `github_read_file` и обнови
     локальную копию вместе с манифестом, и только потом правь.

Напоминание: автопуша нет, публикация только через API-инструменты и только
с явного согласия пользователя (см. п. 5).

---

## 3. Правка файлов

1. Правим только в каноничной копии; перед правкой файл прочитан целиком.
2. **Любая правка файла = bump его версии в манифесте.** Правила semver:
   - patch - исправление ошибки/неточности (не ломает контракты);
   - minor - новая функциональность (обратная совместимость сохранена);
   - major - ломающие изменения. У промптов версия совпадает с заголовком.
3. После правок - `python3 scripts/verify_manifest.py --fix-hashes`, затем
   обычный прогон (должен быть exit 0; ошибки - блокер).
4. Новый файл: `git add` + `git commit` локально, затем
   `python3 scripts/verify_manifest.py --add <путь>`.
5. `app_version` (core/version.py + манифест) bump-ится при релизе, а не при
   каждой правке файла; `release_note` описывает суть релиза для пользователя
   (его видят в UI обновлений).
6. Если версия файла поднята, а содержимое менялось - обновите при
   необходимости `note` (ru/en) файла/пакета, чтобы пользователь понимал суть
   изменения (особенно selectable-файлы).

UI-строки - только через i18n (`langs/`); код-комментарии - по-английски.

---

## 4. Тесты перед публикацией (обязательны)

1. Targeted-тесты изменённых модулей (для сложных изменений - сценарные тесты).
2. Регрессия: `python3 -m pytest` - весь набор должен быть зелёным.
3. `python3 scripts/verify_manifest.py` - без ошибок.

---

## 5. Публикация на GitHub (ТОЛЬКО после явного разрешения пользователя)

1. **CHANGELOG.md никогда не публикуется - ПОСТОЯННОЕ исключение.** Ни один
   инструмент загрузки (github_upload_file / github_update_file /
   ghr_upload_file / ghr_update_file / ghr_batch_commit / ghr_batch_upsert)
   не должен загружать CHANGELOG.md - ни по одному файлу, ни пакетом. При
   формировании пакета файлов всегда отфильтровывай CHANGELOG.md из payload
   (при чтении файлов с диска - явно пропускай этот путь). CHANGELOG.md
   ведётся только локально и не входит в манифест (COVERAGE_SKIP).

2. **Предпубликационный отчёт обязателен.** Перед любым обращением к GitHub
   закончи все правки, тесты и манифест, затем покажи пользователю:
   - полный список изменённых файлов (пути), для каждого - что именно
     изменилось (кратко, по сути, с пометкой «новый файл» где применимо),
     а также новая версия в манифесте (было → стало);
   - для изменённых файлов укажи bump версии и пересчитанный sha256 - они
     уже должны быть зафиксированы в file_versions.json;
   - итоги тестов (targeted + регрессия + верификатор манифеста);
   - пометку, что CHANGELOG.md исключён из загрузки (постоянное правило).
   Отчёт завершается ОБЯЗАТЕЛЬНЫМ вопросом: «Публиковать эти изменения на
   GitHub?» (перечисли варианты: все файлы / выборочно / отмена).

3. **Жди явного разрешения.** Пушить (github_upload_file / github_update_file)
   можно ТОЛЬКО после явного «да»/«публикуй» от пользователя. До этого запрещён
   любой вызов инструментов GitHub, меняющих репозиторий (чтение для сверки -
   можно). Изменить файл после одобрения = повторить запрос разрешения.

4. Порядок публикации при согласии:
   - изменённые файлы по одному: `github_read_file` (получить актуальный sha) →
     `github_update_file` с sha (или `github_upload_file` для новых файлов);
     либо одним пакетным коммитом, если пользователь явно попросил «пакетом»
     (`ghr_batch_commit` / `ghr_batch_upsert` со списком {path, content});
     в любом случае CHANGELOG.md в набор не включается;
   - **`file_versions.json` - ПОСЛЕДНИМ** (он - маркер завершённой публикации:
     пользователи сверяются с ним); при одиночной загрузке каждого файла
     манифест идёт последним вызовом; при пакетной загрузке манифест входит
     в тот же пакет вместе с остальными файлами;
   - пути идентичны относительным путям в workspace (корень репо).

5. Верификация публикации: повторный `github_read_file(file_versions.json)` и
   сверка с локальным манифестом; по каждому выложенному файлу - повторное
   чтение ключевых строк.

6. После успешной публикации - локальный `git add + git commit -m "<суть>"`,
   чтобы история локальной копии отражала состояние GitHub.

---

## 6. Как эта инструкция помогает пользователям

Манифест + встроенный апдейтер (core/updater.py, хук в app.py, UI «Обновления»)
доставляют изменения пользователям автоматически и без токенов: апдейтер
качает манифест по `channel`, показывает обновления (release_note, note
юнитов/файлов), пользователь выбирает, что ставить (selectable - по файлам,
units - только пакетом), файлы скачиваются, сверяются по sha256 и применяются
атомарно при холодном старте (бэкап + откат при сбое). Правильно ведя манифест,
ты тем самым публикуешь рабочие обновления.
